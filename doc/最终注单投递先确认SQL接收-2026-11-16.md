# 最终注单投递先确认 SQL 接收

> 本方案已被用户 2026-11-16 明确要求取代：不写 MySQL，直接写 ES。配套 SQL 原文保存与投递代码已移除，最新实现、测试与应用状态见《注单账变直接写ES-2026-11-16.md》。下文仅为历史记录，不作为当前行为。

2026-11-16 开始核验，上一批下注及撤注原账变合并 13 文件已全部应用，0 待应用。本轮继续核对资金原文首次持久接收，发现最终注单定时投递仍可直接写 ES，没有先确认既有 MySQL 原文存储。

## 修复行为

lottery 从原已完成结算快照提取原注单，填入原成功入账结果中的余额后，先调用既有 StoreFinancialRecords，将该批原结果交给 fg_game_storage 接收。原存储按既有文档身份、版本和完整原文检查，事务失败或版本内容冲突不能算已接收。

只有该批 SQL 成功，才继续向原 ES 索引写入，完成后推进原 ReportOffset／BillOffset／ReportsIndexed。SQL 失败不发出该批 ES 写入；账变已接收但注单接收失败时也不提前推进整个批次进度。重复操作仍使用原局、玩家、时间、版本、log 和原余额，不读取当前钱包来替代历史余额，不重新结算。

SQL 接收成功而 ES 失败时，原 SQL 原文保留，原快照进度不变，下一次投递继续使用同一原文。沿用已有 SQL 原文到 ES 的保存能力，不新增资金幂等流水、独立恢复任务或其他 Redis 历史副本。

扫描选择及实际处理前均检查终态一小时期限。已满一小时的原快照不因物理清理尚未完成而继续被这条投递路径读取。CLAIMED、账户失败或原结果不完整仍不能作为成功注单保存。

## 范围与限制

- 覆盖 NORMAL、VOID_REFUND、SEAT_NET、BANKER_NET 的原最终注单投递；刮票沿同一已完成原快照路径。最终现金注单仍是 go_gp_settlement，详情仍在 log，原资金账变仍在 go_gp_flowing_water。
- SQL 每批最多 100 条、超时 3 秒；ES 沿原每批 40 条写入，原每轮房间数量限制保留。网络操作不持有原快照锁。
- 不修改余额、cash_revision、带入凭证、奖池或原下注，不重放退款、派奖或发牌。没有新增表、Redis 键或 protobuf 字段。
- 只保存已有原文，不补造旧记录、版本或未知结果。旧原文缺少有效 RowVersion 时，既有 SQL 接口明确拒绝，不能猜一个版本冒充原记录。
- 终态一小时到期仍直接删除；超过期限、SQL 尚未接收的原文仍可能丢失。Redis 完全丢失及部分旧入口也未因此全部收尾，不能宣称所有故障下永久零丢失。
- 已接收 SQL 原文不随 Redis 快照删除，后续保存继续沿原流程。真实环境 MySQL／Redis／ES 多实例故障验收仍待完成。
