# 客户端资金请求实例容量保护

2026-11-18，Asia/Shanghai。继续限制慢资金请求导致的待执行闭包积累。保留已有修改，不重启服务、不提交代码。

## 问题与处理

原 create-handler 的 WebSocket 入口限制每个连接最多 64 条未完成消息，但多个连接仍能同时向同一钱包串行队列追加大量任务。单连接限制不能代替实例整体容量限制。

game-server/src/create-handler.js 在需要进入权威钱包的客户端消息入口，增加同一 runtime 最多 **256 条**待完成请求的准入计数。计数在进入登录租约协调／wallet.run 之前占用，等待协调的请求也纳入；超限用原 9999 消息提示“资金请求处理中，请稍后重试”，不进入钱包、不执行游戏动作、不扣款，不自动重试。

已受理任务不丢弃、不取消；结束或失败释放原计数，同步抛错也释放。计数属于 runtime.cashRequestAdmission，热替换处理器复用，不产生第二套额度。原单连接 64 条限制保持。

心跳继续走原无资金路径，不占新额度。正式刮票请求继续使用其原票务独立准入与原子资金接口，不叠加第二个资金事务。结算 tick 和断线清理直接走原内部 wallet.run，没有经过客户端入口的新额度，不因新请求过多而被拒绝；它们仍可能排在已经受理的任务之后，未增加抢占或优先调度。

本限制针对客户端进入实例的钱包请求，不宣称给所有服务器内部任务设置总上限，也不是分布式全局限流或账户速率限制。没有取消已提交金融命令，没有新增流水或恢复机制。

## 测试

扩展 test/game-server/request-limits.test.js，新增五项：

- 300 个独立连接同时提交，前 256 个进入权威钱包；44 个只收到繁忙提示，不关闭连接。容量满时心跳仍正常，原任务排空后可再次接受。
- 四个连接各受理 64 条后替换处理器，新处理器共用原计数，不能绕过上限；排空后恢复。
- 同步 wallet.run 抛错和异步拒绝都释放实例／连接计数。
- 登录协调等待期间已经计入实例上限，未提前进入钱包。
- 满额时真实处理器的 tick 和 onClose 仍将内部任务交给钱包，未被客户端上限拒绝。
