# 旧接口原始注单与流水持久保存

上一批“刮刮乐最终战绩与常驻时钟保护”4 个 Go 文件已应用，实际摘要核对为 0 待应用。本轮继续处理旧资金接口的报告输出，并补统一接口 SaveBill 的原流水保存；不变更旧游戏扣款和派彩规则。

## 实现

- lottery 旧接口的 SaveRecord／SaveBill 先在现有玩家库 fg_game_storage 保存原输出文档，事务成功后才结束本次同步保存。不是只把原指针放到内存队列。
- 不新增表或字段，使用 game_id=0 和 final-record: 前缀，与原游戏恢复状态、用户中心报告前缀隔离。
- 注单身份沿用 agentId|userId|roundID 哈希，版本取原 RowVersion；原牌谱、注单时间、金额、余额、币种均按调用时内容保存。不同版本保留为不同原始快照，同一版本不能用另一份内容覆盖。
- 流水保留原 FlowingWaterOn、时间、bet、award、账后余额及说明，ES 使用同一固定文档身份和 create，重复投影不产生另一条流水。
- 注单 ES 写入采用 external_gte 原版本，较早的旧进程快照不能覆盖较新结果；版本冲突 409 代表 ES 已有更新版本，不触发资金变化。
- 单一 lottery 报告循环每秒最多读取 40 份原文，受 8 秒超时限制，不叠加慢查询；SQL 中尚未确认索引的记录不设置过期时间。ES 确认后保留 31 天，定时清理仅限本前缀、game_id=0 且已索引到期的行，每次最多 100 条。
- 换进程后扫描的是原已保存的文档，不重新调用下注、开奖、结算、退款、派奖或资金对账。
- 统一接口原 SaveBill 也使用此保存入口；统一结算最终注单仍沿用上一批结算快照路径，不改回另一条内存输出链路。
- MySQL 暂时失败时记录明确错误，原注单缓存／流水队列仍保存原内容；原批次消费者改为重试 SQL 持久保存，SQL 未确认不清空批次，后续 ES 由报告循环索引。

## 兼容边界

旧游戏有多条资金路径，一部分已经在调用保存前实际扣付。本轮不把报告保存失败改成“投注失败”，因为该返回可能诱发客户端重试并重复扣付；不根据当前余额假造退款、不为显示失败回滚真实已完成派彩。

因此本轮的保证是：**MySQL 已成功保存的原注单和流水，进程替换或 ES 故障不会使原文仅随内存消失**。资金变更之后、保存函数被调用之前，以及 MySQL 尚未成功接收时退出进程的窗口仍存在。SQL 故障后的原内存缓冲仍不是跨进程持久保证；错误日志会明确 not durably stored，而不是把保存失败伪称成功。

这不是新建的资金幂等流水或未结算记录；保存的是原接口已产生的原输出文档，索引阶段不参与资金事务。原业务 API 返回、流水金额口径、既有余额和奖池规则本轮保持原逻辑。

## 修改位置

4 个 Go 文件：

- lottery/dao/final_record_store.go：现有游戏存储中的原文保存、版本身份验证、批量 ES 投影及有限清理。
- lottery/dao/final_record_store_test.go：SQL／ES 隔离回归。
- lottery/rpc/service.go：旧 SaveRecord／SaveBill 先持久保存，失败沿原缓存重试。
- lottery/unified/service.go：统一接口原流水同步保存，启动共享的原记录投影。

不需迁表。沿用 InitMysqlDb 已创建的 fg_game_storage，正常发布 Go 才会生效。本轮不修改 Node 业务或启动常驻服务。
