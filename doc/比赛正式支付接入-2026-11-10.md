## 调用与事务边界

Node match 继续管理比赛、报名状态、排名、广播和计划；资金及门票事务由现有 data-center 执行。新增的是现有 GogameStorageService.Call 的 matchPayment 业务操作，不改变 proto，不接收 SQL、表名或客户端自报余额。

统一 common.matchPayment 支持 charge、refund、award、query。match/src/payments.js 只调用该门面，不连接数据库、不保留本地权威账本、不使用 CommonRpcProd.debit/credit 占位接口。

报名和退款的顺序调整为：在比赛事务内保存/读取原计划，释放事务，再调用权威资金接口；最后重新加锁读取当前状态、核验凭证并更新。资金端也会获取同一比赛行锁，不能嵌套在 Node 持有的流式比赛事务内调用，否则会相互等待。

资金端以持久计划为准核对代理、玩家、币种、报名尝试编号、原费用和指定门票。票据准备及支付结果仍保存在既有 gg_match_runtime 对应报名项中，比赛行锁、这些记录与 outbox 沿用原 MySQL 事务；不新增独立幂等流水表、未结算表或启动重放程序。

## 扣费与退款

- 每次报名复用原 match:代理:比赛:玩家:尝试编号。报名费和服务费分开保存，总扣款必须等于两者之和，金额使用安全整数最小货币单位。
- 指定门票先按 owner、ticket_id、is_use=0 及比赛绑定规则锁定具体持有记录，并把具体 ID 与原报名计划一同提交。准备后出现不确定错误时保留原票据绑定，不能再选另一批门票。
- 实际现金扣款复用 cashwallet.Apply 的身份、币种、修订号和带入保留校验，不能消费棋牌桌已保留的金额。
- 现金变化与该请求既有 wallet marker 在同一 Redis Lua 内提交。SQL 凭证尚未提交时 marker 不过期；提交后才可设置 7 天 TTL，后续重试先读持久 SQL 凭证，不能因 marker 过期再次收费。
- 明确余额不足时，退回本次准备的原门票并记录拒绝结果；未知错误保持原计划等待确认。比赛取消或截止后，没有现金成功标记的准备项只恢复门票，不补扣过期报名费。
- 用户于 2026-11-10 更新：退赛、人数不足取消和管理员取消均退回实际支付的报名费加服务费。退款核对原计划、原代理和原币种，旧比赛的 refund_service_fee=0 不再限制未执行退款。重复退款读取原凭证；未扣款的报名只关闭原尝试，返回 uncharged，不生成一笔现金退款。已完成历史退款不自动补发。
- 已扣款但 SQL 保存失败，重试确认原 marker，不重新扣款。已退款但 SQL 保存失败，同理不重复入账。Node 不覆盖并发取消、已完成退款或后续报名尝试的当前状态。

## 奖励与查询

资金端不仅匹配待派奖计划，还复核比赛已结束、真实参赛者状态、最终名次和锁定的 award_json；金额、币种、奖品种类、门票种类和原奖励编号必须一致。

现金奖励经既有权威钱包增加余额；同一奖励编号不重复入账。门票奖励在同一 MySQL 事务内扣发行库存、增加持有记录并保存原奖励凭证，不重复扣库存或发票。库存不足保持待处理，不假造成功。

query 从 SQL 返回原报名/奖励的确认状态和凭证，查询本身不扣钱或发票，不要求钱包或门票数据库可用。资金请求超时后 Node 先查询；只有查到相应成功凭证才确认，否则保留原计划等待再次处理。

发奖每次推进最多 32 项，避免无限处理；单次指定门票和单项门票奖励最多 1000 张，新配置在管理入口同步校验。失败项保留原编号，不生成新编号绕过；尚未实付的奖励不向客户端宣称已发放。

## 数据库条件与部署

现有 gg_match_runtime 在 manager 库，gg_ticket_hold 在 player 库。涉及门票时，后端读取两个连接的 server_uuid 与数据库名，必须确认同一 MySQL 实例，且 manager 连接有访问 player 库对应表的事务权限；随后使用经核验的服务端库名执行跨库事务。不同实例、元数据缺失或权限不足时失败，不拆成两个独立成功事务。纯现金支付不要求这项门票条件。

本批复用已有表结构，无新增 DDL；仍需部署环境已有比赛运行表、门票库存、持有记录和正确的账户缓存。真实 MySQL 条件尚未验证。不能把跨库 SQL 事务与 Redis 钱包描述成一个数据库事务：它们之间通过原计划、已提交的门票准备状态及既有 wallet marker 确认。
