# 比赛管理表单提交锁与编辑会话保护

本轮继续比赛管理编辑及提交流程，修复连续提交重复发起请求、旧保存回调干扰新编辑器，以及旧门票发放结果清除新请求编号的问题。

## 问题与修复

原列表按钮有自己的禁用逻辑，但比赛、盲注和运营表单的 submit 事件没有提交锁。真实浏览器中连续 requestSubmit 可以在首个保存完成前发出两次建赛请求；修改前已复现 2 次请求，失败证据为 cache/admin-submit-before-browser.log。

新增 match/src/admin-submissions.js，为三个既有表单分别保留一个进行中的提交锁。锁在调用操作前同步取得，重复提交不再发起第二个请求；请求结束、同步校验异常或异步失败后释放。独立表单仍可分别操作，失败不自动重试，用户可以在失败结束后明确重试。

match/src/admin-page.js 的 submitForm 在提交期间禁用保存按钮并设置 aria-busy，结束后恢复原按钮状态。没有新增金融幂等记录、资金流水、Redis 键或服务端重试机制，原服务资金确认及防重规则继续有效。

比赛、盲注和运营保存均在提交时固定本次记录 ID、数据、管理身份和编辑版本；接口成功或失败返回时再次核对该编辑会话。保存 A 尚未返回时打开 B，旧请求仍可完成原服务器操作，但不会关闭、清空或把旧错误显示到 B 编辑器。盲注新增／编辑／关闭也增加相同的编辑版本保护。

门票发放同样捕获原票种、接收玩家、张数和原 requestId。旧发放结果不能清除后来新开的 issueRequest 或关闭新发放表单，也不会因界面变化重新发票。手动重试原表单仍使用其原编号；主动重新打开发放表单仍按原规则生成新编号。

切换管理身份、管理项目或关闭编辑器继续使旧编辑会话失效；上批只读请求取消和迟到响应保护保留。进行中的同一表单保存锁不会因为打开另一个编辑会话而提前解除，避免旧请求尚未结束时又发送新的保存。

## 验证

新增 test/match/admin-submissions.test.js 四项：重复提交只执行首个操作、独立表单并发分别释放、同步／异步失败后释放且不自动重试、同步嵌套提交也不能绕过锁。

管理请求、菜单集成、盲注、代理权限及提交锁专项共 **19 项通过**，日志 cache/admin-submit-scoped-node.log。Node 全量 **1351 项通过**，日志 cache/admin-submit-full-node.log，含实际剔除 test/cache 的生产副本检查。

扩展真实浏览器回归：

```powershell
node test/browser/check-match-admin.mjs --proxy --submission-check --identity-check
```

浏览器使用独立 profile、隔离 HTTP 端口和内存存储。通过真实接口先提交，再延迟测试页面接收结果，验证：

- 连续提交比赛表单只发 1 个 POST，实际存储只创建 1 场该名称比赛。
- 保存期间打开另一份比赛编辑器，旧响应不会关闭新编辑器或改掉新名称。
- 连续提交门票发放只发 1 个 POST，真实测试库存仅扣对应 2 张。
- 原发票尚未返回时重新打开发放表单，旧结果不清掉新 requestId、新接收玩家或新编辑器。
- 原比赛发布、延迟报名／自动暂停展示、排期启停、门票发放、盲注删除、文本安全渲染及身份／旧响应隔离回归继续通过。

日志 cache/admin-submit-browser.log，未捕获未处理脚本异常。迟到响应使用隔离浏览器网络包装模拟，服务器业务已通过实际隔离接口执行；未操作真实比赛、真人库存或余额。这些结果不替代正式多实例和资金故障验收。
