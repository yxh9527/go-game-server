# 已结算战绩持久接收

本轮继续处理记录可靠性，完成用户中心最终战绩及德州回放的持久接收。它不是全部金融记录零丢失方案，下面明确区分保障范围。

## 行为变化

此前 game-server 在内存 outgoing 队列保存记录，data-center 直接写 ES；队列超过 50000 项会删除最旧项。本轮修改为：

1. data-center 先验证记录、账号、代理及币种，然后在同一 MySQL 事务保存整批已经结算的最终记录，事务提交后才返回 `durable:true,stored:n`。
2. 沿用玩家库现有 `fg_game_storage` 表，不增加资金流水、未结算表或数据库字段。报告使用 game_id=0、storage_key=`uc-report:<sha256>`；原游戏恢复接口拒绝 game_id=0，与正式票务等原记录隔离。
3. 记录身份包含目标索引、代理、玩家、币种及原记录 ID。同一记录回执丢失后重试不会重建或覆盖原内容；牌面、金额或其他内容改变则拒绝，整批事务回滚。
4. 提交完成后最多尝试 2 秒即时 ES 索引；ES 失败也可确认 MySQL 已持久接收，同时返回 indexed=false。ES create 使用原固定文档 ID，重复索引不会生成另一条记录。
5. data-center 在首次合法用户中心读写请求后启动单一周期投影，每 10 秒、8 秒处理预算、最多 100 条。它只读取已经保存的最终报告并补 ES，不调用任何扣款、退款、派奖或比赛恢复，不是启动资金对账机制。
6. ES 确认成功的 MySQL 报告保留 31 天；清理每次最多 100 条，限定 game_id=0、报告前缀及已确认索引且到期的行。ES 未确认的报告不设置过期时间，也不会因重试次数而删除。新进程收到用户中心请求后可继续处理原报告。
7. game-server 仅凭合法持久回执删除这一批 outgoing 记录；旧服务未返回 durable、数量不匹配或请求失败时保留并退避重试，不每个 tick 冲击存储。批次最多 100 项／约 8 MiB。
8. 取消队列超过 50000 条时删除最旧项；达到该高水位时普通座位桌先完成现有牌局、带出及到期回收，再暂停新开局；百人公共入口拒绝新增下注，已接受投注继续结算。该高水位是背压，不是已接收记录的丢弃策略。
9. 生产 RPC 先保存现金报告和回放，再处理玩家面板统计；任意阶段失败仍可沿原 ID 重试，不能把未收到持久回执当成功。

## 仍未解决的窗口

这一步保障的是**data-center 已经提交并确认接收的最终战绩和回放**。游戏服还没送达或 MySQL 尚未提交时，记录仍可能只在游戏进程内存中；资金结算完成到战绩首次被接收之间仍有崩溃窗口。当前手牌的回放数据若随游戏进程丢失，也不能根据钱包余额编造恢复。

lottery 的金融注单和资金流水仍走其原内存缓存／批次链路，本轮没有将它们改为本报告存储；原失败批次重试仍保留。ES 索引延迟期间，用户查询可能暂时看不到已经持久接收的报告，不返回本地假数据替代。

因此剩余清单中的“注单与用户中心跨进程持久保障”只完成其中一部分，不能标成全部完成。后续还需沿原资金结果或其他已授权方式关闭资金确认后的记录窗口，并完成实际数据库／多实例故障验收。
