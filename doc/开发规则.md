# 开发规则

本文是 gogame 后续开发的基础准则。实现 hall、game-server、match、管理后台及协议对接时，必须遵守本文。与本文冲突的做法，以本文为准。

协议字段、消息号、游戏类型 ID 的细节以 `doc/协议` 和现网客户端为准；本文只定边界、职责和不可违反的约束。

## 1. 仓库与范围

1. 本项目仓库是 `D:\project\gogame`（git 远程为 go-game-server）。hall、game-server、match、管理端、协议实现都写在本仓库，**一律使用 Node.js**。
2. 表结构与默认数据写在 `D:\project\gogames` 的 `app/tables/gogame`，由现有 `InitMysqlDb` 建表和灌种子。禁止在 fg 仓库实现本项目的 hall、game-server、match、比赛管理后台。
3. 热更新：HTTP / WebSocket 进程与连接常驻，业务模块热替换。禁止用整进程重启充当热更新（会踢掉在线连接）。
4. 当前要做的服务只有：**hall**、**game-server**、**match**，以及挂在 match 上的比赛管理能力。拓扑图中的 open-api、data-center、web-api、存储已存在，本仓库不重做。
5. `mock-server` 只用于本地抓包/联调测试，**不在开发范围**。不得把它当成协议实现、编解码标准或上线服务。
6. Node 依赖只装在仓库根目录，hall / game-server / match 共用这一份 `node_modules`。在 `D:\project\gogame` 执行 `npm install`；新增包也在根目录装。禁止在各服务目录再装一份。
7. 本地 dev：根目录 `npm run dev`。浏览器打开 `http://lobby.localhost:11042/21/0?userId=10001&userToken=dev&openId=10001&v=2.0.1279`。大厅静态 HTML 必须和 `__NEXT_DATA__` 一致（现网导出是 21/0），进德州在大厅里点「德州」。客户端 `isApi()` 依赖 URL 上的 `openId`，缺了会停在 launch。游戏 Cocos 静态资源是独立站点 `client-web`（默认 `http://localhost:4000`），大厅不托管这些文件。现网大厅会把 iframe 指到同端口的 `www.*`，本地 `www.localhost:11042` 由大厅按 Host 转发到 `client-web`。进房 WebSocket 仍走大厅本端口，再代理到 game-server。

### 1.1 测试、本地模拟与生产打包

1. 自动化测试统一放在根目录 test/，按 shared、hall、client-web、game-server、match 分目录；测试文件使用 *.test.js，浏览器手工回归放 test/browser/。禁止继续在业务 src/ 或 shared/rpc/ 内新增测试文件。根目录 npm test 递归运行全量测试；npm test --workspace=<服务目录> 运行对应服务测试。
2. 仅供本地开发使用的内存 RPC、种子数据、模拟鉴权与余额、Redis/PubSub 替代实现、LocalWallet、内存牌局回顾查询/存储、页面调试补丁及开发启动器，统一放根目录 cache/。npm run dev 使用 cache/dev.js。本地模拟代码仍须提交版本管理，不能放进 .gitignore；生产构建必须剔除。
3. 生产入口禁止静态导入 test/ 或 cache/；本地实现只可在 dev 分支按需加载，删除这两个目录后生产模式仍须可加载。RpcAdapter 同步工厂使用 Node.js 22.20+ 的同步 ESM require 按需加载本地类，保持现有构造接口；业务仍只依赖统一 RPC 门面。生产缺少钱包依赖必须报错，不能偷偷回退本地余额。
4. 正式业务的常驻房间、八小时排行榜、旁观列表、资金重试状态和 Redis 回顾缓存属于生产功能，继续留在业务模块，不得因为使用内存或名称含 cache 就迁走。生产 ES 查询仍只能经 data-center。
5. 使用 npm run build:prod 生成 dist/production/；只包含服务、shared、原始 static、生产启动器及依赖清单，排除 test/、cache/、mock-server/、tools/、文档、日志、临时文件、Git 元数据、node_modules。构建产物配置强制 env: prod / wallet.mode: online，生产启动器设置 GOGAME_ENV=prod、IS_DEV=0、NODE_ENV=production；源配置不改。部署前填好生产连接配置，在产物目录 npm ci --omit=dev，然后按服务启动。详见 doc/项目结构与打包.md。
6. 涉及目录调整必须更新相对导入、测试启动命令、热更新监听范围及文档；验证全量测试，并在真实剔除 test/cache 的副本中验证生产模块加载。不得用重启常驻服务代替业务热更新。cache 中的回顾与页面补丁仍通过版本号导入；相关监听由各服务启动器注册。

## 2. 物理架构

依据 `doc/系统物理拓扑图.drawio`：

```text
玩家 -> 第三方平台 -> open-api -> Redis/ES/MySQL
玩家 <-> hall <-> data-center <-> Redis/ES/MySQL
玩家 <-> game-server <-> data-center
game-server <-> lottery（grpc，图中 11）
管理员 <-> web-manager <-> web-api <-> Redis/ES/MySQL
match <-> Redis/ES/MySQL
match --Pub/Sub--> 全部 hall
```

环境切换对齐 fgServer：`shared/rpc` 的 `RpcAdapter`，业务只依赖 `rpcService.gateway / common / lobby / bus`，禁止直接 `new XxxRpcDev/Prod`。

```text
shared/rpc/adapters/rpcAdapter.js
cache/rpc/*RpcDev.js
shared/rpc/implementations/prod/*RpcProd.js
```

- **dev**（`env: dev` 或 `IS_DEV=1`）：`GatewayRpcDev` / `CommonRpcDev` / `LobbyRpcDev` / `BusRpcDev`，纯内存，不连 data-center、MySQL、Redis、ES。
- **prod**：`GatewayRpcProd` / `CommonRpcProd` 走 data-center gRPC；`LobbyRpcProd` / `BusRpcProd` 走 MySQL / Redis `match`。

编号含义（图中已有部分）：

| 编号 | 含义 |
| ---: | --- |
| 1 | 玩家向第三方平台请求登录游戏链接 |
| 2 | 第三方请求 open-api 鉴权，并获取指定代理的游戏/大厅链接 |
| 4 | 玩家用链接登录 hall |
| 5 | hall 访问 data-center |
| 6 | data-center 访问 Redis / ES / MySQL |
| 7 | 玩家在大厅点游戏后，hall 返回 game-server 地址，客户端用 WebSocket 连接 game-server |
| 8 | game-server 访问 data-center（余额、注单等） |
| 9–11 | 管理端链路 |

补充约束：

1. hall 可按代理划分，同一代理的玩家进入同一大厅，再从该大厅进入游戏。
2. match 负责比赛，不负责普通现金桌发牌。牌局在 game-server。
3. 消息队列使用 **Redis Pub/Sub**，不再引入 NATS 或其他 MQ。
4. 比赛状态广播使用独立频道 `match`，不得占用已有业务频道（例如配置同步用的 `message`）。
5. 信封格式：`{"event":"<事件名>","data":"<JSON 字符串>"}`。hall 全量订阅 `match`，用内存维护比赛列表；玩家拉比赛列表只读 hall 内存，不查库。

## 3. 协议准则

1. **必须兼容现有客户端**。客户端以本仓库 `static/client` 当前版本（现为 `2.0.1279`）和 `static/hall` 为准。
2. 大厅 HTTP 对齐现网：`GET /internal/v1/do`，`param` 为 Base64 查询串。已确认的 op 必须按协议文档实现，包括但不限于：
   - `op=38` 房间配置/列表
   - `op=45` 进入游戏，返回房间连接信息
   - `op=35` 比赛列表
   - `op=36` 比赛详情
   - `op=54` 钱包与门票数量
3. 房间 WebSocket 必须使用客户端已有消息号、字段名、进房流程。编解码以客户端 `readBuffer` / `writeBuffer` 及 `doc/协议` 为准，不以 mock-server 为准。
4. 游戏识别按 `doc/协议/游戏类型ID映射文档.md`：先 `gameType` / `subGameType` 定入口，再以服务端返回的 `roomType`、`playMode`、`gameRoomConfigId` 为准。禁止发明另一套 ID 去替换客户端字段。
5. 多语言名称、咨询等若协议里是 JSON 字符串，保持二次解析，不要改成另一套结构发给客户端。
6. 协议文档与客户端行为冲突时，以 **客户端实际收发** 为准，并回写协议文档。

## 4. 游戏抽象

游戏只抽象为三类基类。game-server 共用连接、房间、进出房、扣款结算；每个具体游戏单独目录，继承对应基类，配置写在本游戏目录。

```text
GameBase
  SeatGame      普通类（有座位、回合、分桌）
  HundredGame   百人类（共享一桌、下注区、可旁观）
  SlotsGame     slots 类（单人、无座位）
```

### 4.1 普通类

有座位、回合、分桌。典型：德州现金桌（`gameType=19`，`roomType=19`）、牛牛、炸金花、十三水、麻将、21 点、三公。

玩家路径：大厅 `op=38` 列表 → `op=45` 拿连接 → WebSocket 进 game-server。

### 4.2 百人类

共享一桌、下注区、可旁观。典型：`gameType` 1000–1003（百人棋牌、街机、百家乐、龙虎斗）。

玩家路径：房间列表 → 进入指定 `roomId` / `roomIndex` → `ENTER` 拿房间快照。

### 4.3 slots 类

单人、无座位。本项目客户端对应刮刮乐（`gameType=1004`，如 `roomType=61/63`）。

不得把 fg 的 lottery 玩法 ID 直接套进本客户端。

### 4.4 普通游戏房间与玩家座位生命周期

1. game-server 的房间管理必须按可信的 `agentId` 和游戏身份分组；同一代理、同一游戏类型的房间统一由该组管理，不能因玩家连接先后创建互不关联的同类房间。
2. 玩家请求进入普通游戏房间时，先在所属代理、指定游戏及同一配置的活动房间中查找；优先复用请求的未满座房间，否则复用同池有空座的房间，没有可用房间才创建。房间配置身份与运行时牌桌身份要区分；大厅 op=45 必须返回实际分配的运行房号，不能始终返回配置的第一个房号。
3. 普通座位类游戏的入房默认是旁观。玩家主动点击入座后立即占据座位，再弹出带入流程；从成功占座时起 **12 秒内必须成功带入金币**，否则服务端强制站起，释放座位并回到本房间旁观，不退出房间。未带入的座位不参与发牌/下注；带入失败、重复点击、重新打开带入面板、重连及热更新均不得延长原截止时间。超时带入请求不得扣款或隐式重新入座，必须重新点击入座；正常已带入玩家（包括本局全下后筹码为零）不受此初次带入时限影响。座位快照 carryLeftTime 和带入面板 leftTime 按客户端协议传剩余毫秒数。只有完成有效带入的玩家才参与牌局；旁观者不得收到仅面向座位玩家的操作选项。
4. 普通游戏房间自创建起保留 **8 小时**；空房间、仅机器人房间、最后一位真人离开都不提前回收。入房、离开、开新局、补充机器人及业务热更新不得重置创建时间。预创建的空备用房也从创建时开始计时。
5. 满 8 小时后停止开新局，停止接纳新玩家入座/带入，并从可分配房间池移除；若当前局进行中，允许原有玩家和机器人继续动作并正常结算，**结算后再销毁**，不得中断当前局或直接退还下注冒充结算。没有进行中的牌局则直接回收。销毁前按既有钱包接口带出真人剩余筹码，通知客户端房间解散；失败保留关闭状态重试，禁止重复带出。
6. 扩容按同一可信代理、游戏、房间类型、配置及 playMode 分池统计。口径为 **完全坐满的活动房间数 ÷ 活动房间总数**，达到 **80%** 时创建当前池房间总数 **5%** 的空备用房，数量向上取整且至少 1 间。不是全部已坐座位数除以全部座位数。真人和机器人占据的有效座位都计入满座判断；旁观人数不计入。到期及关闭中的房间不参与统计。
7. 备用房创建时不得自动入座机器人或启动牌局；实际进房后继续各游戏既有机器人行为。空备用房必须纳入房间池和大厅分房，不能只创建无法进入的内存对象。每次检查最多按该次快照扩一批，下次按新增空房后的比例重新判断。
8. 回收时同步清除房间索引、成员、房内回顾与验码缓存；已销毁的房号不能被旧连接重建。房间时钟、已用房号进度、待完成带出状态均保存在常驻对象，业务热更新不得丢失。当前普通现金桌分房/扩容接入德州 19、炸金花 25；比赛桌 101 仍由 match 管理分桌，不参与现金桌扩容。细节见 doc/协议/游戏/房间生命周期与扩容.md。

9. 普通现金桌每局结算完成后，按房间 carryMin（与入座最小带入相同的积分单位）检查在桌玩家的剩余筹码。低于准入金额或筹码为零时必须强制站起，带出剩余筹码并转为本房间旁观；等于门槛可继续。检查使用结算派彩后的桌上筹码，不使用账户钱包余额，不在全下尚未结算时执行。真人、机器人使用同一门槛；机器人的模拟筹码不得写入真人钱包，也不得原座位无条件补满。正在首次入座且尚未超过 12 秒带入期限的玩家保留该期限。先发送本局结算结果，再发送既有站起消息，禁止用房间登录快照打断结算动画。带出记账、统计、失败重试状态保存在房间对象，热更新/重复 tick 不得重复带出；失败期间不得开下一局。八小时到期则由统一销毁流程带出，避免重复退款。比赛桌淘汰由 match 管理，不套用现金桌最小带入规则。
10. 已有真人进入过的普通现金桌，在桌与旁观的真人都离开后，继续正常运行，**连续无真人期间完成 3 局结算后再挂起**，不按分钟计时。离开时正在进行的一局（包括离开触发弃牌而结算）计作第 1 局；第 3 局真实结算及必要带出后不得再发第 4 局。按公共结算累计手数计数，不按 tick、开局次数或机器人进出次数计数，重复结算不能重复计入。期间有任一真人进入（包括仅旁观、在桌等待带入）立即取消本次计数，游戏继续；下次最后真人离开重新计算 3 局。新建且从未有真人进入的空房/备用房仍等待首次真人入房，不为凑满 3 局自行启动机器人。挂起后停止发牌、机器人入离桌、带入、下注和游戏超时，既有离房带出、结算带出与持久化重试必须完成。实际真人入房时恢复剩余开局和机器人倒计时，再下发快照，仍默认旁观；机器人与大厅列表/分房查询不能取消计数或唤醒。计数基线和挂起状态保存于常驻房间，热更新不能清空，不改变房号、筹码、排行及创建时间。八小时始终从创建时计时且优先于 3 局规则，到期无未结算牌局直接回收，有当前局则按第 5 条结算后回收，不为补足 3 局延期或开新局。公共实现放在 core/room-lifecycle.js 与 SeatGame，所有 SeatGame 现金桌继承；比赛仍归 match，百人/单人玩法不直接套用桌位生命周期。

### 4.5 牌局回顾、牌局信息与桌面设置

1. 牌局回顾的权威数据源是 ES，但只能由 data-center 查询。game-server 必须经现有 data-center RPC 获取记录，禁止在 game-server 中连接 ES、构造 ES 查询或绕过 data-center 访问 ES。
2. 每次回顾请求先查 Redis；缓存键至少区分玩家、游戏和请求范围，设置明确 TTL。未命中才查 ES，成功查询后写回 Redis。必须限制和规范分页、局号范围及查询参数，避免无限范围或高频请求造成 ES 压力。
3. 回顾数据必须按现网客户端要求映射为既有消息号和字段结构；缓存只存可复用的查询结果，不改变权限校验，玩家只能读取自己有权查看的记录。
4. 牌局信息（例如局号、盲注、当前状态、玩家列表及历史回顾所需字段）应从房间/牌局配置和状态生成。可配置项由管理配置或对应房间配置提供，禁止散落硬编码；配置变更须按热更新边界生效。
5. 桌面设置使用客户端已有请求/响应字段和消息号。服务端保存或返回客户端支持的设置；不得发明客户端不识别的字段、消息号或设置枚举。新增协议行为前先核对 `static/client` 与对应 `doc/协议`。

在骨架可运行的前提下，先打通：

1. 普通类：德州现金桌
2. 百人类：经典百家乐

### 4.7 机器人实现与决策

1. 机器人公共生命周期只实现一套：创建身份、选座、概率入离桌、带入延迟、冷却、模拟账户和旁观清理统一放在 **core/robot.js**，由 **SeatGame.tick** 自动调度。各游戏目录的 **robot.js** 负责牌力评估、下注/出牌选择和行动思考时间；游戏引擎调用自己的策略，不得复制公共调度器。现有德州和炸金花均直接继承 SeatGame 的 tick、queueStart、入座、带入、站起和结算准入检查。
2. 机器人与真人共用游戏动作校验、下注扣款、广播及结算入口。金额单位必须遵守既有协议，不能另写机器人专用扣款或修改客户端来适配机器人。真人默认旁观、主动入座带入的流程不得改变。
3. 机器人只能使用自己已获知的底牌、已公开公共牌和公开的座位/筹码/下注状态；禁止读取对手底牌、洗牌结果或未发出的牌。炸金花未看牌前也不得使用自己的底牌决策。胜率采样只能从排除已知牌后的未知牌集合生成，且必须限制计算量和缓存生命周期。
4. 决策须结合牌力、跟注成本、底池赔率、剩余筹码及位置，允许合理的跟注、过牌、下注、加注、弃牌和比牌。禁止固定到某轮就弃牌、超过固定底注倍数无条件弃牌，或筹码不够跟注时无条件全下。允许有限随机变化和不同风格，但不得控制发牌或输赢结果。
5. 思考时间须有变化且早于行动超时；房内有真人在桌或旁观时，机器人可自主对局，不要求真人参局。最后真人离开后继续正常对局，连续无人期间完成 3 局结算再按第 4.4 节挂起；中途真人进入取消计数。不提前回收，仍遵守八小时生命周期及到期结算规则。robot.js 必须纳入版本化热更新依赖链，不得靠重启服务生效。修改策略须验证动作金额、隐藏信息隔离、多局结算和筹码守恒。
6. 已激活且未挂起的普通现金桌（包括连续无人尚未完成 3 局期间）必须持续进行概率入桌、离桌决策，不能只在真人进房或入座时一次性补齐机器人。挂起期间停止调度，唤醒后沿用剩余时间，不集中补执行挂起期间的动作。默认参数仅定义在 core/robot.js 的 roomBehavior，配置优先级为公共默认值 → 游戏 config.robotBehavior → 房间 cfg.robot_behavior；无需在每个游戏重复声明。默认每 5–10 秒检查一次，有空座时以 60% 概率安排一名机器人入座，机器人至少保留一个空座给真人。默认入座满 45 秒后，每局结算动画完成、下一局发牌前，以 15% 概率独立决定离桌；空闲时按同一周期判断。每局仅做一次结算离桌判断，额外 tick 不得反复抽取，检查定时器不得使其错过局间机会。
7. 机器人入座同样先占零筹码座位，再延迟 1–3 秒走既有带入处理；12 秒内未成功带入即站起。离桌走既有带出、站起及旁观流程，等待随机 15–45 秒后才可再次按概率入座；不得原地无条件补满筹码。模拟账户初始默认有五份正常带入资金，带入扣减、带出返还，重复入座不重置资金；热更新接管旧机器人时不得补发账户资金。机器人模拟账户不调用真人资金 RPC。
8. 正在参与的牌局不因随机离桌而弃牌或中断；新入座机器人待正常下一局发牌。结算动画期间不新增入桌，正常离桌等动画结束，低筹码强制站起仍按第 4.4 节执行。机器人座位变更使用既有 JOIN_ROOM/CARRY_SCORE_RESULT/USER_STANDUP_ROOM 和完整排名、旁观推送，不能广播会打断牌局的登录快照。机器人旁观超过默认 180 秒后清理，八小时排名历史保留；调度、冷却、模拟余额保存在常驻房间并于最终销毁时清理。空备用房、比赛桌、到期房及带出重试中的房间不启动概率调度。
9. 后续新增座位类游戏继承 SeatGame 即复用这些规则，只需提供玩法配置、开局 startRound、回合 playTick、动作处理、结算和自己的 robot.js 策略。可选 defaultBuyIn(table) 仅定义正常带入金额，真人建议带入与机器人共用；默认使用房间 carryMin。禁止在游戏中再写 tick 调度、概率循环、12 秒计时、站起退款或冷却状态。结算完成仍须调用公共统计钩子、更新 phase/hand/startAt，由现有 handler 调用公共 afterRound；不另起定时器。新增游戏应验证继承链和客户端协议适配。
10. 公共规则按已有三类基类复用：有座位的普通现金桌统一走 SeatGame；百人类走 HundredGame，单人类走 SlotsGame，各类公共能力在对应公共层实现一次。没有座位/带入概念的玩法不能生搬桌位消息；比赛桌仍由 match 管理。跨类型扩展应增加公共层适配入口，各游戏只提供玩法差异，禁止以开发新游戏为由复制整套生命周期。

### 4.8 房间公用功能：公正码、旁观列表、实时排名

1. 旁观列表和排名的协议适配、累计统计放在 game-server/src/core/room-features.js；公正码的生成、授权、查询和生命周期放在 game-server/src/core/fair-code.js。普通游戏通过 SeatGame 和开局/结算钩子接入，禁止为每个游戏复制一套公共逻辑。
2. 旁观列表从真实座位/旁观状态生成，排除已入座玩家并按 uid 去重；入房、入座、站起、离开时同步，昵称和头像使用现网客户端要求的 userName、userIcon、userInfo。真人默认旁观规则不变。
3. 实时排名直接使用房间从创建到销毁这八小时内的累计数据。房间创建时绑定独立统计对象，按 uid 累计玩家资料、带入、带出、已结算手数、下注总量和净盈亏；查询读取房间内存，不另查 ES 或全平台榜单。玩家站起、离开、重新进入及热更新不得清零，离桌历史保留至房间真正销毁；到期延续的最后一局结算仍计入该房间。不同房间的数据不得混用。带入/带出不得计作游戏输赢，未结算下注在本局结算后记账，同一局不得重复累计，活动积分不得用桌上筹码冒充。
4. 公正码必须在发牌和下注前绑定本局真实牌序，同一局已经公布的码不能被重新生成。进行中只公布密文，已结束后仅公开本人手牌、已公开的对手牌和实际发出的公共牌；未公开的对手牌、烧牌及未发牌不得下发密钥或真实牌值。
5. dev 可使用房间内存保存本地验码记录，当前上限 128 局、结算后 TTL 24 小时，房间回收即清理；此实现只用于开发验码，不代表外部公证或链上证明。prod 必须接入权威 lottery/记录服务，历史数据经 data-center 读取，不得将开发环境生成的证明充当正式公证，更不得从 game-server 直连 ES。
6. 公正码列表/详情校验登录、可信代理、房间及该局参与/旁观权限。hall 的详情查询不得隐式入房、入座、带入或带出；查询连接关闭不能让真实玩家离桌。
7. 公用模块及新增消息号必须进入版本化热更新依赖链。统计和已公布的验码记录放在常驻房间对象，热更新不得重置；进行中的旧局保持原发牌顺序，新局才使用新的发牌布局。服务进程不重启。
8. 消息号、字段、客户端适用范围及当前未接入项详见 doc/协议/游戏/全局公用功能协议.md。新增游戏必须分别核对它的客户端入口和验码布局，不能仅因共用后端模块就宣称所有玩法均已兼容。
9. 排名时间与房间时钟统一：1244 的 gameTime=28800、lastTime 为剩余秒数，2206 的 leftTime 使用同一截止时间；德州 dzpk/dzpkParams、炸金花 ctjh/ctjhParams 的 gameTime 同步下发。当前通用排名按钮直接打开缓存并发送 1130 DATA_REPORT（buttonCode=realtime_rank_main_btn），不能只等待 1144。进房/重连及座位/旁观变化时须先推完整 1244 再推 2219，按钮事件刷新完整排名；不能让原客户端以仅含旁观列表的对象计算剩余时长。不得修改客户端来掩盖缺失字段或错误推送顺序。
10. **机器人行为、房间排行榜、旁观者列表属于全项目公共能力，不是德州或炸金花的专属功能。** 公共行为和状态管理只维护一套，各游戏禁止复制。机器人入离桌规则统一由 core/robot.js 与 SeatGame 调度；排行榜和旁观者列表统一由 core/room-features.js 生成、排序、去重和推送。排行榜不是跨房间共用一份数据：每个房间持有自己的统计和旁观状态，真人、机器人使用同一份房内记录。
11. 新座位类游戏默认继承 SeatGame 的建房初始化、房间快照、进房、入座、带入、站起、离房和重连公共功能，onMessage 先交给 super.onMessage 处理公共请求。引擎只传入本局参与者及真实结算结果，调用 beginHandStats/finishHandStats，再在自己的结算消息之后调用公共 pushRanking；成员/旁观变化由公共 pushObservers 统一推送完整排名及旁观列表。不得在游戏内另建排名缓存、重写排序或拼装旁观数组，消息名称中的 DZPK 前缀不代表仅限德州。
12. 新游戏接入必须验证机器人入离桌与排名/旁观同步、纯旁观者不计入参局排行、离桌历史保留、结算不重复累计、同房热更新不清零及不同房间隔离。牌力/出牌选择、游戏结果映射属于玩法适配；百人类或单人类的成员来源和客户端消息若不同，应在公共层增加适配，不复制公共逻辑，也不得宣称尚未接入的协议已完成兼容。

### 4.9 大厅房间列表公共人数

单个房间的动态展示人数最多为 **100 人**，所有游戏共用此上限；公共配置、启动覆盖配置及随机波动都不得使动态展示值超过 100。

默认人数变化须在大厅约 5 秒一次的轮询中可观察，并保留高准入房间的最小活动区间；不能因百分比变化过小、准入衰减和整数取整而让高准入房间全天固定为最低人数。允许相邻刷新相同，测试须覆盖低谷、高峰及高准入房间的短时变化和日内趋势。

当前大厅普通棋牌列表缺少定时更新，统一通过 hall/src/room-list-refresh.js 在资源响应层启用现有 op=38 轮询，不修改原始 static 文件。保留隐藏暂停、防并发、切页旧响应丢弃和卸载清理；op=35 比赛列表不套用。升级大厅版本必须核对响应适配位置并验证实际列表状态随响应更新，不能仅测接口数值。

1. 所有游戏的房间列表展示人数统一由 hall/src/room-population.js 在 op=38 公共入口生成，通过既有 roomInfoData[].totalPeople 返回非负整数。普通棋牌、百人、slots 及后续游戏复用同一模块，禁止按玩法复制逻辑或修改原始客户端；正式功能保留在 hall/src，不能放入仅本地使用的 cache/。
2. 准入越低，展示人数越多；默认按北京时间 03:00–06:00 最低、06:00–12:00 增加、12:00–14:00 减少、14:00–24:00 增加、00:00–03:00 减少。时段之间连续，在基础趋势上叠加可控随机波动。人数范围、准入衰减、随机幅度和时段倍率在 hall/src/room-population-config.js 集中配置并支持业务热更新。
3. 同一时间桶、同一配置的展示值不得因为请求频率、用户或热更新而任意重抽；跨 hall 实例使用相同配置可复现。不得修改真实成员、排行榜、旁观列表、分房容量、满座扩容和房间生存周期，也不得为显示人数创建/唤醒房间或机器人。比赛报名和存活人数仍来自真实比赛状态。
4. 具体金额字段、计算方式、开关及调参说明见 doc/协议/大厅/房间列表公共人数.md；新增游戏走统一 op=38 即复用，不再独立实现。测试覆盖时间边界、准入排序、随机变化、重复请求、热更新、全游戏入口及真实房间池隔离。

### 4.10 德州普通不秀牌接入约束

1. 普通不秀牌复用 HoldemGame/SeatGame 及已有公共模块，不另写机器人、房间、排行或旁观逻辑；新档位从房间配置区分，不能复制一套引擎。
2. 大厅普通现金桌 playMode=0 与运行桌 2201/2206 的 playMode=1 分阶段映射；forceShowCard 独立保留。房间 key 包含完整配置身份，分房不能将缺失的不秀牌、盲注档或特殊模式回退到普通秀牌桌。
3. 底牌权限同时约束 3174/3282、3172/3277、3441、3432、重连、3446/op=46 和公正码：只公开本人授权牌和实际摊牌；单人获胜不强制亮牌，选择一张不能泄露另一张，嵌套牌型也不得泄露。
4. 全下必须补发公共牌，主池/边池按实际投入及资格派奖，未匹配投入退还，平分余数按庄位顺时针分配；中途弃牌离桌者投入仍计入本局。筹码守恒、底牌隔离、现有秀牌模式和完整入座退出流程都要验证。
5. 开发种子支持热更新，不能重建钱包或常驻桌。正式默认数据继续在 gogames/app/tables/gogame 维护；不秀牌暴击、保险和正式 data-center 回顾未接通时不得宣称已完成。协议及实现状态见 doc/协议/游戏/德州不秀牌普通游戏消息及游戏流程分析文档.md。

### 4.11 炸金花普通场接入约束

1. 普通炸金花使用现有 `games/zjh`，大厅 gameType=21，房间 roomType=25、playMode=3；房间 key 为 `25/{playMode}/{ante}/{roomClassification}/{carryMin}`。不能用德州盲注 key 或忽略底注匹配不同档位。
2. 公共生命周期、入座带入、概率机器人入离桌、排行榜和旁观列表必须继承 SeatGame；玩法目录只维护三张牌评估、下注圈、比牌与策略。新游戏的 2206 若清空客户端手牌状态，必须通过公共快照流程补回按接收者授权的牌局数据。
3. 以 2.0.1279 客户端为准：4 是加注、7 是看牌、10 是跟到底开关；3726 使用 data.score/data.isEnable 并私发；3756 是轮数整数；比牌目标取 targetUid。请求金额为显示单位，扣款/推送为积分单位，不能把无效操作默认为跟注。
4. 牌局参与者与房间当前座位分开，离座不得丢弃已投入与结算记录；三张牌结算、回顾、公正码和重连均遵守可见性。机器人闷牌时不得读取自己的手牌，更不能读取对手底牌。
5. 开发回顾放 cache/zjh，测试放 test；生产回顾继续经 data-center 与 Redis，未接入不得冒充正式历史。普通场不代表看一张、看二张、暴击或保险已实现。字段依据和实现范围见 `doc/协议/游戏/炸金花普通场游戏消息及流程分析文档.md` 第 11 节。

## 5. match 服务

match 专门管理比赛，职责如下。

### 5.1 比赛状态

1. 维护开赛时间、开赛状态、报名人数、存活人数、玩家积分/排名、分桌房间。
2. 后台可操作的状态机：`草稿 → 报名中 → 进行中 → 结束 / 取消`。
3. 进入「进行中」后，开赛时间、报名费、奖励结构锁定；只能改展示文案或强制结束/取消。
4. 状态变化必须 `Publish` 到 Redis 频道 `match`，所有 hall 更新内存列表。

### 5.2 比赛房间

1. 维护比赛分桌与观赛房间列表。玩家通过比赛房间列表进入指定房间观看比赛。
2. 德州比赛对外房间类型为 `roomType=101`，与现金桌 `roomType=19` 分开。
3. 分桌映射以比赛详情中的 `MTTRoomInfos` 为准；房间号会换桌，不能把第一次 `roomId` 当成永久房间。
4. 牌局逻辑在 game-server；match 管赛况、分桌、观赛入口，不管发牌。

### 5.3 报名与门票

1. 应付金额 = 报名费 + 服务费，币种为玩家当前货币。
2. 若本场配置了指定门票张数，先扣对应门票持有记录。
3. 剩余金额可用钱包支付，也可用门票按后台配置的「门票:货币」比例折算抵扣。
4. 扣费成功后才写入参赛玩家，并广播人数变化。
5. 门票分两层：
   - **种类**：名称、面值、是否绑定某场比赛（0 为通用）、发行量
   - **持有**：种类、归属玩家、是否已用、用于哪场比赛
6. 奖励发门票 = 写入持有记录。报名抵扣 = 将持有记录标为已用。
7. 「门票:货币」比例按币种在管理后台调整，match 报名扣费必须读当前比例，不得写死。

### 5.4 奖励

奖励按名次配置，每条可包含钱和/或门票。钱必须带货币类型。

示例结构（存储与管理 API 使用，下发给客户端时再映射为客户端已有字段，如 `MTTRankPrices`）：

```json
[
  {
    "rank": 1,
    "items": [
      {"kind": "money", "currency": "CNY", "amount": "10000"},
      {"kind": "ticket", "ticketId": 3, "amount": "5"}
    ]
  }
]
```

结算：钱走已有资金通道加余额（带币种）；门票写入持有表。

## 6. 管理后台

比赛运营功能做在 gogame（管理 API 挂在 match）。至少包括：

1. **比赛发布**：名称、游戏类型、开赛时间、人数上下限、报名费/服务费/币种、是否允许门票抵扣、指定门票种类和张数、奖励模板、盲注、延迟报名、初始积分。
2. **比赛信息修改**：未开赛可改规则；进行中按第 5.1 条锁定。
3. **比赛状态修改**：按状态机切换，成功后广播 `match` 频道。
4. **门票种类**：增删改、发行量。
5. **门票兑货币比例**：按币种配置。
6. **奖励模板**：名次 → 钱（含币种）和/或门票。

管理端改配置的路径：管理 API → match 落库 → Redis `match` 广播 → hall 更新内存。禁止只改库不广播，导致大厅列表落后。

## 7. 服务划分

```text
gogame/          Node.js；进程常驻，业务模块热更新
  hall          玩家大厅；订阅 match 频道；内存比赛列表；返回 game-server 地址
  game-server   客户端 WebSocket 房间
    core/       GameBase / SeatGame / HundredGame / SlotsGame
    games/      每个游戏一个目录（配置 + 状态机）
  match         赛况、门票、报名扣费、奖励、管理 API、Redis 广播
  admin         比赛 / 门票 / 比例 / 奖励后台页面
  test          自动化测试与浏览器回归脚本，按服务分目录；不进入生产包
  cache    本地 RPC/缓存/钱包/回顾模拟及调试补丁；不进入生产包
  scripts       生产打包与启动工具
  doc           协议与本开发规则
  static        现网客户端与大厅资源（协议事实来源之一）

gogames/app/tables/gogame
  gg_match / gg_match_player / gg_match_room
  gg_ticket / gg_ticket_hold / gg_ticket_currency_rate
  gg_award_template / gg_blinds / gg_room_config
```

鉴权、余额、注单走已存在的 data-center / open-api / 存储，本仓库通过调用接入，不在 hall 里直连改余额。game-server / hall 的资金通过钱包适配器切换：`wallet.mode=local` 只改内存，方便本地开发；`wallet.mode=online` 读写 `user_info.score`（后续接到 data-center）。

## 8. 开发顺序

1. match：表结构、门票与奖励、管理 API、Redis `match` 广播
2. hall：登录与现网 op、订阅 `match`、内存比赛列表、`op=45` 返回 game-server
3. game-server：按客户端 WS 进房，落地三类房间接口，先接通第 4.4 节三款样例

## 9. 禁止事项

1. 在 fg 仓库开发本项目服务。
2. 把 mock-server 当正式服务或协议标准。
3. 为图省事改客户端协议字段名、消息号、op 编号。
4. 比赛列表每次请求都打 MySQL/Redis，而不走 hall 内存。
5. 比赛状态变更不广播，或广播打到错误的 Redis 频道。
6. 奖励只配金额、不带货币类型。
7. 门票抵扣报名费时写死兑换比例。
8. 用普通现金桌 `roomType` 冒充比赛桌。
9. 在 match 里实现具体牌局发牌/下注状态机。

## 10. 文档维护

1. 新增或变更 op、消息号、房间类型、比赛字段，必须同步更新 `doc/协议`。
2. 本规则变更须单独提交，并说明影响的服务。
3. 实现前先核对本规则第 1、3、7、9 节。
