> 后续核验：实际 gogames 的本批 4 文件已全部匹配，0 待应用。下文待应用及审批失败保留为当时记录；源码已应用不代表已核验运行中的 data-center 版本。

本轮按最新清单推进第一项 Redis 保留期限收尾，修复比赛报名、退款及现金奖励凭证已由 MySQL 确认、但 Redis 过期设置丢失后可能长期保留的问题。其他未确认资金责任、未交付刮刮乐票据和票号防重复出售仍需继续处理，本轮不将第一项整体标为完成。

## 行为变化

原付款状态查询只返回 SQL 状态，不处理已提交 SQL 回执对应的 Redis marker。若进程在 SQL 提交后、设置 marker 过期时间前中断，后续只有查询而没有再次调用报名／退款／派奖接口，原 marker 会持续保留。

现在查询先完成原 SQL 事务及身份、计划校验，再对已经确认的原收款／退款／奖励回执进行缓存清理。Redis 必须配置可用才尝试；未配置时 SQL 查询仍正常，Redis 不可用或清理失败只日志，不把已经确认的查询或资金结果改成失败。整次查询清理共用最多一秒预算，没有新增扫描任务或启动对账机制。

新 match 现金 marker 在现有封装中增加内部 createdAt，记录首次原子资金操作时间；公开回执、SQL 业务文档和 RPC 格式保持原样。只有原 SQL 回执提交成功后才允许缩短 marker 生命周期，上限为该原 createdAt 加 3600 秒，迟到确认或查询不会重新给一小时。原 Redis 现金操作已发生、SQL 尚未确认时仍保持防重凭证，不提前删除。

对于缺少原时间的旧 marker，仅在 SQL 回执、请求指纹及原 Redis 回执完全匹配后直接移除，不以当前查询时间赋予新的一小时。新字段为非法、负数、零或未来时间时拒绝清理并记日志；回执不匹配也不删除。不存在的键不重建；Lua 比较原完整值后执行删除或缩短，已有更短期限不延长，并发替换不能覆盖。

退款查询可以同时清理已经确认的原收款与退款 marker，按各自原资金时间处理。正常查询不调用扣款、退款、派奖或门票扣返逻辑；这些操作仍以原 MySQL 业务回执为确认依据。
