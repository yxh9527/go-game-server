# 比赛服务器实现（2026-10-30）

## 当前实现

match 使用 Node.js 管理排期、报名、退款、分桌、积分排名和奖励；game-server 继续复用公共 SeatGame/Holdem 引擎发牌、操作和逐局结算。未修改 static 原版资源，未重启常驻服务。正式上线的未完成依赖见末节，不得将开发模拟当成生产完成。

## 排期和管理接口

比赛仅由管理后台发布，管理入口 /admin/v1。生产必须配置管理凭证，并传 X-Admin-Token；缺令牌时拒绝管理请求。

admin_agents 配置为代理凭证数组，每项包含 agent_id、token，令牌必须非空且唯一。代理令牌自动绑定所属代理，不允许通过查询参数、请求体、嵌套 match.agent_id 或 X-Agent-Id 切换代理。平台级 admin_token 可以代代理发布，但每次必须用 agent_id 或 X-Agent-Id 明确选择代理，不提供跨代理聚合列表。仅未配置管理凭证的 dev 保留本地管理入口，默认代理 1。

比赛与排期的列表、详情、创建、修改、取消和 runtime 查询全部校验代理归属；跨代理资源返回不存在，伪造代理参数返回拒绝。已创建比赛和排期不能修改所属代理。日常场次继承后台排期的 agent_id，玩家大厅与报名继续使用登录数据中的可信代理。共享的门票/汇率/奖励/盲注模板尚无代理归属表结构，代理管理令牌不能访问这些管理接口，仍由平台管理员维护。

| 接口 | 含义 |
| --- | --- |
| GET/POST /schedules | 列出/新建排期模板 |
| PUT /schedules/:id | 修改模板，不追改已生成场次 |
| GET/POST /matches | 列出/新建独立比赛 |
| PUT /matches/:id | 修改比赛，有待支付/已报名者后仅允许展示文案 |
| PUT /matches/:id/state | state=1 开放草稿报名，state=4 赛前取消并退款 |
| GET /matches/:id/runtime | 查看支付、退款、分桌、奖励和失败重试状态 |

daily 排期字段：agent_id、schedule_kind=daily、timezone=Asia/Shanghai、daily_time=20:00、enabled=1、match=比赛配置对象。once 排期字段：schedule_kind=once、start_time=明确的 Unix 毫秒时间。比赛配置需含 init_point、min_player、max_player、register_gold、service_gold、currency、有效的 small_blind/big_blind 或 blinds_id；championship_name 仍为原版多语言 JSON 字符串。这里的 daily/once 不覆盖客户端 championshipType。

daily 唯一键为模板 ID:本地日期，once 为模板 ID:once。每天独立报名、费用和结果，不结转报名费；今日时点已过则预创建下一天场次。停机错过且未创建的日常场次不补扣费，已创建逾期场次仍按人数检查。单次赛不滚动。夏令时重复钟点选第一次，不存在的本地钟点报错。当前技术上限 5000 名真实报名者，max_player=0 也受此限制。

## 报名和资金

原版大厅源码确认：op=42/type=2 是提交报名，op=43 是退赛，op=48 是重入/重购；不是空数组资格查询。42/43 经 hall 转发 match 的 /internal/v1/tournament，由 match 验证 token 和可信代理。48 当前明确返回尚未开放。

支付计划先落账，再按幂等键扣款；报名费/服务费分开记录，重复点击不重复收费。支付成功才计人数。报名后冻结费用、初始积分、奖励与当时的盲注模板。到预定时点才判断：人数达到 min_player 则真实分桌，不足则取消本场，**只退报名费，服务费不退**。退款按原计划/凭证，不按新金额或新门票比例。当前赛前退赛/管理员取消也采用逐项支付记录及不退服务费政策；生产收费退赛开放前应核对运营政策。

扣款明确拒绝不计名额；超时等不确定结果保留 pending，截止后不能补计，按原幂等键查询/退款；失败保留 refund_pending 重试。适配器必须区分从未扣款与已扣款但丢回执，不得将超时视为未支付。

dev 的报名费、退款、现金奖励统一由 game-server 进程的钱包扣付，op=54 读取同一余额。match/hall 内存 RPC 余额不是跨进程共享，不能各改一份。本地模拟只支持 CNY 整数积分，门票和多币种不能假扣成功。

## 比赛桌

match 通过现有 game-server WebSocket 监听器的独立服务间 JSON 调度，不新增客户端协议号。请求带 HMAC-SHA256、时间及 nonce，并校验有效期；start 按代理/比赛/原名单幂等，advance 按 revision 幂等。生产两端必须设置相同私密 match_control_secret，不能用 cache 中的开发密钥。

按公共德州容量平均分配真实玩家，不用现金机器人凑人数。只有 match 可以创建 101 房间，客户端不能凭房号制造筹码。外层进房 roomType=101；2201.conf.roomType=19、isMtt=true、mttId、gameRoomConfigId=0。报名者绑定初始积分/座位，非参赛者旁观。禁止现金带入/带出/站起/下局站起；退出或断线保留比赛积分与座位，沿用行动超时，不退成钱包余额。不套现金桌八小时回收。

各桌真实结算并等待原有动画结束后暂停于局间；match 核对积分守恒、持久化淘汰与排名检查点，再推进。合桌必须等所有桌到检查点，不能搬动进行中玩家；优先保留原桌，只移动溢出及被合并桌玩家。使用原版 20004 {mttId,roomId} 换桌，MTTRoomInfos 同步实际人数。

零积分淘汰，同一检查点按局初积分排序，完全相同按 UID 固定排序以保证开发重放一致。**这一同分裁决尚未取得运营确认，正式涉及同分奖金前必须明确，不能宣称与现网一致。**

盲注从 gg_blinds.data 的 min/max/bet/interval（积分/秒）或比赛显式大小盲读取；无有效配置拒绝分桌。20009 提供当前级别、下一级和剩余秒数，金额下一手生效，不改进行中手牌。休息级别暂不支持，不静默当普通级别。

仅剩一名存活者后结束比赛。按 award_json 生成独立幂等奖励计划，资金确认且凭证核验后才记已付；失败保留 pending。20010 的 award/ticketNum 只在确认发放后下发，不把剩余比赛积分当现金奖金。缺权威接口时显示待发放，不伪造成功。

## 持久化和热更新

manager 库新增 gg_match_schedule、gg_match_occurrence、gg_match_runtime，以及 gg_match.refund_service_fee=0。Go 模型在 gogames 登记 ManagerModels，Node 不临时建表。完整待应用源码位于 doc/待应用/data-center，已包含原比赛持久化表结构补丁，不能再重复应用旧补丁。

生产查询和持久化经 shared/rpc 委托 gogames data-center，Node 不创建 MySQL 连接或执行 SQL。MatchTransaction 双向流由 data-center 持有同一 MySQL 事务与比赛行锁，串行化报名/取消/开赛，将比赛状态、JSON 资金日志和 outbox 原子提交后才返回确认；客户端断开或超时回滚。排期行锁/唯一键同样由 data-center 防止多实例重复建场。推进丢回执后重试已存检查点，不能重复淘汰或分配初始筹码。

Redis 沿用 match 频道及 {event,data:JSON字符串} 信封；match_snapshot 附递增 sequence，hall 丢弃旧快照。启动时经 RPC 从 runtime 还原报名/分桌，旧 gg_match_player/gg_match_room 只兼容未接入场次。约 30 秒补发完整快照修复订阅遗漏，列表只读 hall 内存。dev 不共享跨进程总线，op=35/36 从 match 同步内存快照，不查库。

支付账、退款、房间和检查点属于常驻对象/数据库；业务热更新只换逻辑与唯一调度回调，不重复添加定时器，不重启进程。

### 一小时防重缓存

shared/tournament-idempotency.js 统一缓存成功的变更请求响应：比赛服务间 start/advance/awards/payment，以及开发支付适配器的扣费/退款/奖励回执。防重键包含代理、比赛、操作和完整请求摘要；status 不缓存，以免读到旧桌况。生产尚未接入的权威资金适配器不能因此被宣称已完成资金防重。

每条成功响应从写入时起固定 3600000 毫秒过期，命中不续期；读取时即时检查，唯一常驻定时器每 60 秒清除过期项，空闲项最迟在过期后的一个清理周期内物理移除。热更新复用状态及原到期时间；执行中的操作单独合并，不因等待超过一小时而并发重放；失败不缓存成功结果。缓存失效后重新执行仍须检查权威报名/支付账本、比赛 revision 和场次唯一身份，不能再次扣款、退款、派彩或重复创建日常场次。

报名/退款/奖励流水、退款补偿、比赛和场次唯一映射属于权威业务数据，不随一小时响应缓存删除。开发钱包对应的 resident ledger 模拟权威资金流水，也保留供超时重试查询；不能简单给 ledger 整体加 TTL，否则超过一小时就可能重复收退费。多实例正确性仍依赖既有数据库事务、唯一键及正式支付系统幂等记录，进程内短期响应缓存只用于减少重复处理。
