## 配置归属和玩法

- 两款转轴配置分别在 game-server/src/games/ggl-mjhl/reel-config.js 和 ggl-queen/reel-config.js。Go 后端不保存轴带、不生成图案，管理端不管理轴带。
- Node 根据自己的轴带生成自然、玩家赢、玩家输三组完整候选，每张均为 20 个符号。同一购买请求的三组候选全部预先生成，超时重试复用原请求、编号和图案。
- Go 按原帮助的符号 1 数量和固定倍率重新验算奖额，用现有 GetPoolControlDecision 选定一整组，购票时锁定结果及赔付责任。开奖时不得重新抽奖、改变票面额或改用当前转轴。
- 面额仍为 100、200、500、1000、2000、3000、5000、10000 最小货币单位。20 档倍率为 0.5 至 10000；这些是兑付规则，不是转轴配置。
- 初始轴带为可审阅模板，未声称复原原站概率。实际出奖受水池控制，不承诺模板的理论返奖等于线上返奖率。

## RPC 和客户端

保留旧 Lottery RPC，新增 ScratchAction，operation 为 state、search、allocate、issue、reveal；原 history operation 已于 2026-11-12 删除，历史改走 data-center 的 ES 查询。请求和响应载荷为有界 JSON，后端严格检查字段、玩法映射、币种、原归属和候选结构。Node 仅通过统一 common 门面调用资金接口。

可信账户来自已鉴权会话。财务 gameId 来自 gp_game 的 clientGameType + roomType → number 映射；roomType 61/63 必须与资金后端运行配置一致。房间 finance_level 必须显式配置，不能从客户端获取或猜默认等级。

原客户端 3701—3704、6121 及百人多房间立即刮奖消息继续使用原编解码。正式票务直接交给权威资金端，不再包进本地 staged cashApply，避免对同一购票重复扣款。其他游戏保留原资金边界。

已售未刮票只向客户端返回 serialFull、faceValue、gglKind；未兑奖图案、奖额、决策摘要不返回。Node 同时拒绝带有这些私有字段的异常票据响应。

## 资金和票据归属

1. 选号只产生 60 秒有效候选，单账户候选最多 100 项；每本 20 张，单次及未刮票最多 100 张。循环和抽样均有边界，不使用一直重抽直至中奖的循环。
2. 新购买先确认 MySQL 票据表已由部署建立，玩家请求内不执行 DDL。随后同一 Redis Lua 调用既有 cashwallet 校验并扣除整批款项，同时写既有 finance round、每张赔付预留、未刮票归属、售出票号和原购买回执。
3. 任意一张已售出、账户身份/修订号错误、可用余额不足、筹码已被棋牌桌保留或预留池不足，整批在首次写入前失败。整本不会只扣部分票款。
4. 购买回执复用既有 wallet marker 命名空间。相同请求读取原结果；改变原候选、金额或编号拒绝。已售票不因普通预赔到期而失去归属或释放责任。
5. 已售票禁止通过普通 Bet、PrePay、RenewReservation、CancelBet 修改。兑奖仅允许票据锁定的 settlementId、归属、图案摘要和金额；人工整票退款使用固定 VOID_REFUND 编号关闭票据。
6. 兑奖通过既有 Settlement 和 wallet marker 加余额，再保存已兑奖归属和历史。重复兑奖不重复派奖、累计奖额、历史或释放预留。前台传入其他面额不影响原票面额。
7. MySQL 写入失败时返回可恢复错误，已经扣款的票仍在未刮归属中；用原购买回执或原票号继续确认，不生成新编号重复扣款或重抽。整本的水池统计先全部处理，再写逐张 SQL，避免某张镜像失败中断剩余票的统计。

资金与归属/预留的原子边界是现有 Redis Lua，不把 Redis、MySQL 镜像和 ES 统计说成一个事务。沿用既有资金服务统计刷新机制及单一代理写入归属；跨存储崩溃一致性和多写实例故障转移仍须单独验收，不能由本批测试推断已解决。
