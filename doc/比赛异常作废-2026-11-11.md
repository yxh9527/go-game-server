# 比赛异常作废

用户于 2026-11-11 明确：比赛崩溃后不恢复牌桌，记录当前比赛异常并作废；报名费、服务费全额原路退回，沿用取消规则。本批按该要求实现，撤掉了刚开始的恢复接口草稿，没有新增牌局持久恢复、启动重放或资金对账机制。

## 异常判定

适用于进行中 state=2 的比赛，不将已经结束的比赛重新作废或退费。

- 游戏服签名响应明确返回 MATCH_STATE_LOST：牌桌状态已不存在，立即记录 GAME_STATE_LOST 并作废。
- 游戏服返回的进程标识与该场比赛记录不一致：记录 GAME_SERVER_PROCESS_CHANGED 并作废。标识保存在常驻 runtime.tournamentRooms，业务热更新不更换标识。
- 游戏服请求 503/504 持续失败：先保留故障观察记录，默认持续 60000 毫秒、且至少连续失败 3 次才记 GAME_SERVER_UNREACHABLE 并作废。期间有成功响应则清除该次连续失败记录。match 配置 tournament_failure_timeout_ms 可设为 1000 至 3600000 毫秒。

故障计数和首次失败时间通过现有比赛事务保存，不因 match 业务热更新重新计时。非游戏服请求的数据库异常、普通 409 检查点冲突等不会触发此网络故障规则。

## 持久记录与后续处理

在现有 gg_match 行锁及 gg_match_runtime 的同一事务中：

1. 设置比赛 state=4、结束时间、cancelReason=game_server_failure。
2. 保存 invalidated.reason、at、message、原游戏服进程标识、原分桌列表及原检查点；每位玩家保留 invalidRank，正式排名清零。异常标记独立保存，不冒充正常完赛。
3. 清空活动分桌与升盲投影，停止比赛推进和未支付奖励；旧的异步推进响应在写入前重新核对比赛状态，不能将已作废比赛改回完成。
4. 将已报名、在赛、已淘汰等实际参赛玩家以及尚待确认的支付项转入原退款流程。报名费和服务费合计全退；原门票按既有权威退款凭证恢复，不能把比赛积分或门票擅自兑换成现金。

退款始终复用原计划及支付编号。未扣款的项目由权威接口确认 uncharged；退款失败保持 refund_pending，后续 tick 重试，重复处理或热更新不能重复入账。

match 发签名 invalidate 请求，游戏服丢弃该场比赛剩余虚拟牌局及房间引用，推原 ROOM_DISSMISS。此时不按牌面派奖，也不把比赛积分带出为现金。游戏服仍不可达时保留桌清理待处理，钱包退款继续推进；游戏服恢复连接后重复清理安全。已经确认最终奖励的比赛拒绝按“在局异常”清理。

原管理运行状态接口可以查看完整异常和退款记录；match_snapshot 与大厅详情附带 invalidated、invalidReason、invalidAt，原客户端仍使用既有取消状态。没有修改原版静态客户端增加新状态枚举或异常样式。
