# 记录存储故障背压与队列保护

上一批“旧接口原始注单与流水持久保存”4 个文件已经应用，实际目录摘要核对为 0 待应用。本轮补 SQL 长时间故障下的准入和原记录转交边界，不修改游戏赔率、投注口径或已完成资金操作的成功回执。

## 完成内容

### 新投注进入资金处理前检查

统一 Bet 发现新 betId 时，在任何新资金动作之前检查原记录数据库可用性。已知 betId 的原请求重试不因此走新投注路径；Settlement、CancelBet、预留续期等原有责任处理不新增该准入限制。

旧路径在正金额扣注前增加检查：SlotsBet、deductBet、doSingleBet、doMultiBet，以及 Ug5Guess 的本次正金额投入。UG5 原幂等响应读取在该检查之前，已完成请求仍可返回原回执；尚未执行的新请求被阻止时释放其既有请求占位，不留假执行成功。

预检最多 1 秒，健康或失败结果短期复用 1 秒，检查 SQL 连接与原 fg_game_storage 表的只读访问。PING 不等同于写权限验证；此处不是跨 SQL／Redis 原子事务，探测成功后发生故障仍走保留原输出的路径。

### SQL 失败后的原记录保留

- 保存失败的合法原流水不再必须阻塞发送到已满 BillChan，先复制到进程常驻的原输出保留集合。
- 同样保留旧注单的各个原 RowVersion；不再用同一注单最新版本覆盖此前尚未存入 SQL 的版本。
- 保留身份为原种类／文档 ID／版本，原内容重试不会重复增加项；同版本不同内容报错，原内容不被覆盖。
- 只要原输出保留集合非空，新投注预检即拒绝继续接纳，避免 SQL 故障时持续新下单增加未保存记录；已接受的在局责任仍允许继续产生其应有输出。
- 原报告循环每轮先尝试把最多 40 份保留原文提交 SQL，SQL 未确认前不移除。成功后才由此前的固定 ID／版本 ES 投影继续处理。
- 在缓冲集合选取下一批时最多取 40 个键，不对整个积压集合排序或复制，不为每条失败记录新增重试协程。
- 保留集合不返回 durable，不是跨进程持久层。进程在 SQL 尚未提交时退出仍可能丢失这些内容；没有以“内存已保留”冒充已落库。

该集合不新增资金流水或未结算记录，保存的是此前 SaveRecord／SaveBill 已构造的原输出。它不补造牌局、不重新执行下注／退款／派奖，不执行启动资金对账。

### 原缓存向队列转交

旧记录缓存每轮最多尝试 128 条转交，用非阻塞 channel send。队列满时立即返回，原缓存项保持原指针与内容；只有已成功转交并符合原超时／Complete 规则的项才从缓存移除。不通过额外 goroutine 隐藏阻塞或无限堆积待发送任务。

异常或无效身份文档仍可能进入原缓存／队列作为最后的保留边界，并有明确错误日志；本轮不丢弃它们或伪造新的身份。不能据此声称任何畸形数据下整个服务都永不阻塞。

9 个 Go 文件：

- lottery/dao/final_record_store.go：SQL 错误失效健康缓存，原投影循环先写回保留原文。

- lottery/rpc/service.go：旧保存路径使用保留集合、调用原缓存非阻塞转交、投注前准入。

- lottery/unified/service.go：新 betId 准入、统一 SaveBill 失败保留。
- 新增 lottery/unified/record_storage_admission_test.go：数据库不可用时不创建新局、不触发钱款。
