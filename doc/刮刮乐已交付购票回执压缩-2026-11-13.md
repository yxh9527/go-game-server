# 刮刮乐已交付购票回执压缩

本轮开始时，上一批比赛 SQL 已确认资金凭证 3 文件仍未应用。本轮新增刮刮乐 4 文件，与其合并为 7 文件包，保留已有修改。

## 问题

原购票回执 lottery:settle_wallet:scratch-buy:* 包含原指纹、公开返回结果及整批完整 financeRound 快照。100 张批次会重复保留大量已经另行保存的票据与金融内容。

旧 finishScratchIssue 在金融快照不存在时，还会从购票回执恢复初始 RESERVED 副本；对已经完成、按一小时规则清掉的牌局，迟到购票重试可能使本地重新出现旧状态。

## 处理

- 批次全部票据逐一通过原 mirrorScratch 持久保存确认后，以原 Redis key 存放原 fingerprint、原 result 及 deliveryConfirmed=true，移除重复 rounds 数组。
- 不改变原购票结果、余额口径、票据编号、开奖候选、资金金额、历史 ES 索引或 log。
- 精简通过 Lua 比较原完整字符串后更新，保留当时剩余 PTTL；重复确认不会刷新期限。原 key 已过期不重建，并发替换时不覆盖。
- deliveryConfirmed 回执重试只返回原公开结果，校验原请求指纹，不再次读取或恢复金融快照，不重新扣款、预留、派彩或写票据镜像。
- SQL 全部或中途失败时，不精简原恢复批次；原金融快照仍在时继续原镜像重试。原金融快照已不存在时明确失败，不能单凭旧购票回执重建金融责任。
- 精简失败发生在原购票及整批交付成功之后，仅记录错误，不能把这一步内存优化失败变成付款失败。原回执和资金处理保持原状态。

本轮仅减少重复内容，购票回执原 TTL 仍为 7 天，未擅自改成一小时。尚无可独立查询原购票请求的永久权威回执时，直接缩短可能导致原请求在窗口外再次进入购票；已付款待刮票据和原归属也没有删除。

此优化针对新完成交付的批次，旧完整回执在后续合法原重试且全部镜像确认时可精简；不后台扫描全部旧回执，也不宣称立即释放所有旧占用。
