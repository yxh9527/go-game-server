# 刮刮乐最终战绩与常驻时钟保护

上一批“智能投注执行登记与故障收尾”6 个文件已应用，实际后端摘要检查为 0 待应用。本轮继续处理独立票务的显示记录窗口，并修复常驻时钟异步异常。

## 独立票务最终战绩

此前 Go 已持久保存售出票据与兑奖资金结果，但用户中心显示记录仍依赖 Node 收到兑奖响应后再次发送；游戏服在两者之间退出可能没有这份显示战绩。

本轮基于原票据和已经完成的原 Settlement 生成用户中心记录：

- 只接受原金融局 state=SETTLED、status=COMPLETED、NORMAL 兑奖及原 ClaimID；未完成、作废退款或身份不一致的来源不生成完成战绩。
- 保留售票时锁定的票号、面额、中奖图案、命中数、倍率、奖金、购买房间及实际结算时间；不重新读取当前转轴规则，不重新开奖、兑奖或派奖。
- 最终 ID 与原 Node 记录规则一致：代理:游戏:原票号:玩家；麻将胡了和赏金女王分别使用 ggl-mjhl、ggl-queen。原购买房间和结果时间不会因换房或重新查询移动。
- 原票据和金融报告仍在已有结算快照中；投影仅在拷贝上附加完成显示记录，不替换原 immutable ticket.Record，原 scratchSettlementMatches 校验不受影响。
- 复用已完成的金融报告投影和固定 ES ID，写入金融注单与用户中心索引，不需要 Node 收到兑奖回包后重新生成相同战绩。
- 兑奖响应仅在确认原快照具备足够数据时返回 finalReportStored=true。Node 仅对明确的权威适配器和该确认值跳过原战绩发送；旧适配器没有此字段时仍保留原兼容发送。
- finalReportStored 表示已有可持久恢复的原最终来源，不表示 ES 当时已可查询。原异步投影重试仍可能带来短暂查询延迟。
- 新增服务对象测试仅恢复原票据／结算快照，不调用 claim，确认可以索引实际战绩；已完成兑奖的原余额和票据不因索引再变化。

不新增表、协议字段或资金流水机制。售票概率配置仍在 game-server，Go 此处只投影已经确定的实际结果。

Go 本批 4 文件：lottery/unified/scratch.go、settlement_reports.go、新增 scratch_display_report.go、scratch_display_report_test.go。

Node 修改：game-server/src/games/ggl-core/engine.js，及 user-center 的权威／旧适配器兼容测试。

## 常驻时钟异步保护

game-server/src/boot.js 原定时器只 try/catch 同步 handler.tick()，异步拒绝没有被观察。本轮引入 shared/resident-tick.js：

- 同一 resident timer 已有工作未结束时，返回原任务而不是叠加队列。
- 捕获同步异常和异步 Promise 拒绝；记录错误后释放 busy 状态，下一次正常 tick 可以继续。
- 热更新后下一次 tick 读取当前 handler，不强行终止进行中的旧 tick；单个失败日志函数也不会生成另一个未处理拒绝。
- shutdown 清理该 timer。

这属于监听／启动层改动，需后续正常部署才会作用到现有常驻进程。本轮未重启服务，也不宣称热更新已替换旧 timer。完整 Node ESM 历史版本隔离回收仍未实现，当前运行时未启用 vm.SourceTextModule；未通过新旗标重启在线服务绕过这一边界。

## 剩余边界

旧资金接口和部分非结算流水仍有原内存输出路径；比赛回放尚未送达 data-center 时仍有进程退出窗口。售票发行／兑奖 Redis 和 SQL 镜像的故障可靠性继续需要真实环境验收。本轮未把局部记录持久化当作全项目永久零丢失。
