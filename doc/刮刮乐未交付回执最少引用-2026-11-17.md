## 问题与处理

原彩票购票回执在 SQL 交付确认前，以 rounds 数组重复保存整批完整 financeRound。原金融快照已在 lottery_finance_rounds，交付重试只从回执取得原局号，再读权威原快照；回执副本不能恢复已清除的金融状态。

新原子购票在原 key 内只存 fingerprint、原公开 result、原 createdAt 和最少 rounds 身份引用，新增 referencesOnly=true。每个引用仍为 JSON 字符串，保留 roundId、agent、gameId 和 scratch 中的 serialFull／userId／currency，不包含牌面、中奖额、投注、钱包或资金恢复快照。原 rounds []string 和非空 scratch 对象的形状保留，兼容当前旧交付读取方式；不是为所有历史二进制提供兼容承诺。

旧完整回执在原请求合法重试时，也可在 SQL 确认之前精简。Lua 先比较原字符串，匹配才替换，并保留原 PTTL；过期键不重建，并发修改不覆盖。不设置 deliveryConfirmed，不删除 pending／售出票号／权威资金快照，不改已有金额、结果或原期限。

精简前检查代理、游戏、玩家、币种、票号和局号，禁止重复引用。已精简回执同样做身份校验；实际交付还要确认引用与原资金快照的身份和票号完全匹配。原快照不存在时明确失败，不能凭引用或旧副本重新判奖、重建金融状态或再次扣款。

整批票据全部保存确认后，继续走既有已交付回执压缩和原购买时间一小时清理。这次只去掉未交付回执的重复原文，不将尚未完成的玩家权益直接设为一小时删除，也不新增 SQL 投递表、注单备份、ES 重投或恢复机制。
