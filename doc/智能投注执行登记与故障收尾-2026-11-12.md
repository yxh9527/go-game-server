# 智能投注执行登记与故障收尾

继续处理原实例退出时的任务责任。上一批“最终记录随结算快照持久化”8 个 Go 文件已由用户应用，摘要核对为 0 待应用。本轮在这些原金融快照之上确认任务结果，不重新创建游戏或重复提交资金操作。

## 本轮行为

1. 新固定任务标记 executionProtocol=2。每次实际下注前，先通过 data-center 在原 gg_smart_task 行锁内保存 activeAttempt，包含原资金牌局 roundId、代理、财务 gameId、等级、局号及唯一 attemptId。
2. 只有登记回执匹配、版本及原任务配置一致，原游戏服才发起实际投注。登记失败或回执丢失都不当成新任务重新下单；已保存但尚未确认是否扣款的执行身份保留。
3. 原 task 状态、停止请求、任务次数、实例及版本再次校验；远端已停止／已收尾的任务、过期版本或另一执行实例不能登记下一笔。先保存停止／收尾的请求与后来的开始请求通过同一行锁互斥。
4. 当前实际结算的用户中心报告携带 smartTask={taskId,attemptId,inning}，随原 SettlementItem.record 保存进上一批的金融结算快照；它只是任务关联，不是另一份资金流水。
5. 原任务正常确认结算时清除 activeAttempt，原局号和统计按原规则保存；明确下注拒绝时停止任务。钱包提交不确定、进程退出或缺回执时不能清空可能已接受的责任。
6. 固定任务页新增“确认结果并结束”。任一已鉴权节点都可以请求，但 data-center 必须先按代理／玩家／房型锁定原任务，读取原 Redis 金融热快照或冷归档。
7. 仅 state=SETTLED、settlement.status=COMPLETED，且原代理、gameId、等级、roundId、taskId、attemptId、房号、局号、玩家、币种、下注金额、净盈亏及账户结果一致时，才补入这次任务统计、变为 stopped 并释放原 active_key。整个过程只更新任务，不调用扣款、退款或派奖。
8. 重复确认已收尾任务不会重复累计次数或盈亏。旧执行实例读到已收尾的更高版本后同步停止，不再保留本地运行标识阻挡原任务的安全清理，也不能以旧快照恢复任务。
9. 新任务从未登记过执行且没有 pendingInning 时，可以直接确认结束：同一行锁保证后到的执行登记失败。这不适用于只有旧 pendingInning、没有可信执行身份的历史任务。

不新增数据库表、字段、幂等资金流水、未结算表或进程启动对账机制。不自动恢复可能产生重复下注的任务，不迁移未确认资金责任。

## 仍保留的边界

- 原金融牌局未完成、快照缺失、数据不匹配或存储不可用时，拒绝确认结束，保留责任；不会因超时、断线或当前余额相同就判定已经结算／未扣款。
- 执行登记已保存但回执丢失、尚无最终结果时，宁可保留待确认，也不自动重新下注。需要后续按原金融事实处理，不把“不存在已完成结果”当成没有下注。
- 旧 executionProtocol 缺失的历史任务没有完整本次执行身份，仍需原实例确认或人工按原资金记录处理。
- 本次只接受已正常 SETTLED 的明确结果，尚未将取消／退款的所有终态扩展为任务确认依据；没有原最终报告的旧金融快照也不会补造任务盈亏。
- 原游戏服崩溃时仍在进行的牌局不会因本功能自动开奖／退款。比赛崩溃作废全退的约定不受影响。
- 功能依赖金融 Redis 的持久性、原资金写入归属和配套服务发布；自动化测试不是实际多机故障验收。
