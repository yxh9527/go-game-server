## 已确认并修复的公共问题

1. 二进制消息未限制同步解压输出。小型压缩包能触发大分配和主循环阻塞。codec 现在限制消息体与解压后 JSON 为 1 MiB，并拒绝长度不一致和损坏压缩包。测试包含实际 deflate 膨胀包。
2. 每条权威钱包消息都会读取所有在线账户、捕获整个房间对象图，普通心跳也进入该路径，在线人数增长会放大 RPC 和主循环工作。空心跳现在只执行既有鉴权与心跳响应，不进入资金事务；下注等业务不绕过钱包。
3. 慢 RPC 期间单连接可以无限追加请求，重复登录也能排入权威钱包全局队列。处理器现在限制每连接 64 条未完成消息，超限关闭连接，完成后释放计数。超大消息在资金处理前拒绝。WebSocket 传输层同样配置帧大小上限；常驻 listener 不重启，因此启动层的新限制需在后续正常部署生效，热更新的业务解码与排队限制已可生效。

## 其余已修复项

4. 慢资金 tick 未结束时定时器继续追加所有房间的 tick，且内部每个房间又触发一次全量会话续约。现在合并未完成的 tick 批次，续约仅外层执行且不重入；测试连续调用 100 次仍只排入一批，业务热更新也不丢批次引用。
5. 伪造房号能利用 findConfig 的按类型兜底创建未配置房间，并把分房进度跳到 9999。现在校验新房的配置 ID、类型、启用状态和初始索引，只允许分房池已创建的扩展房间；同一个 mahjong 实现的不同房间类型也不能交叉进入。
6. 十三水八鬼极端手牌：相同牌值但不同物理鬼牌副本重复计算。增加仅限本次推荐的等价牌序缓存，仍按物理副本验证十三张牌，不更改推荐排序、牌型或输赢。本机隔离实测约 1954.84 ms 降到 309.84 ms；三条推荐与修复前逐项一致，未修改实牌。牛牛五癞子评估本机约 21 ms，枚举有固定牌数上界。耗时是本机样本，不是生产延迟承诺。
7. 权威钱包只刷新在线会话与座位，已离线下注玩家和庄家退款可能沿用旧账户版本，导致延迟派彩持续冲突。现在同时刷新接受下注的 playerSessions、在局/已离桌保留成员和庄家退款账户；机器人模拟账户不混入真人钱包。
8. 过期带入释放路径没有删除全局成员 Set 中的强引用；现在清除失效绑定引用，不生成新的扣分/加分。
9. 百人逐局派彩仅使用长期字符串 key，开发/本地钱包的全局收据 Map 会逐局增长。现在把既有 hand 作为 operation，使回执随既有牌局对象释放，保留同局重复付款保护；不增加流水表、未结算记录或重启对账机制。生产权威钱包并不使用该本地收据 Map，不能把这个修复描述成已改变生产持久化。
10. 本地登录顺序 Map 永久保留退出用户。现在最后连接退出且该用户没有待认证任务后释放；慢认证仍被较新的登录顺序拦截，不能因清理内存而恢复旧登录。热更新前已保留的历史键没有冒险批量丢弃，避免破坏仍在途的旧认证。
11. 大厅 WebSocket 代理等待上游连接时，pending 数组没有数量、字节或握手期限。新增每连接 64 条/1 MiB 积压上限、10 秒握手期限，连接结束清空队列，保留合法关闭码与原因；正常双向转发、超大首包及未完成握手下的积压攻击已通过独立端口集成测试。当前常驻代理监听器没有重启，启动层配置与新代理监听器需后续正常部署，不能声称已替换现有连接监听器。

## 资金异常增加：已复现并加失败关闭保护

隔离故障注入模拟“上游已经入账、回包超时”：200 分派彩本应使余额从 1000 到 1200，旧代码回滚本地 paid 状态后，下一次业务结算使用新请求再次加分，余额变成 1400。并非线上事故证据，但证明该执行路径有重复加分风险。

现改为：提交结果无法确认时，记录受影响账户的暂停标志，阻止后续资金写入并暂停有其未结算责任的房间；不主动重发资金请求，不新增幂等流水、未结算记录或自动对账。其他账户仍可正常资金操作；仅旁观别人的房间不会暂停那个房间。明确的版本冲突/业务拒绝不被当作不明提交，修正后仍可重试。

同时核验提交回包：账户归属、数量、余额、版本及带入状态必须与本次计算相符；回包缺失或不一致不能先发送成功或发布错误余额，而是按结果不明处理。

修复后同一故障注入实际余额停在 1200，仅发送一次资金请求，下一次资金动作返回 CASH_CONFIRMATION_REQUIRED。暂停标志随常驻钱包对象跨业务热更新保留，但没有新增持久化恢复机制；发生后必须人工核验权威账务与对应业务结果，不能靠热更、重启、重新读一个余额或新发一笔请求解除风险。本轮没有调用线上资金服务，也没有声称完成自动补偿。

证据：cache/game-audit-cash-timeout-before.json、cache/game-audit-cash-timeout.json；test/performance/game-audit-cash-timeout.mjs。生产资金实现另外只读核对了 gogames/data-center/dao/gogame_cash.go 与 app/cashwallet/scripts.go，没有修改外部项目。原接口的 ID 和版本校验不能证明一个新 ID 的业务重试不会重复入账。

## 未解决的真实风险与验证边界

### 热更新代与长驻账户缓存

多版本 ESM 动态导入本身持续保留已加载模块。隔离进程强制 GC 后，1 代游戏模块堆约 7.85 MB，8 代约 23.08 MB，证明热加载增加不是都能被普通 GC 回收。现有账户缓存、开发模拟账本、登录尝试序列也有按累计用户增长的保留；不能随意清掉资金相关状态来降低堆，需结合活跃/未结算引用设计回收。

本轮未擅自重构常驻业务为 Worker/子进程，也没有通过重启掩盖问题。没有完成数天持续运行和真实并发压测，因此不能声称无任何内存泄漏、卡顿或进程卡死可能。

### 百人单批 64 账户上限

本地 gogames/data-center/dao/gogame_cash.go 的 CashApply 限制单次最多 64 个账户、1024 条步骤。游戏侧百人结算可以一次产生 65 个非零派彩账户；隔离契约测试实际得到“invalid cash transaction size or id”，结算状态仍未完成。该情况不会静默记成成功，也不是 CPU 无限循环，但房间可能一直卡在结算。

**此项尚未修复，属于正式上线前的高优先级阻塞项。** 需要确认扩大权威原子资金接口容量，或另行设计不破坏原子性的分批结算方案；本轮未擅自拆分资金批次、改 Go 接口或新增资金流水。证据 cache/game-audit-cash-capacity.json，复现 test/performance/game-audit-cash-capacity.mjs。

### 正常退出与辅助连接

原版多场景退出重入回归还观察到主连接退出导致辅助连接收到 1203，可能出现误导性的异地登录提示。尝试简单改成无通知关闭会触发原版自动重连，故已撤回该尝试，保持原行为并将问题明确列出，不能把取消提示等同于修复生命周期。需要共同处理主连接退房、辅助连接退场和原版重连策略。单场景实际入房/公正码查询的冒烟测试通过，不代表该多场景退出问题已解决。

### 生产联调

这是一轮源码复核、自动化测试、隔离故障注入和本机性能样本；没有测试生产 Redis/ES/MySQL、权威彩票/赔率接口、真实多人压力或真实支付。传输层新增配置需下次正常部署；业务限制与安全暂停使用既有热更新。没有重启常驻服务、没有提交代码，原静态客户端未修改。
