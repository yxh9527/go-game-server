# 游戏主体类与共享父类可回收加载

> 后续已接入 17 个引擎，当前默认范围为 71 个模块，Node 1333 项通过；下文保留本批类／父类的历史实现与实测。最新范围及常驻配置单例修复见《游戏引擎可回收加载与常驻配置一致性-2026-11-16.md》。

本轮将游戏类本身及共享父类加入可回收加载，默认范围从 30 个模块扩大到 54 个。引擎、钱包、资金提供方及其余未选业务依赖继续原加载路径，完整业务图回收及长期验收仍未完成。

## 新增范围与状态归属

shared/hot-entry-factory.js 增加两组显式白名单：

| 分组 | 模块 |
| --- | --- |
| 17 个具体游戏类 | 德州、炸金花、牛牛、十三水、二十一点、三公、麻将、百家乐、龙虎、两种刮刮乐、五种百人棋牌的具体类，以及五个街机玩法共用的 TurntableGame |
| 7 个共享父类 | GameBase、SeatGame、HundredGame、CardShoeGame、BairenGame、SlotsGame、GglGame |

核对了这些文件的顶层声明、构造器及引用方向：配置与引擎引用保留在类／实例中，房间、座位、手牌、筹码和生命周期仍由既有 table／registry／runtime 持有。父类与子类走同一加载路径，避免只回收子类却留下不一致的父类身份。

引擎、钱包、资金操作及 RPC 模块未加入本批白名单。特别是资金函数仍从原模块取得，未增加账本、缓存归档、金融重试或状态迁移机制。测试中的原方法继承、房间退出保护和资金相关回归保持通过。

## 静态配置实例修复

在扩大范围前复现了一个依赖重复实例问题：可回收模块的静态导入先写 link 参数、再由内容解析器写 v，而直接原生导入通常按 v／link 顺序生成地址。同一原生配置因此可能出现两份命名空间。

现在先完成内容版本解析，再继承 link，与原生解析顺序一致。新增回归核对可回收调用方和直接原生导入取得的是同一配置命名空间及同一个配置对象；修改前的失败记录为 cache/hot-native-config-before.log。此前已选模块的地址归一化与缓存规则继续保留。

## 类及实例回收验证

新增 test/shared/hot-game-classes.test.js，复制 24 个真实类文件，保留类间引用关系，并重定位原依赖。每轮实际改变这些副本的版本字段，连续 24 轮，共加载 576 个真实模块版本。

每次验证默认实例／构造器身份及实际版本。主动保留首轮实例，释放中间版本后，以弱引用检查旧命名空间、类、默认实例及类自有方法／访问器均可回收；首轮保留实例仍能读取原身份与房间类型。最后活跃副本 24 个、弱缓存上限 256，pendingEntries／dependencyWaits 为 0。

test/game-server/hot-catalog.test.js 进一步核对全部 21 个游戏：使用既有开发房间配置夹具创建房间，比较新加载路径与原类的游戏标识、房间类型、配置引用及客户端配置输出。这是隔离测试数据，未写入运行服务、MySQL 或 ES。

原 GameBase 继承、刮刮乐基类与炸金花机器人相关 **39 项回归通过**，日志 cache/hot-class-inheritance-before.log。该日志是在接入后的兼容性检查，文件名中的 before 不代表本轮实现前的基线。

生产副本烟测确认 54 个已选模块实际各编译一次，继续验证删除 test/cache 的产物仍能加载和处理 HTTP 请求。

## 连续实际类更新与驻留房间验证

test/performance/hot-source-change-load.mjs 新增 --entry=class，复制真实德州类、入口、目录及完整处理器；逐次改变德州类副本，并用仅在测试副本中附加的方法核对新类行为已生效。真实项目业务源码不改。

每轮要求德州实例与构造器切换到新版本，保留的旧实例仍返回原版本；其他 20 个游戏实例复用。原德州房间、座位、手牌、筹码、总下注、底池、局号以及创建／到期时间均必须保留。钱包入口一旦被调用就失败，本测试不执行真实资金划转。

```powershell
node --expose-gc test/performance/hot-source-change-load.mjs --loader=collectible --entry=class --revisions=600 --clients=128 --sample-every=50 --output=cache/hot-concrete-class-600.json
```

| 项目 | 结果 |
| --- | --- |
| 成功类源码变化／新类生效 | 600／600 |
| 故意错误并保留原处理器 | 24 |
| 持续连接／成功心跳 | 128／80000 |
| 驻留房间核心状态保留 | 600 次通过 |
| 每次复用的其他游戏实例 | 20 |
| 最终残余会话／房间／捕获异常 | 0／0／0 |
| 采样时 pendingEntries／dependencyWaits | 均为 0／0 |
| 隔离场景活跃模块／弱缓存上限 | 48／256 |
| 堆增长 | 24331752 字节，23.20 MiB |
| 后 300 次堆增长 | 约 0.08 MiB |

| 事件循环 P99／最大延迟 | 172.88／201.20 ms |

原始结果 cache/hot-concrete-class-600.json，日志 cache/hot-concrete-class-600.log。此场景只加载游戏服务及临时副本，故活跃数为 48；生产副本还加载 hall／match，默认总范围为 54。

这次更新的是具体游戏类，连带入口／目录／处理器共四层模块；此前只更新目录的场景较轻，不能直接据两次耗时推断性能改善或退化。堆仍有增长和 GC 波动，重载仍有解析、源码复核及编译成本。保留手牌夹具不等于验证任意规则改动均可跨局兼容，也不能替代所有游戏的真钱流程、多实例故障、多日及八小时生命周期验收。
