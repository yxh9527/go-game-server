# 比赛回放确认后推进

本轮开始时核验实际 gogames：上一轮移除 Luck5 的 9 文件包全部匹配，0 个待应用。本轮只修改 Node 业务和测试，不新增 Go 补丁。

## 修复的问题

比赛手牌结束时，用户中心原记录先进入内存发送队列；比赛状态原先只检查手牌结束和动画时间，没有等待 data-center 的持久接收回执。因此 match 可能在回放未持久接收时完成淘汰排名、推进下一手，最终结束、发奖和清桌；此时进程退出仍可能丢掉尚未送达的最终回放。

## 本轮行为

- 生产比赛每手生成本人授权的原回放后，在常驻桌上登记这些已完成记录的确认状态。所有真人参与者的记录必须完整、身份不重复，空投影或投影异常都不会视为成功。
- 在钱包任务尚未投递原记录之前就标记等待，避免“还没入发送队列”被误判成“已持久确认”。
- 沿用原发送队列和重试，不另建发送循环。只有原 `writeUserCenter` 返回 `durable: true` 且 `stored` 等于整批记录数时，原队列才移除确认项。
- 只要本场任一桌仍有未确认的已结束回放，控制面 `status` 返回 `reportingPending: true`、`ready: false`，拒绝推进该检查点。match 原有轮询因此不会按该手结果继续淘汰、合桌、结束和发奖。
- 正常结束清桌也检查这些确认项，防止热更新前已经结束／通知奖励的常驻桌在回放仍未确认时被回收。确认后沿用原有清理期限和流程。
- 原比赛异常作废流程仍可移除牌桌，后续费用及门票退款继续由既有比赛服务处理，不被回放存储故障阻止。已生成的原记录仍留在全局原发送队列重试。
- 确认状态随常驻桌跨热更新保留；首次加载会接管原发送队列中属于该桌的回放，并能观察旧模块已开始的写入完成。不会让其他代理、其他比赛或同房号旧生命周期的记录错误地阻塞新桌。
- 兼容早期仅初始化本地 records 的常驻状态，补齐发送队列容器，保留已有记录。

确认信息只涉及已经生成的回放及内存发送状态，不新增资金流水、未结算表或启动资金对账。没有复制资金处理、重新下注、退款或派奖。游戏服仍通过统一 RPC 写 data-center，不直连 MySQL／ES。

## 修改文件

- `game-server/src/core/user-center.js`：完整性校验、桌级原回放确认、延迟投递及旧状态接管。
- `game-server/src/core/tournament.js`：检查点与正常回收等待原回放确认，内部状态附 reportingPending。
- `test/game-server/tournament-record-persistence.test.js`：7 项新增回归测试。
- 比赛实现说明与剩余开发清单同步更新。

## 验证

相关专项测试 44 项通过，日志 `cache/tournament-record-gate-scoped-node.log`。覆盖持久回执缺失／数量不符、延迟投递、热更新、原写入确认、参与名单缺失、空投影、正常回收等待、作废仍可执行，以及其他代理和旧桌生命周期隔离。

Node 全量 1200 项通过，日志为 `cache/tournament-record-gate-full-node.log`，包括真实剔除 test/cache 的生产副本加载验证。未访问真人账户、未改真实资金、未重启服务、未提交代码。本轮未修改 Go，不重复运行无关 Go 回归。

## 仍有的边界

这道检查保护的是本模块处理的已完成比赛手牌，在持久确认前不把该手推进为已确认检查点。SQL 已接收并不等于 ES 查询立即可见，ES 投影继续使用既有后续重试。

原记录首次被 SQL 接收前，进程退出仍可能丢失内存原文；本轮没有增加跨进程日志，也不恢复崩溃比赛。游戏进程丢失后仍按用户确认的异常作废、全额原路退款规则处理。

首次热加载只能接管仍存在的原队列及常驻状态，不能重造更早已丢失的回放。普通现金旧接口的持久化窗口、完整旧 ESM 回收及长期多实例故障验收仍在剩余清单内，不把整项“跨进程记录保障”标为全部完成。
