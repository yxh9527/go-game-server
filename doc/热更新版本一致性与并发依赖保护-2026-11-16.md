# 热更新版本一致性与并发依赖保护

本轮修复可回收加载路径中的源码错载、更新漏检、并发循环等待和依赖重复实例化问题。保留三个入口及五个无状态依赖的白名单范围，没有把房间、钱包或连接状态纳入回收。

## 已复现的问题

旧实现遇到以下情况会出错，新增用例先验证了失败，再修改代码：

1. 内容版本地址已算出，源码或其传递依赖在真正编译前变化。加载器会读取新文件，却仍使用旧版本地址。旧命名空间被 GC 回收后，再请求其旧地址也有同类问题。
2. 文件等长修改，文件系统时间戳又相同时，原大小／mtime／ctime 缓存把修改当作未发生。
3. 两个入口并发加载，各自先等待异步依赖，再互相导入。只检查单条祖先链不能发现跨加载任务的循环，两个 Promise 会相互等待。
4. 同一依赖通过静态导入和直接加载进入缓存时，版本与 link 参数的顺序可能不同，导致重复创建命名空间。实际大厅的 decode.js 也可能遇到该路径。

源码不变、原来缺失的依赖文件后来补齐时，原依赖列表还可能遗漏新文件，导致内容版本没有变化。本轮也补充了对应处理与回归。

## 修改

shared/hot-loader.js 每个新的重载周期实际读取并哈希源码；同一周期每个文件只核对一次，只有内容哈希相同时才复用解析后的依赖列表。依赖候选保留在列表中，在遍历版本图时检查文件是否存在，因此创建或移除依赖也能反映到图版本中。仍保留原 4096 文件缓存上限，不长期保存源码原文。

新增 readSource，用于可回收模块首次编译：重新核对当前依赖图与请求版本，并检查实际读取源码的哈希。如果已经变化，返回 ERR_HOT_SOURCE_CHANGED，不把当前磁盘内容冒充历史源码。已经存活的旧命名空间仍可复用，正在运行的旧处理函数继续正常执行；版本源码已不可取得时明确失败，原 watcher 保留之前正常的处理器。

shared/hot-entry-factory.js 增加仅在依赖加载期间存在的等待图，插入等待边前检查是否会形成循环。失败与正常结束均释放等待边，不影响多个正常入口共享同一个依赖。新增 dependencyWaits 纯数字诊断计数，不对外暴露任务或运行对象。

可回收模块的地址在缓存、依赖持有和等待图中统一参数排序，消除同版本仅参数顺序不同造成的重复实例。生产副本烟测除了检查 8 个活跃模块，还检查实际只编译 8 个模块，覆盖直接加载和静态导入复用。

源码复核只接入当前可回收加载路径，不代表所有原生 ESM 依赖图的卸载及升级竞态已经解决。本轮不新增 Redis 键、源码归档、SQL 备份或资金重试机制。

## 验证

test/shared/hot-entry-factory.test.js 新增 7 个回归，覆盖自身源码变化、传递依赖变化、相同时间戳的等长修改、参数顺序复用、并发循环、正常并发共享和缺失依赖补齐；已有 GC 用例进一步验证旧命名空间确实回收后，旧地址请求不能偷偷执行新源码。循环失败后及正常共享后，pendingEntries 和 dependencyWaits 均为 0。

修改前的失败证据为 cache/hot-source-consistency-before.log、cache/hot-source-query-before.log。最终专项 **38 项通过**，日志 cache/hot-source-consistency-scoped-node.log；Node 全量 **1318 项通过**，日志 cache/hot-source-consistency-full-node.log，包含实际剔除 test/cache 的生产副本加载及 HTTP 检查。

源码复核与等待图保护完成后，还运行了完整真实编解码副本连续变化的隔离验证：

```powershell
node --expose-gc test/performance/hot-source-change-load.mjs --loader=collectible --entry=codec --revisions=600 --clients=128 --sample-every=50 --output=cache/hot-source-verified-600.json
```

源码复核增加了重载时的文件读取与哈希成本，不在每次心跳或下注请求中执行。不能只看内存数字而忽略重载延迟，也不将不同批次的单次测量作为严格的性能对照。
