## 接口与生产配置

新增内部 datacenter.GogameStorageService；Node 协议为 shared/rpc/proto/gogame.proto，对应 Go 协议在 micro_service/proto/gogame.proto。业务操作统一在 Call 的 operation 白名单内；payload 是业务 JSON，不接收 SQL 或表名。包括房间配置、比赛及排期、门票数量/模板/比例、奖励、盲注，以及比赛玩家和分桌快照。

Node 服务配置 data_center 指向现有 data-center 地址。新存储接口的凭证从 Node 配置 data_center_token 或环境变量 GOGAME_DATA_CENTER_TOKEN 读取；data-center 同名环境变量必须设置相同值，通过 x-gogame-storage-token 元数据验证。未配置或不匹配明确失败，不回退 MySQL 或本地模拟。原有 Gateway 登录/鉴权和 ES 回顾接口保持现有协议。

生产 listMatchPlayers/listMatchRooms 由 data-center 将 gg_match_runtime 的权威报名/分桌投影覆盖旧 gg_match_player/gg_match_room，同一场次不能两份叠加。原版 playing 状态仍为 4，代理隔离仍由后台凭证和玩家登录资料判定；代理归属在数据中心更新/事务中再次检查不可迁移。

## 比赛事务

withMatch 使用双向流 MatchTransaction，保持原有回调接口：Node 发 begin(id)；data-center 开启 MySQL 事务并 SELECT FOR UPDATE，返回比赛行与报名/资金/outbox 日志；Node 执行业务后发 commit(row,state)；data-center 在同一事务中写回并真实提交，最后回 committed。

同一流承载整个事务，不能拆成无锁读后写或在不同实例间传递事务连接。客户端回调抛错、断开或超时会回滚；服务端最多持锁 60 秒，不接受无限等待的客户端。仅收到提交确认才报告持久化成功；提交回执丢失时结果不确定，后续按权威状态和原幂等键重试，不假设未执行。排期场次唯一性由 data-center 中的排期行锁及 gg_match_occurrence 唯一键保证，不能通过多个无事务 RPC 拼接。

一小时短期响应防重缓存继续生效；权威报名、扣退费/奖励日志及场次唯一映射不随缓存到期删除。并发和崩溃恢复仍需真实 MySQL/资金系统联调，不把内存缓存当作跨实例锁。
