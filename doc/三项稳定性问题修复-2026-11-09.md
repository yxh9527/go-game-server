# 三项稳定性问题修复

日期：2026-11-09。延续安全排查，不重启常驻服务、不提交代码、不修改原 static，不新增幂等流水、未结算记录或启动对账机制。

## 1. 百人派彩超过 64 账户

保留一个完整资金批次，在既有 Redis Lua 中先校验全部账户和操作，再一次提交，避免把一局拆成多批而产生部分入账。

- 数据中心 gogames/data-center/dao/gogame_cash.go：单批最大 1024 账户、4096 步骤，原资金校验和 Lua 写入顺序不变。
- shared/cash-limits.js 与权威钱包使用同样边界，超限在发起 RPC 前抛出 CASH_CAPACITY_EXCEEDED 并回滚本地本次业务状态。
- 每局最多接受 1000 个实际下注账户，预留 24 个资金账户给庄家等附带操作；百人两条公共下注路径都在扣款前检查。已有下注者可继续正常下注，撤注清空后可释放名额。不是把在线旁观人数限制为 1000。
- 验证 65、1000、1024 账户均一次原子派彩；最后一个账户版本有误时没有任何人先入账；原版本重复批次被拒绝。4096 步骤成功，1025 账户和 4097 步骤拒绝。Go dao/rpc 全部通过。
- 安装/复核脚本 scripts/expand-cash-capacity.ps1 已实际同步本地 gogames 源码及容量测试；doc/待应用/cash-capacity 是可审阅副本，不代表服务已经发布。

发布顺序：先正常发布 data-center，再发布配套 Node 业务与容量限制。仅更新 Node 不能改变仍在运行的旧 Go 服务上限。本轮没有启动或重启 data-center。

## 2. 无改动热加载重复保留模块

shared/hot-loader.js 根据模块自身与可达相对依赖的内容计算指纹，shared/hot-import.js 在真正 import() 之前生成规范 URL；不能只在 resolve 回调中改 URL，否则原始时间戳解析项仍可能保留。

- 未变化的模块重复导入复用同一个命名空间；修改 B 时其调用父模块重新加载，无关 C 的命名空间继续复用。
- 既有 rel.js 导入在热加载时链接到规范导入器，无需批量改写全部玩法文件。静态相对依赖同样参与指纹，循环依赖有访问集合保护。
- 旧任务已加载的依赖保持不变，不因磁盘后来修改而临时切到新版本；新处理器得到新依赖图。编译失败时旧模块仍可继续使用。
- 环境、RPC 门面/传输、房间注册表等常驻设施保持单例，避免切出另一套钱包/房间或重复建立传输连接。源码指纹元数据和重载令牌历史均有边界。
- hall/game-server/match 的监听器用规范入口导入；四个服务的启动监听范围补充 shared。监听基础设施本身变更需要随正常发布启用，不能声称现有旧 watcher 已被整套替换。

测量：旧时间戳方案仅 8 次无改动导入，强制 GC 后约 23.08 MB；新方案 128 次无改动导入，约 8.28–8.35 MB。原始测量见 cache/game-audit-profile-before.json、cache/three-fixes-hot-profile.log。单位为本机独立进程的 heapUsed，不是生产 RSS 上限。

### 严格回收仍有边界

本轮解决了无改动/无关模块反复加载的主要增长源，**没有声称 Node 能卸载所有真实修改后的历史 ESM 版本**。已经由旧加载器导入到当前进程的模块不会因为新补丁自动消失。

若要求长期多次真实改代码后的堆也严格有界，需要后续业务 Worker/隔离运行时方案：主进程继续持有监听器、会话和权威钱包；房间业务在独立运行时内执行，结算边界交接房号、创建时钟、成员与已结算历史，资金提交继续由原权威接口控制。旧运行时没有未完成动作和房间责任后退出，才可回收其模块缓存。当前没有擅自把在局牌桌或资金状态跨进程迁移。

已经执行 100 个并发 WebSocket、120 秒心跳与无改动导入短压测：约 43.79 万次请求、59 次重复导入，错误为 0，关闭后注册会话为 0。该测试使用独立端口和合成鉴权状态，不调用线上服务或真实钱包，**不等于数天压测，也不等于 1000 人同时真实下注的生产容量证明**。日志和详细堆/事件循环数据：cache/three-fixes-load.log/json。

## 3. 正常辅助连接关闭被当成异地登录

不能简单停止发送 1203 再直接关 socket：原版客户端可能自动重连，使刚退出的旧连接又回来，影响后续进房。

- 服务端只对“主连接结束所触发的、角色为 hundred 的辅助连接”附带现有 1203 的兼容可选字段 reason=primary-closed、auxiliary=true。
- 客户端 RoomSocket2 在这两个字段匹配时执行 close(true,true)：不显示异地登录对话、不走自动重连、清除旧连接上下文。
- 真正不同凭证/设备替换、租约无效等仍使用原踢出处理，不以房间类型或退出时间窗口笼统忽略 1203。
- 数据通过已有 WebSocket 消息传递，兼容大厅代理是否转发 CloseEvent.reason；不依赖刚才已经被代理清掉的域名。
- 配套客户端 1105 增加可选的 auxiliaryOnly=true，只约束 RoomSocket2 必须配对，不能新建或替换主登录；独立百人场景仍可正常建立主连接。辅助登录等待主连接 1205 鉴权成功再发送，主连接失败或关闭会取消等待并清理监听。
- 本地与 Redis 协调器同时校验代理/账号、凭证摘要、宿主房号、服务端确认的房间类型以及主连接状态。允许已鉴权但尚未首次进房的短暂配对窗口；hasJoined 一旦为真，退出后不得再用该窗口接纳旧辅助。标记为辅助的请求不递增主登录尝试号；被拒绝的辅助也不能推进本地登录栅栏，避免踢掉仍在慢鉴权中的主连接。协调版本 native-sockets-6 复用已有 backend 与会话。
- 重复浏览器回归还定位到开发入口的重复消费：capture 适配先直接进房，原版 bubble 监听又把同一请求留作启动缓存，导致偶发旧房号回流。cache/client-web/dev-patch.js 改为原版先消费、适配延后兜底，识别原版已开始进房；轮询不再重复执行组件 start。新增消息顺序与原版启动去重测试。
- 旧客户端未更新时保持原有踢出处理，因此需要完整刷新大厅/iframe 取得新响应适配脚本。

回归直接执行原版 RoomSocket2 方法，验证正常关闭不触发替换登录逻辑，真实替换仍触发；分布式双连接测试确认租约释放与真正互斥保留，并覆盖辅助先于慢鉴权主连接完成的情况。修正消息消费后，原版 Chrome 连续三轮完整完成“炸金花退出 → 牛牛退出 → 红中血流退出 → 再进红中血流”，无误导性替换提示、无退出后 1105 自动重连、无脚本异常；日志 cache/three-fixes-native-fixed.log 与 cache/three-fixes-native-repeat.log。百人跨场景菜单与快照另行通过。此前失败日志保留作诊断依据，不算通过结果。

协议注意：正常辅助退场仍可能在网络日志看见带上述原因的 1203；修复的是错误提示和错误重连，并没有伪称网络上彻底不再出现这个消息号。
