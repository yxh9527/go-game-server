# 最终记录随结算快照持久化

本轮在上一批“data-center 持久接收”之上继续处理：统一资金确认后，游戏服可能尚未把战绩发给 data-center。上一批 5 文件已应用，当前代码摘要检查为 0 待应用；本轮为新修改。

## 实现范围

1. Node 权威钱包在同一次游戏动作中收集最终用户中心记录。普通座位／净额结算、百人和赌场结算提交前，把真实战绩（包括本人可见回放）附到原 SettlementItem.record 的 completedDisplayReport 字段，不新增协议字段或资金流水。
2. 不补造未保存的历史牌局、机器人个人战绩或对手未公开手牌。已正常公开的牌保持原可见性。
3. Go 将完整金融注单及原 record 保存到既有 financeRound.Settlement.Reports。普通结算先保存原 CLAIMED 快照，再执行原钱包路径；SEAT_NET／BANKER_NET 的最终报告和原终态快照一起进入原 Redis Lua 原子提交。
4. 从已经完成的结算结果取权威余额补入索引文档；原记录时间、牌局结果和最终金额保留，不用当前余额或新配置编造历史。
5. 后续 ES 投影只读既有最终快照并写固定 ID 文档，不调用 Bet、Settlement、退款、扣款或派奖。没有报告内容的旧快照不生成假记录。
6. 金融注单、completedDisplayReport 对应的用户中心／回放索引都确认成功后，才保存原快照的索引完成标志；此前不能归档该牌局。单一投影循环每秒最多选择 4 个牌局，每局最多处理 100 条记录，ES 批次最多 40 条，已处理位置保存在同一个快照中。慢写入不叠加并发循环，首个失败返回后下轮重试。
7. ES 失败或索引确认回执丢失时重复固定 ID 写入；用户中心及回放使用与 data-center 相同的文档身份及 create 语义，接受已存在的 409，不重复生成记录。
8. 用户中心元数据的代理、玩家、币种、有效下注及净盈亏必须与已确认的金融记录一致，余额取权威结算结果。不符合时保留原快照并报告错误，不能将错误索引标为完成。
9. ES 长期不可用时，不再通过丢弃旧报告控制容量。按现有热快照计算积压，高水位 50000 份报告或估算 128 MiB 时，统一 Bet 拒绝创建新牌局；已接受牌局仍可结算／退款。检查每秒缓存，阈值属于背压而非严格进程内存上限；同时进入结算的在局责任仍会增加报告。
10. 百人预留保持原金额、游戏结果、抽水及账户信息锁定，仅允许最终附加 completedDisplayReport；不能借此修改原结果或重新请求另一份预留。

不新增数据库表、独立幂等资金流水或启动资金对账机制。利用服务原有牌局快照装载，仅定时投影已经完成的原记录；原服务已有的资金重试机制本轮未扩展为自动重新派奖。

## 验证

Go 用例覆盖：服务对象替换后只从原 Redis 快照恢复报告、ES 失败保留报告、恢复后固定 ID 索引、账户余额／版本不变、没有权威余额或身份不一致拒绝索引、未完成结算不索引、待索引不能归档、100／40 条处理预算及大积压背压。原 SEAT_NET Lua 用例确认资金和带原报告的终态一起写入，并且重复请求不改原内容。

Node 用例使用实际普通桌、12 款百人和赌场游戏引擎及统一资金门面，验证最终提交带真实战绩；异步 data-center 发送失败时，金融提交中已保留同一份最终记录。另测牌面隐私、原预留复用及修改经济结果拒绝。

Node 全量 **1180 项通过、0 失败**，日志 `cache/settlement-final-payload-full-node.log`。Go app 全模块、data-center、lottery、micro_service、web-api/controller/v2 检查通过，日志 `cache/settlement-final-payload-full-go.log`。未访问真人账户或运行远端故障演练，未重启服务或提交代码。

## 仍有边界

- 保证依赖原资金 Redis 的持久配置及故障可靠性，不能用代码测试代替 Redis AOF／复制／故障切换验收。
- 旧客户端／旧游戏服没有附加最终显示记录的请求，只保留它原本有的金融结果，不会凭空补齐战绩或逐手回放。
- 比赛 101 不走现金 Settlement，仍使用 data-center 持久接收；游戏服尚未送达的比赛回放存在原窗口。比赛崩溃后的作废规则不变。
- 刮刮乐使用独立持久票据链路，本批不自动给其 record 添加 Node 用户中心元数据；旧游戏资金接口、下注／取消流水的内存输出链路也没有全部迁移。
- 资金结果处于 CLAIMED 等未完成状态时不索引为完成。本轮没有增加进程启动自动重结算或恢复在局游戏的机制。
- data-center 玩家面板统计和 ES 显示为不同投影，不能把最终战绩已保存当作所有统计也在同一事务完成。
- 生产多实例仍应遵守现有资金写入归属，未解决跨写入实例同时更新原金融快照的全部问题。

因此剩余清单中的“记录持久保障”继续列为部分完成；本轮关闭了已接入统一 Settlement 且随请求附上原最终记录的主要窗口，不是整个项目所有记录永久零丢失的结论。
