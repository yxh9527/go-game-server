# 智能投注已停止任务内存一小时清理

本轮开始核验上一批正常零盈亏凭证合并 12 文件已全部应用，0 项待应用。本轮仅修改 Node，不新增 Go 包、表结构、Redis 键或资金恢复流程。

## 问题与修复

原智能投注任务停止后一直留在 runtime.smartBetState.tasks 和各房间 table.smartTasks 中，只有用户主动删除或后来查询到远端删除才移除。任务逐渐累计，会占满全服 10000 个本地任务容量；旧房间已经移除时，原投递还可能缺少持续执行入口。

生产模式现在仅对已确认存入 MySQL、状态 stopped、没有 pendingInning 和 activeAttempt、也没有待投递内容的任务，记录首次终态确认时间。本地副本满一小时后分批从 runtime 和房间 Map 清除，任务历史仍保留在原 gg_smart_task。原任务版本变化、存在资金责任或保存未确认时，不按本地时长清理。

状态确认时间位于常驻 runtime，业务热更新保留；读列表、详情、同版本重复确认不会续期。首次热加载新清理规则时，对既有停止任务先通过原保存操作重新确认，不能仅凭旧内存中的 stopped 标志直接认定已持久化。

公共游戏心跳调用原 smartBet.flush，即使原房间已销毁，也会继续处理待投递及本地到期清理。每次最多保存 100 条，清理每 5 秒最多移除 100 条；清理属于分批轮询，积压会延迟物理移除。任务保存仍由原 SQL 接口执行，不在 Node 直连 MySQL。

## 回执与重试保护

保存回执必须 stored=true，且原任务身份、配置、版本和状态相符；回执缺失或不符时保留原待投递快照。较旧保存请求完成时，不能删除后来排入的新快照，也不能为新出现的资金责任标记清理时间。

清理本地任务后，创建同一 requestId 会先读取原任务历史并返回原结果；配置不一致明确冲突，不重新附加到房间或重新下注。新 requestId 仍可创建，原每玩家历史数量限制继续保留。已停止的任务没有通过清理自动恢复执行。

本轮只对生产 MySQL 已确认任务移除本地副本。开发模式的任务历史仍使用既有真实内存来源，不因为没有 MySQL 副本而被本轮清理掉。金融下注／退款／派奖记录和 Redis 终态期限没有改变，旧 ESM 模块的运行时回收问题也没有据此标为完成。
