# gogame 完整部署：nginx + PM2 + 集中配置

当前部署方案使用最外层 nginx、一个域名的不同端口、PM2 托管四个 Node 服务。**所有服务的默认配置集中在项目根目录 ecosystem.config.cjs**，不再维护 hall/config.yaml、match/config.yaml、game-server/config.yaml；client-web 也有独立配置段。

## 1. 架构与端口

```text
浏览器：一个域名 game.example.com
  └─ 最外层 nginx（TLS、HTTP 代理、WebSocket 升级）
       ├─ :443  大厅 / API ─────────────→ hall :11042
       │        /admin、/admin/v1/* ────→ match :11040
       ├─ :8444 游戏资源 ───────────────→ client-web :4000
       │                                  └─ 自动创建多个 worker，共用 4000
       └─ :8445 WebSocket（/、/hundred）→ game-server :11041

hall → match 内部 HTTP :11040
hall → game-server 内部 WebSocket :11041
match → game-server 带签名的内部 WebSocket :11041
match → Redis「match」频道 → hall 内存投影
hall / match / game-server → 现有 data-center、lottery → 数据与资金后端
```

nginx 是唯一公开应用入口，浏览器无需直连 Node 内部端口。nginx 保留 Node hall、client-web 的页面和脚本响应适配，不直接替代它们读取 static。不需要 nginx-client 服务、静态文件生成命令或 worker 级 nginx 端口配置。

| 服务 | 内部端口 | PM2 应用名 | 职责 |
| --- | ---: | --- | --- |
| hall | 11042 | gogame-hall | 大厅、登录、HTTP API、比赛列表 |
| client-web | 4000 | gogame-client-web | 游戏资源、语言映射、JS 响应适配 |
| game-server | 11041 | gogame-game-server | 连接、常驻房间、牌局与结算 |
| match | 11040 | gogame-match | 比赛、报名、调度和管理接口 |

PM2 四个应用均使用 fork、instances: 1、watch: false。只有 client-web 主进程内部创建 worker；其他服务的房间和连接属于现有进程，不能直接改 PM2 instances 随机分流。

## 2. 环境与目录

要求 Node.js 22.20.0 或更高兼容版本、npm、PM2、支持 TLS 的 nginx。以下示例为 Linux。证书覆盖实际使用的一个域名，不必为三个端口分别申请域名。

```text
/opt/gogame/app/              # dist/production 的内容

  package.json、package-lock.json
  node_modules/              # 根目录只装一份依赖
  scripts/prod.js
  shared/
  hall/src/
  client-web/src/
  game-server/src/
  match/src/
  static/avator/
  static/hall/
  static/client/2.0.1279/
  build-manifest.json、DEPLOY.md

```

## 3. 外部服务准备

| 依赖 | 集中配置字段 | 用途 |
| --- | --- | --- |
| data-center gRPC | common.data_center | 业务数据、鉴权、比赛存取、历史和报告等 |
| 业务存储凭证 | common.data_center_token | 需与后端 GogameStorageService 使用的 token 一致 |
| Redis | common.redis | 生产 Pub/Sub 和既有缓存职责 |
| lottery gRPC | common.lottery | 权威余额、统一现金资金和票务接口 |
| open-api / 第三方平台 | 平台自己的入口配置 | 签发真实登录凭证、生成公开大厅链接 |

common 是本配置文件中的公共对象；合并后各服务实际字段仍叫 data_center、redis 等。

Node 不直接配置 MySQL/ES 连接。表结构和默认数据位于 gogames/app/tables/gogame，沿用 InitMysqlDb。匹配的后端协议、GogameStorageService 注册、资金接口、路由投影、代理归属和房间数据必须先真实部署。Node 单测或 Go overlay 测试通过，不代表后端已应用或真实资金链路已验证。参见《数据中心存取迁移.md》和对应玩法对接文档。

## 4. 构建与上传

在源仓库根目录执行：

```sh
npm ci
npm test
npm run build:prod
```

输出 dist/production/。生产包包含 ecosystem.config.cjs、四个服务、shared、原始 static、生产启动器和依赖清单；不包含 test、cache、mock-server、tools、doc、node_modules，不生成各服务 config.yaml。

生产构建将集中配置中的 developmentEnabled 改为 false，禁用 env_development。生产配置为 env: prod、wallet.mode: online，game-server 的 finance 已覆盖全部现金玩法。源配置保留开发入口，构建不修改源文件。

上传 dist/production/ 的**内容**到 /opt/gogame/app，然后在该目录安装依赖：

```sh
cd /opt/gogame/app
npm ci --omit=dev
```

nginx 模板在源仓库 doc/deploy，不自动进入生产包，需单独部署。重复 build:prod 会替换原先由构建器生成的目录；填写过的线上配置需独立备份，新构建后重新应用，不能依赖 dist 目录保留手工修改。

## 5. 统一配置 ecosystem.config.cjs

先配置生产包根目录的 ecosystem.config.cjs，再启动 PM2。文件包含以下区段，均有注释：

| 区段 | 说明 |
| --- | --- |
| common | 四服务共享的 data-center、Redis、lottery、日志设置 |
| publicProduction | 生产浏览器访问的 nginx 地址 |
| publicDevelopment | 源仓库开发环境的浏览器地址 |
| services.hall | 大厅监听和内部服务连接 |
| services['client-web'] | 资源服务监听、worker 数 |
| services['game-server'] | 游戏监听、比赛控制密钥、现金资金覆盖 |
| services.match | 比赛监听、控制密钥、管理凭证和调度 |
| configuration / environment / apps | 合并配置，生成 PM2 启动快照及进程设置 |

### 5.1 公共依赖

```js
const common = {
  data_center: '127.0.0.1:50051',
  data_center_token: process.env.GOGAME_DATA_CENTER_TOKEN || '',
  redis: { host: ['127.0.0.1:6379'], user: '', pwd: '实际密码' },
  lottery: process.env.GOGAME_LOTTERY_ADDRESS || '',
  log: '',
};
```

填写真实地址、凭证。代码中保留的内网 IP 和上述 127.0.0.1 都只是各自环境设置，不能据此假定服务已可达。可将引用环境变量的位置直接改为实际值，或用第 7 节的环境文件提供；不要把真实密钥提交到代码仓库。

lottery 也支持现有 nodes/agents 对象映射。如果按代理绑定权威写入节点，不要改成随机负载均衡。Redis 的比赛广播要求 hall 和 match 连到同一目标。

### 5.2 对外地址

```js
const publicProduction = {
  hall_url: 'https://game.example.com',
  client_url: 'https://game.example.com:8444',
  game_ws_url: 'wss://game.example.com:8445',
  hundred_ws_url: 'wss://game.example.com:8445/hundred',
};
```

换成实际域名。hall_url 不带 /21/0，client_url 不带版本目录或参数；大厅自动拼接资源版本。/hundred 用于区分第二条连接，nginx 仍转给同一个 game-server。填写 https/wss 不会自动配置 TLS，必须由 nginx 提供真实证书。

hall 和 client-web 从同一 public 对象生成配置，不需维护两份。浏览器对外端口与 Node 内部端口独立：public.client_url 为 8444，client-web 监听仍为 4000。

### 5.3 服务内部配置

```js
hall: {
  server_ip: '127.0.0.1', server_port: 11042,
  game_server: '127.0.0.1:11041',
  hundred_server: '127.0.0.1:11041',
  match_server: '127.0.0.1:11040',
},
'client-web': {
  server_ip: '127.0.0.1',
  client_web_port: 4000,
  client_web_workers: 'auto',
},
```

同机 nginx 可监听 127.0.0.1；跨机器部署填可达内网地址，并修改 nginx upstream。当前源文件保留 0.0.0.0 便于开发机被内网 nginx 访问，线上按实际网络设置。

hall 的 game_server/hundred_server 用于内部 WebSocket，不填静态资源 URL；match_server 是内部 HTTP 入口，生产比赛功能不能遗漏。

client_web_workers: 'auto' 按 CPU 选择、最多 4 个，也可填 1～64 的整数，1 为单进程。PM2 只管一个 client-web 主进程，不要再用 PM2 cluster 或 pm2 scale。worker 共用 4000，每个 worker 独立执行原有业务热更新。

### 5.4 比赛、管理和生产资金

services['game-server'].match_control_secret 与 services.match.match_control_secret 必须相同；默认均引用 GOGAME_MATCH_CONTROL_SECRET。该密钥签名比赛调度，不是玩家 token。

services.match.admin_token 默认引用 GOGAME_ADMIN_TOKEN。生产管理功能启用前填写独立凭证；可在 admin_agents 添加 `{ agent_id: 真实ID, token: '代理独立令牌' }`，各令牌非空且唯一。管理 API 使用 X-Admin-Token，平台管理比赛时还需指定实际代理，代理凭证不能越权操作其他代理。

保留 game-server.finance 的 provider: 'lottery' 和完整 room_types。启动时会验证全部现金玩法覆盖；不要为绕过错误删掉资金校验或改成 local 钱包。

## 6. 配置最外层 nginx

正式模板：[deploy/nginx-production.conf](deploy/nginx-production.conf)。该文件是包含 events/http 的完整主配置，替换 /etc/nginx/nginx.conf 使用，不能再嵌入已有 http/server。

替换域名、证书、upstream；端口调整须同步 publicProduction：

| 外部请求 | 内部目标 |
| --- | --- |
| :443 大厅、/_next、API、头像 | hall:11042 |
| :443 /admin、/admin/* | match:11040 |
| :8444 游戏首页、资源、头像 | client-web:4000 |
| :443 或 :8444 /api/internal/v1/do、/internal/v1/do | hall:11042 |
| :8445 WebSocket /、/hundred | game-server:11041，保留路径和升级头 |

Node、nginx 同机 upstream 使用 127.0.0.1；分机用 Node 内网 IP，并确保监听地址和内部网络可达。浏览器只开放 nginx 的 443、8444、8445，80 用于跳转；Node 及后端端口只向必要内网开放。

模板不直接读 static、不添加长期接口缓存，access log 去掉查询参数，避免记录登录凭证。不要新增会阻止跨端口 iframe 的 X-Frame-Options: SAMEORIGIN。

```sh
sudo nginx -t
# 已运行 nginx：
sudo nginx -s reload
# 首次启动按系统服务管理方式执行，例如 sudo systemctl start nginx。
```

## 7. PM2 启动、日志和开机恢复

所有 PM2 命令使用同一运行账号，例如 gogame。不要混用 root 的 sudo pm2 与普通用户 pm2。按发行版准备账号和目录，已有账号不要重复创建：

```sh
sudo useradd --create-home --user-group --home-dir /opt/gogame --shell /bin/bash gogame
sudo install -d -o gogame -g gogame /opt/gogame/app
sudo install -d -o root -g gogame -m 0750 /etc/gogame
```

项目文件、依赖由该账号管理。如果选用环境文件，填写 /etc/gogame/runtime.env（shell KEY=value 格式），可设置 root:gogame、0640：

```sh
GOGAME_DATA_CENTER_TOKEN='实际存储凭证'
GOGAME_LOTTERY_ADDRESS='实际lottery主机:端口'
GOGAME_MATCH_CONTROL_SECRET='两端共用的随机签名密钥'
GOGAME_ADMIN_TOKEN='独立的平台管理凭证'
```

也可以直接在 ecosystem.config.cjs 对应字段填写，省略环境文件。环境变量只是可选的密钥来源，服务配置结构始终集中在一个文件。

在具有可用 Node/npm 的 gogame 账号安装 PM2 CLI（全局 npm 目录须可写，或由管理员预装）：

```sh
sudo -iu gogame
node --version
npm install -g pm2
pm2 --version
```

首次启动：

```sh
cd /opt/gogame/app
# 使用可选环境文件时，先执行：
set -a
. /etc/gogame/runtime.env
set +a

pm2 start ecosystem.config.cjs --only gogame-game-server
pm2 logs gogame-game-server --lines 50 --nostream
curl -fsS http://127.0.0.1:11041/
# 确认加载成功后启动依赖服务。
pm2 start ecosystem.config.cjs --only gogame-match,gogame-client-web,gogame-hall
pm2 status
```

依赖和配置已预先检查完，也可选择一次启动 `pm2 start ecosystem.config.cjs`。PM2 不会因 apps 数组顺序等待前一服务业务就绪；online 仅表示进程存在，还需检查日志与第 9 节的健康、真实业务链路。

PM2 直接运行 src/boot.js；默认 env 是生产模式，完整服务配置序列化到 GOGAME_SERVICE_CONFIG。服务与 client-web worker 读取同一快照，不会各自重新拼一份配置。开发入口在源配置 env_development，只有显式 --env development 或开发启动路径才使用；生产包没有此入口。

日志默认在运行账号 ~/.pm2/logs，安排日志保留与磁盘管理：

```sh
pm2 logs gogame-client-web --lines 100
pm2 logs gogame-hall --lines 100
pm2 logs gogame-game-server --lines 100
pm2 logs gogame-match --lines 100
pm2 monit
```

client-web 日志出现 primary/worker ready；worker 异常补位，同一位置连续快速失败 5 次后停止服务，PM2 按策略恢复。PM2 不开启文件 watch，不配置定时/内存阈值重启；业务 JS 使用项目自身热加载。

验证通过后，同一账号保存列表、设置开机恢复：

```sh
pm2 save
pm2 startup
```

执行 pm2 startup 输出的管理员命令，以实际 Node 路径、账号和主目录为准。Linux 上这可能创建 PM2 自身的 systemd 启动项，四个应用仍只由 PM2 管理。

PM2 保存列表包含启动环境及配置快照，不要把 ~/.pm2/dump.pm2 当普通无凭证文件公开。修改集中配置、环境变量后，旧进程和已保存列表不会自动更新；在维护窗口更新受影响服务，例如资源服务：

```sh
# 如用 runtime.env，先重新加载它。
pm2 restart ecosystem.config.cjs --only gogame-client-web --update-env
pm2 save
```

四服务配置共用字段变化时要核对全部受影响应用。game-server 重启会影响连接和进程内房间、比赛，不能把 pm2 restart/reload all 当成普通业务热更新。旧手工/systemd 进程迁移到 PM2 前，先安排维护并释放端口，不会自动接管旧进程游戏状态。

## 8. 开发及单 IP nginx 测试

源仓库直接 `npm run dev` 时从集中配置读取开发 profile，继续用内存模拟。`npm run hall`、`npm run client-web` 等也默认读取源配置的开发段；`npm run prod:hall` 等强制读取生产段。在生产包内，直接启动也只有生产段。

也可以在源仓库用 `pm2 start ecosystem.config.cjs --env development`，只适合隔离开发环境。生产包禁用这一 profile。

单 IP 测试使用 [deploy/nginx-test.conf](deploy/nginx-test.conf)，不要和正式主配置同时替换。默认 nginx 172.21.211.219、Node 172.21.211.216，修改集中配置的 publicDevelopment：

```js
const publicDevelopment = {
  hall_url: 'http://172.21.211.219:10031',
  client_url: 'http://172.21.211.219:10032',
  game_ws_url: 'ws://172.21.211.219:10033',
  hundred_ws_url: 'ws://172.21.211.219:10033/hundred',
};
```

Node 内部端口不变，server_ip 需可被 nginx 内网访问。测试模板 upstream 按真实 Node IP 调整。Windows nginx 要调整 mime.types/log 路径。一个 IP 三个端口，不需要 hosts 或域名。

源文件当前 publicDevelopment 保留直接访问开发机的地址；本次集中配置迁移不代表已把实际运行服务切到测试 nginx。env: dev 不连接真实生产资金，生产联调使用隔离 prod 环境及真实测试凭证，不将内存模拟暴露公网。

## 9. 部署验证

内部服务检查（同机方案）：

```sh
curl -fsS http://127.0.0.1:11042/health
curl -fsS http://127.0.0.1:11040/health
curl -fsS http://127.0.0.1:11041/
curl -I http://127.0.0.1:4000/2.0.1279/
```

确认正确 service、env=prod、已加载业务版本；资源返回 200。资源版本换成实际 static/client 目录版本。HTTP 健康不等于真实资金接口验证。

外部 nginx/TLS 检查：

```sh
curl -I https://game.example.com/health
curl -I https://game.example.com:8444/2.0.1279/
curl -I https://game.example.com:8444/2.0.1279/js/index.js
curl -I https://game.example.com/admin
```

使用真实 open-api 链接进入大厅，平台入口也需改成公开域名和端口。浏览器检查 iframe 走 8444、游戏 API 走 443、WSS 走 8445 和 /hundred，握手返回 101。测试进房、退出、再次进入，以及余额、下注、结算、历史、报名、退赛、比赛调度。

管理 /admin 使用独立管理凭证，无凭证访问 /admin/v1/matches 应拒绝；平台比赛操作需选择代理，代理令牌不可越权。模板不公开代理 match 的内部 tournament 路由，hall 仍走内部 match_server。

## 10. 热更新、维护与回滚

| 变更 | 生效方式 |
| --- | --- |
| 已监听的业务 JS | 稳定部署目录中原子替换审核文件，检查 hot loaded 日志；不重启进程 |
| static 资源 | 发布匹配版本并核对版本选择和浏览器缓存 |
| ecosystem 配置、环境、端口、worker 数 | 启动快照；维护窗口按受影响服务更新，再保存 PM2 列表 |
| boot.js、加载器、依赖 | 启动基础设施升级；安排维护或状态迁移 |
| nginx/证书 | nginx -t 通过后 reload；现有 WS 不会自动迁移上游 |

不要靠切换软链接假设旧 watcher 跟随新目录，不要在在线目录删除依赖后再复制。保留旧配置、代码和资源。业务回滚原子恢复对应文件并检查热加载；nginx 回滚先 -t 再 reload；资金/比赛状态不因代码回滚自动撤销，不能重复扣款或派奖。

本次改了启动器和配置加载器，旧进程不会自动获得这套启动配置；未重启现有服务，首次迁移需安排维护。集中配置不是动态重载，页面刷新只能在服务已经读取新配置后获取新地址。

## 11. 常见问题

| 现象 | 检查 |
| --- | --- |
| 502 | nginx upstream、Node 监听、端口占用和内网 |
| loading/503 | 业务加载日志、依赖、static 完整性 |
| iframe 仍是 www.* | 是否启动新版 hall、public 配置快照、_app 旧缓存 |
| WSS 失败 | 端口、证书、Upgrade/Connection、/hundred 路径 |
| 配置改了不生效 | 是否更新正确的 ecosystem、PM2 --update-env 和启动快照 |
| 报名失败 | match_server、身份、付款、data-center |
| 比赛无法开桌 | 两端控制密钥、时钟、内部 game-server 地址 |
| 生产资金校验失败 | 完整 finance.room_types、lottery 地址/路由、后端是否部署 |
| 多进程持续退出 | 是否重复启动主进程、端口、配置、日志 |
