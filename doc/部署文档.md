# gogame 完整部署文档：最外层 nginx

适用当前项目：hall、client-web、game-server、match 均为 Node.js；client-web 已支持一次启动自动多进程。部署准则以《开发规则.md》为准。

本文以 **Linux + systemd + 最外层 nginx + 一个域名、不同端口** 为正式部署方案，同时提供单 IP 的 HTTP 联调方案。不再使用“nginx 直接代替 client-web 读取 static”的方案，也没有额外的 nginx-client 服务或静态生成步骤。

## 1. 整体结构

```text
浏览器：同一个域名 game.example.com
  │
  └─ 最外层 nginx：TLS、HTTP 反向代理、WebSocket 升级
       ├─ :443  大厅 / API ───────────────→ hall :11042
       │        /admin、/admin/v1/* ──────→ match :11040
       ├─ :8444 游戏资源 ─────────────────→ client-web :4000
       │                                   ├─ worker 1 ┐
       │                                   ├─ worker 2 ├─ 共用 4000
       │                                   └─ ...     ┘
       └─ :8445 WebSocket（/、/hundred）───→ game-server :11041

hall ──HTTP──→ match :11040
hall ──内部 WebSocket──→ game-server :11041
match ──带签名的内部 WebSocket──→ game-server :11041
match ──Redis Pub/Sub「match」──→ hall
hall / game-server / match ──gRPC──→ 现有 data-center、lottery
data-center / lottery ──→ 现有 Redis、MySQL、ES 等后端
```

nginx 是唯一对外应用入口。浏览器无需直接访问 Node 的 4000、11040、11041、11042。

三个对外端口均由同一 nginx 提供，使用一个域名和同一套域名证书。内部 client-web 多个 worker 已共享 4000，不需要 nginx 分别配置 4000、4001 等 worker 端口。

| 服务 | 内部端口 | 职责 | 是否常驻 |
| --- | ---: | --- | --- |
| nginx | 对外 443、8444、8445；80 跳转 HTTPS | 统一入口、TLS、反向代理 | 是 |
| hall | 11042 | 大厅页面、登录、HTTP API、比赛列表投影 | 是 |
| client-web | 4000 | 游戏资源、语言映射、原有 JS 响应适配 | 是，自动多进程 |
| game-server | 11041 | WebSocket、普通房间、真实牌局和结算衔接 | 是 |
| match | 11040 | 比赛调度、报名、分桌衔接、比赛管理 API | 是 |

本方案先保持 hall、game-server、match 各一份进程。game-server 的房间和连接属于现有进程，不能套用 client-web 的多进程方式直接复制并随机分流。

## 2. 部署目录和环境

运行环境要求 Node.js **22.20.0 或更高兼容版本**、npm、nginx；示例使用 Linux systemd 托管进程。确认 nginx 带有 HTTPS 支持，证书覆盖实际使用的域名。

推荐目录：

```text
/opt/gogame/app/                 # dist/production/ 的内容
  package.json
  package-lock.json
  node_modules/                  # 仅根目录安装一份
  scripts/prod.js
  shared/
  hall/src/、hall/config.yaml
  client-web/src/、client-web/package.json
  game-server/src/、game-server/config.yaml
  match/src/、match/config.yaml
  static/
    avator/
    hall/
    client/2.0.1279/
  build-manifest.json
  DEPLOY.md

/etc/gogame/runtime.env          # 环境变量及 data-center 凭证
/etc/systemd/system/gogame@.service
/etc/nginx/nginx.conf
/etc/nginx/certs/game.example.com/fullchain.pem
/etc/nginx/certs/game.example.com/privkey.pem
```

client-web **没有独立 YAML**，默认读取 hall/config.yaml；大厅和游戏资源使用的 public 地址必须一致。不要在 client-web、hall 等子目录分别安装 node_modules。

## 3. 先确认外部依赖

这些服务不由本仓库重做，必须在部署前准备好：

| 依赖 | 本项目配置 | 用途 |
| --- | --- | --- |
| data-center gRPC | data_center | 登录/业务数据、房间配置、比赛存取、历史和报告查询等 |
| data-center 业务存储凭证 | data_center_token 或 GOGAME_DATA_CENTER_TOKEN | 调用 GogameStorageService；需与 data-center 保持一致 |
| Redis | redis.host/user/pwd | 生产 Pub/Sub 及原有缓存职责 |
| lottery gRPC | lottery 或 GOGAME_LOTTERY_ADDRESS | 权威余额、统一现金资金、票务等现有接口 |
| open-api / 第三方平台 | 外部平台自己的入口配置 | 签发真实玩家凭证，生成指向公开大厅的链接 |

必须确认当前 gogames 后端已应用匹配的协议、GogameStorageService 注册、资金接口及数据变更。表结构和默认数据在 gogames/app/tables/gogame，沿用 InitMysqlDb 流程，不能用 Node 测试通过来代替后端部署或数据库迁移。相关说明见《项目结构与打包.md》《数据中心存取迁移.md》及对应玩法对接文档。

本仓库 Node 服务不直接配置 MySQL 连接。match 源 YAML 中保留的 elastic 项也不是本方案要求增加的直连 ES；历史和报告仍按既定 data-center / 权威服务链路处理。

data-center 地址和 lottery 地址必须填写实际服务地址。源文件中的本机地址和示例模板中的占位符都不能作为“后端一定已经启动”的依据。生产前确认游戏路由投影、代理归属、房间及比赛基础数据已准备好。

## 4. 构建生产包

在源代码仓库根目录执行：

```sh
npm ci
npm test
npm run build:prod
```

输出为 dist/production/。构建会把配置转换成 env: prod、wallet.mode: online，并为 game-server 生成覆盖全部现金玩法的 finance 配置；不会修改源环境配置。

产物包含服务、shared、static、scripts/prod.js 和依赖清单，不包含 test、cache、mock-server、tools、doc、node_modules。本仓库根目录的 npm run hall 是直接开发启动，而**生产包根目录的同名命令**会经 scripts/prod.js 强制生产环境，二者不要混淆。

每次 build:prod 会替换已有的、由该构建器生成的 dist/production。已在产物目录手工填写的配置必须先保存；部署机保存独立的生产配置备份，重新构建后重新应用。

把 dist/production/ 的**内容**上传到 /opt/gogame/app。不要形成 /opt/gogame/app/production/package.json 的额外嵌套。再在部署机执行：

```sh
cd /opt/gogame/app
npm ci --omit=dev
```

配套 nginx、systemd、YAML 模板位于源仓库 doc/deploy，**不会自动进入生产包**，需单独取出部署。当前方案不需要 npm run build:nginx，也不需要 dist/nginx-client。

## 5. 正式服务配置

下列模板均为单机部署：Node、nginx 同机时监听 127.0.0.1；外部依赖地址按实际环境修改。不要把模板覆盖到仍在使用的开发配置后误当生产环境已验证。

| 模板 | 部署目标 |
| --- | --- |
| deploy/hall.production.yaml | /opt/gogame/app/hall/config.yaml |
| deploy/game-server.production.yaml | /opt/gogame/app/game-server/config.yaml |
| deploy/match.production.yaml | /opt/gogame/app/match/config.yaml |

### 5.1 hall 和 client-web

核心字段：

```yaml
env: prod
server_ip: 127.0.0.1
server_port: 11042
client_web_port: 4000
client_web_workers: auto

# Node 服务间地址：不是浏览器地址。
game_server: 127.0.0.1:11041
hundred_server: 127.0.0.1:11041
match_server: 127.0.0.1:11040

# 浏览器地址：全部经过外层 nginx。
public:
  hall_url: https://game.example.com
  client_url: https://game.example.com:8444
  game_ws_url: wss://game.example.com:8445
  hundred_ws_url: wss://game.example.com:8445/hundred

wallet:
  mode: online
```

game.example.com 是占位域名，所有配置统一替换成实际域名。hall_url/client_url 只填 origin，不带 /21/0、版本路径、参数；大厅自动拼接版本并保留登录参数。game_ws_url/hundred_ws_url 填完整 ws/wss URL，/hundred 用于区分第二条连接，仍连到同一 game-server。

public 中的端口是 nginx 对外端口。client_web_port 是 Node 内部端口，不因为 nginx 使用 8444 就改成 8444。hall 内部 game_server、hundred_server 则不能改成静态站点 URL。

match_server 在生产环境必须明确配置，否则报名等比赛请求可能返回“比赛服务地址尚未配置”。

client_web_workers: auto 按可用 CPU 数选择，最多 4 个 worker；也可填 1～64 的整数。填 1 为单进程。主进程不处理业务，各 worker 共用 4000、共享同一原始 static 目录，拥有各自的内存缓存与业务热更新。

### 5.2 game-server

使用 game-server.production.yaml 模板，并保留 build:prod 生成的完整 finance.provider=lottery、finance.room_types。不能为了让服务启动而删除资金校验、只保留部分现金玩法或回退 local 钱包。

game-server 与 match 的 match_control_secret 填写**同一个独立随机密钥**，用于比赛分桌和调度签名，不是玩家 token 或 data-center 凭证。

lottery 示例采用一个明确地址；如果实际环境按代理分配写入节点，按现有 lottery.nodes / lottery.agents 映射配置，不能在多个权威写入节点间随意随机分流。

### 5.3 match 和管理端

match.production.yaml 配置内部 game_server、同一个 match_control_secret、真实 admin_token、Redis 和 data-center。

admin_token 是平台管理凭证。可按实际代理增加独立令牌：

```yaml
admin_agents:
  - agent_id: 1
    token: REPLACE_AGENT_1_TOKEN
```

令牌必须非空且唯一，代理编号换成实际编号。管理 API 使用 X-Admin-Token；平台管理比赛时还需通过 X-Agent-Id 等接口支持的字段选择代理，代理令牌只能操作自己的代理。管理凭证不要当作玩家登录凭证。

本文 nginx 把 /admin 和 /admin/* 转发到 match，其余比赛内部调用由 hall 直接访问 match:11040。单独的 Vue 后台接入文件在 admin/，不包含于 Node 生产包；若沿用现有管理后台，按现有前端发布流程发布并把管理 API 代理到 match，而不是把 Vue 源文件当静态页面直接上线。

### 5.4 外部依赖和凭证填写

三个模板均需核对 data_center、Redis、lottery。全部 REPLACE_* 字样都需替换。同一个 Redis Pub/Sub 链路必须让 hall 和 match 实际连到同一目标。

建议在 /etc/gogame/runtime.env 保存：

```text
GOGAME_DATA_CENTER_TOKEN=REPLACE_WITH_THE_SAME_STORAGE_TOKEN_AS_DATA_CENTER
```

如果改用 YAML 的 data_center_token，其优先级高于该环境变量。不要在 YAML 留一个过期 token，期望环境变量自动覆盖。示例 systemd 四个服务都会读取此文件。

模板不提供真实密钥。Redis 无密码或使用 ACL 时按实际设置 pwd/user；配置的 127.0.0.1:50051 也应与实际 data-center 的监听一致。

## 6. 配置最外层 nginx

完整文件：[deploy/nginx-production.conf](deploy/nginx-production.conf)。它是带 events/http 的完整主配置，部署为 /etc/nginx/nginx.conf；不要直接嵌进已有 http/server 或作为仅接受 server 内容的 conf.d 文件重复 include。

替换以下内容后使用：

1. game.example.com：统一换成真实域名，DNS 指向 nginx 的公开 IP。
2. 证书文件：填写真实 fullchain.pem、privkey.pem 路径。
3. upstream：同机用 127.0.0.1，跨机器用 Node 服务器可达的内网地址。
4. 如果调整 443/8444/8445，同步修改 hall/config.yaml 的 public。

配置的路由为：

| 外部请求 | nginx 上游 |
| --- | --- |
| HTTPS :443 的大厅页面、/_next、API、头像 | hall:11042 |
| HTTPS :443 的 /admin、/admin/* | match:11040 |
| HTTPS :8444 的游戏页面、资源、头像 | client-web:4000 |
| :443 或 :8444 的 /api/internal/v1/do、/internal/v1/do | hall:11042 |
| WSS :8445 的 / 或 /hundred | game-server:11041，保留路径 |

nginx 不直接读 static，也不绕过 hall/client-web 的响应适配。因此无需 nginx 静态 root、额外生成文件或 worker 级 upstream 列表。

模板的 access log 只记录不含查询参数的 URI，避免记录登录链接中的凭证。API 响应和 WebSocket 也没有开启 proxy_cache。不要给接口加统一长期缓存，不要配置会阻止跨端口 iframe 的 X-Frame-Options: SAMEORIGIN。

允许浏览器访问 nginx 的 443、8444、8445。80 仅用来跳转 HTTPS。内部 Node、Redis 和 gRPC 端口只向所需内部网络开放。跨机器部署时，127.0.0.1 不再有效：Node server_ip 需要监听实际内网地址，并修改 nginx upstream、hall 的 match_server/game_server、match 的 game_server。

nginx 检查和启用：

```sh
sudo nginx -t
# nginx 已运行时：
sudo nginx -s reload
# 尚未运行时使用系统服务启动：
# sudo systemctl start nginx
```

HTTPS/WSS 由 nginx 终止，Node 内部仍使用 HTTP/WS。仅在 YAML 填 https/wss 不会自动产生证书或启用 TLS。

## 7. 用 systemd 启动四个 Node 服务

配套模板：[deploy/gogame@.service](deploy/gogame@.service)。部署到 /etc/systemd/system/gogame@.service。

先创建用于运行服务的 gogame 系统用户及组，确保其能读取项目、运行根目录依赖和读取配置；nginx worker 只需读证书，无需直接读取项目 static。系统服务目录和环境文件由部署管理员维护。

首次部署的目录及账号准备示例（已存在的账号不要重复创建）：

```sh
# 以实际发行版的 useradd、nologin 路径为准。
sudo useradd --system --user-group --home-dir /opt/gogame --shell /usr/sbin/nologin gogame
sudo install -d -o gogame -g gogame /opt/gogame/app
sudo install -d -o root -g gogame -m 0750 /etc/gogame
```

上传产物后，确认项目文件归运行账号管理；环境文件填写完成后，可设置为 root:gogame、0640，避免将凭证公开给其他用户。以具备相应目录权限的部署账号在项目根目录安装生产依赖。将前文三个 YAML 模板应用到产物对应目录，替换占位符后再启动。

核对模板 User/Group、WorkingDirectory=/opt/gogame/app、EnvironmentFile=/etc/gogame/runtime.env 和 /usr/bin/node；使用 nvm 安装 Node 时，systemd 不会自动加载交互式 shell，必须填真实 Node 可执行文件绝对路径。可用 command -v node 查看。

模板经 scripts/prod.js 启动，统一强制 NODE_ENV=production、GOGAME_ENV=prod、IS_DEV=0。不要使用 PM2 cluster 再套一层 client-web cluster；如用其他管理器，client-web 只托管一份主进程即可。

第一次部署：

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now gogame@game-server
# 确认 game-server 加载成功后再启动比赛调度。
sudo systemctl enable --now gogame@match
sudo systemctl enable --now gogame@client-web
sudo systemctl enable --now gogame@hall

sudo systemctl status gogame@game-server gogame@match gogame@client-web gogame@hall
```

每项确认日志与健康响应后再继续。systemd 显示 active 仅代表进程存在，不保证 handler 初始化成功或真实资金接口可用。服务初始化发生错误时可能保留 loading/旧 handler，必须检查日志。

查看日志：

```sh
sudo journalctl -u gogame@client-web -f
sudo journalctl -u gogame@hall -f
sudo journalctl -u gogame@game-server -f
sudo journalctl -u gogame@match -f
```

client-web 日志应出现 primary、worker ready 和共享端口。worker 异常退出会补位；同一位置连续快速失败 5 次停止服务并返回失败，由管理器记录/按策略恢复。持续失败时先查端口占用、配置和模块加载错误。

生产包中也可以在根目录分别执行 npm run game-server、npm run match、npm run client-web、npm run hall 用于排查；不要与 systemd 已运行的同名服务重复启动。源仓库对应的强制生产命令是 npm run prod:game-server 等。

## 8. 无域名的单 IP 测试环境

用单独的 [deploy/nginx-test.conf](deploy/nginx-test.conf)，不要和 production.conf 同时替换主配置。此模板不需要证书：

| 用途 | 测试对外地址 |
| --- | --- |
| 大厅 | http://172.21.211.219:10031 |
| 游戏资源 | http://172.21.211.219:10032 |
| 游戏连接 | ws://172.21.211.219:10033 |
| 百人连接 | ws://172.21.211.219:10033/hundred |
| 比赛管理 | http://172.21.211.219:10031/admin |

模板假设 nginx 在 172.21.211.219，四个 Node 服务在当前开发机 172.21.211.216。更换机器时修改 IP。Node 配置 server_ip 需为 0.0.0.0 或可达内网 IP；不要套用同机生产模板中的 127.0.0.1 监听。

修改源仓库 hall/config.yaml 的 public：

```yaml
public:
  hall_url: http://172.21.211.219:10031
  client_url: http://172.21.211.219:10032
  game_ws_url: ws://172.21.211.219:10033
  hundred_ws_url: ws://172.21.211.219:10033/hundred
```

内部 client_web_port 仍为 4000，game-server 为 11041，hall 为 11042，match 为 11040。同一个 IP 使用三个外部端口，不用 hosts 或多个域名。Windows nginx 需将模板 mime.types 和日志路径改成其安装目录的路径，Windows Node 启动可以沿用 npm run dev。

env: dev 使用内存模拟；它验证页面、资源和连接链路，不验证真实生产资金。正式接口联调应使用隔离的 prod 环境及真实测试凭证。内存开发模式不要暴露到公网。

以上是供你在部署环境应用的配置，本次文档整理不自动改动当前工作区的运行地址，也不重启已运行服务。

## 9. 验证顺序

### 9.1 检查内部服务

同机生产部署在 Node 机器执行：

```sh
curl -fsS http://127.0.0.1:11042/health
curl -fsS http://127.0.0.1:11040/health
curl -fsS http://127.0.0.1:11041/
curl -I http://127.0.0.1:4000/2.0.1279/
```

前三项 JSON 应能确认正确 service、env=prod 和已加载的业务版本；client-web 首页应为 200。资源版本如果不是 2.0.1279，使用实际 static/client 版本。HTTP 健康检查不代表资金接口验证已完成。

### 9.2 检查 nginx 和 TLS

```sh
curl -I https://game.example.com/health
curl -I https://game.example.com:8444/2.0.1279/
curl -I https://game.example.com:8444/2.0.1279/js/index.js
curl -I https://game.example.com/admin
```

应返回正常页面/资源状态且证书验证成功。域名还未切 DNS 时可以在部署机用 curl --resolve 指定目标 IP；不要把永久关闭证书验证当作上线配置。

### 9.3 实际玩家链路

通过真实 open-api 签发指向公开大厅的链接。典型入口结构：

```text
https://game.example.com/21/0?userId=真实ID&userToken=真实凭证&openId=真实ID&v=2.0.1279
```

若 open-api 使用 token 字段，大厅按现有规则规范为 userToken。生产凭证必须真实，不能使用 dev。更新 open-api/平台的大厅链接配置，不要只修改本项目 public 而让平台继续签发旧 IP/端口的链接。

浏览器开发者工具确认：大厅请求走 443；iframe 和资源走同域名 8444；游戏内 API 走配置的大厅地址；进房 WebSocket 走 wss 的 8445，第二条连接使用 /hundred，握手返回 101。点击进游戏、返回大厅、再次进入都要验证。

再验证余额、下注、结算、历史、报名、退赛、比赛调度和管理代理隔离。后端 Go overlay 测试、Node 单测和“首页能开”都不能替代这一步。

### 9.4 管理端验证

访问 /admin，使用 match 管理凭证。无凭证访问 /admin/v1/matches 应被拒绝；平台操作需选择实际代理，代理令牌不得越权读取其他代理。

模板没有把 match 的 /internal/v1/tournament 暴露为公开入口，hall 仍通过 match_server 内部调用。

## 10. 发布、热更新和回滚

服务进程常驻，业务模块源码变化由原有 watcher 热替换；client-web 每个 worker 独立执行相同机制。不要把每次发布都写成 systemctl restart 全部服务，game-server 重启会丢失进程内房间/连接和比赛关联状态。

| 变更 | 生效方式 |
| --- | --- |
| 已被监听的业务 JS | 在稳定部署目录原子替换审核过的文件，检查 hot loaded 日志及功能 |
| 原始资源 | 发布匹配版本，核对 hall/client-web 版本选择和浏览器缓存 |
| YAML、public、环境变量、监听端口、worker 数 | 启动时读取，按维护窗口或有状态服务迁移流程处理；不承诺热生效 |
| boot.js、热加载器、依赖版本 | 属于启动基础设施升级，需规划维护/迁移，不等同于业务热更新 |
| nginx 配置、证书 | nginx -t 成功后 reload；已建立 WebSocket 不会自动迁移到新上游 |

保留部署前配置、代码版本和资源版本。热更新使用稳定的 /opt/gogame/app 目录；不要仅切换软链接后假设旧进程的 watcher 自动跟随新目录，不要用 rsync --delete 把在线依赖短暂删除。

业务回滚将对应审核过的旧源码原子还原，再观察热加载日志；nginx 回滚恢复旧配置后先 -t 再 reload。已经提交的资金/比赛数据不会因为代码回滚自动撤销，不能重放扣款或派奖。无法保持状态兼容的变更安排专门维护步骤。

本项目现有 YAML 不具备统一动态重载能力；“修改 public 后页面刷新”只有在运行进程已加载新配置后才成立。

## 11. 常见故障

| 表现 | 优先检查 |
| --- | --- |
| nginx 502 | upstream 的 IP、端口、Node 监听地址、进程和内部网络 |
| client-web 503/loading | 模块是否加载失败、static 是否完整，查看每个 worker 日志 |
| 页面 404 | URL 是否带真实版本、产物层级、是否误用“直接静态 nginx”旧配置 |
| 重定向过多 | nginx 是否额外添加了 / 与版本目录互跳；本方案资源请求直接交给 client-web |
| iframe 仍指向 www.* | hall 是否已加载 public.client_url、新版 _app 响应是否被旧缓存替代 |
| WSS 失败 | 8445 网络、证书、Upgrade/Connection、public URL、/hundred 路径保留 |
| API 仍访问 localhost 或旧地址 | hall/client-web 是否读取同一 hall/config.yaml，已打开页面是否刷新 |
| 比赛无法报名 | hall.match_server、match 日志、身份/付款和 data-center 接口 |
| 比赛无法开桌 | 两端 match_control_secret、一致的内部 game_server 和签名时钟 |
| finance 校验阻止启动 | 是否使用 build:prod 产物，是否误删完整现金玩法配置 |
| prod 余额/数据不可用 | gRPC 地址、存储 token、lottery 写入路由、后端协议/表结构是否真正部署 |
| 多个 worker 持续退出 | 端口是否被其他主进程占用、配置是否有效、依赖与资源是否齐全 |
