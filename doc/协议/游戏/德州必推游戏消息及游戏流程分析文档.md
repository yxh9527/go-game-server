| 字段 | 值 | 说明 |

## 4. 进入房间流程

客户端先调用大厅 `op=45`，然后发送 `1105 ROOM_LOGIN`：

```json
{
  "isAutoLogin": true,
  "userId": "<uid>",
  "openId": "<openId>",
  "userToken": "<token>",
  "version": "<client-version>",
  "cVersion": 20240607,
  "deviceId": "<deviceId>",
  "language": 1,
  "openHundredGame": false,
  "clubId": "<clubId>",
  "packetId": 5,
  "isApiLogin": true,
  "currency": "CNY",
  "plat": 4,
  "roomId": "<roomId>",
  "isInRoom": false
}
```

服务端用 `1205 ROOM_LOGIN` 返回服务端时间、俱乐部和汇率。主连接随后执行：

1. `2102 SEND_JOIN_ROOM`：申请进房。
2. `2219 DZPK_PUSH_WATCHGAME`：返回观战玩家。
3. `2201 ROOM_TYPE_RESULT`：返回 AOF 配置。
4. `2117/2220 SEND_GAME_SETTING/DZPK_PUSH_GAME_SETTING`：游戏设置。
5. `3178/3465 DZPK_FORCE_INSURANCE_CONF_REQ/RES`：读取保险设置，样本返回关闭。
6. `2200/2221 COMMON_SWITCH_REQ/RES`：通用开关。
7. `2111 LOGIN_ROOM`：正式进入房间。
8. `2206 ROOM_INFO`：同步座位、玩家、观众、局号和规则。

进入时 `ROOM_INFO.currentInning=775`，随后收到 `3260 NIUNIU_INNING_BEGIN_INFO` 且状态为 `DEAL_RIVER`，说明客户端是在恢复进行中的牌局，而不是从新局起点开始。

## 6. AOF 牌局流程

### 6.1 状态序列

```text
BET_PERFLOP
 -> DEAL_PERFLOP
 -> DEAL_FLOP
 -> BET_FLOP
 -> DEAL_TURN
 -> BET_TURN
 -> DEAL_RIVER
 -> BET_RIVER
 -> SETTLE
```

有些进入房间的日志从 `DEAL_RIVER` 开始，这是 `3260` 快照恢复，不是新局异常。

### 6.2 固定必推额度

典型 `3440 DZPK_ACTION_BET_PUSH`：

```json
{
  "uid": "<uid>",
  "currentBetScore": 100,
  "totalBetScore": 100,
  "operation": 12,
  "point": 223,
  "pot": 200
}
```

同一轮多名玩家的 `currentBetScore` 都是 `100`，底池从 `100`、`200`、`300` 递增，和 `aofBet=100` 直接对应。日志还出现 `operation=9` 且 `point=0` 的结果，表现为玩家将剩余分数投入或失去继续资格；操作中文名称仍应以客户端枚举为准。

### 6.3 发牌和底池

| 状态 | 消息 | 说明 |
| --- | --- | --- |
| `DEAL_PERFLOP` | `DZPK_DEAL_DI_PUSH` | 底牌已发，牌面可能隐藏 |
|  | `DZPK_PLAYER_DIPAI_PUSH` | 有权限时返回玩家底牌 |
| `DEAL_FLOP` | `DZPK_DEAL_FAN_PUSH` | 3 张翻牌 |
| `DEAL_TURN` | `DZPK_DEAL_ZHUANG_PUSH` | 1 张转牌 |
| `DEAL_RIVER` | `DZPK_DEAL_HE_PUSH` | 1 张河牌 |

`DZPK_BIANCHI_PUSH` 在本次 AOF 日志中反复返回 `[500]`，表示底池/边池状态更新。它是数组，不是带字段名的对象。

### 6.4 结算前亮牌

进入 `SETTLE` 后，服务端连续推送 `3441 DZPK_ACTION_SHOWCARD_PUSH`：

```json
{
  "uid": "<uid>",
  "cardTypeInfo": {
    "pokerEnumList": ["CLUB_3", "CLUB_4", "CLUB_J", "CLUB_Q", "CLUB_A"],
    "handCardList": [15,16,23,24,13],
    "cardTypeId": 6
  },
  "holeCardList": [24,15]
}
```

同一时间点会为多个参与者推送 `holeCardList`，这是 AOF 房间强制亮牌的表现，不应当解释为玩家逐个主动请求亮牌。

### 6.5 最终结算

`3432 DZPK_INNING_RESULT_PUSH` payload 是玩家数组：

```json
{
  "cardTypeInfo": {
    "pokerEnumList": ["CLUB_3", "CLUB_4", "CLUB_J", "CLUB_Q", "CLUB_A"],
    "handCardList": [15,16,23,24,13],
    "cardTypeId": 6
  },
  "xiaZhuData": 100,
  "insuranceBet": 0,
  "insuranceProfit": 0,
  "isWin": true,
  "uid": "<uid>",
  "score": 475,
  "point": 975,
  "handPais": [15,16,23,24,13],
  "pos": 0
}
```

`score` 是本局输赢分，`point` 是结算后的携带分，`xiaZhuData` 是 AOF 固定投入，`cardTypeInfo` 是完整牌型，`insuranceBet/insuranceProfit` 是保险字段。本次日志没有出现暴击字段或非零 `calamariScore`。

## 7. 补分、离座和退出

AOF 房间的 `carryMin=100`，日志中出现：

```json
{"uid":"<uid>","carryIn":100,"carryBalance":200,"state":true}
```

这是 `3230 CARRY_SCORE_RESULT`，表示补充 100 分成功。离开流程通常为：

1. `2110 SEND_LEVEL_OUT`：退出请求，payload 可能为 `undefined`。
2. `9212 GAME_POINT_UPDATE`：积分更新。
3. `3436 USER_STANDUP_ROOM`：用户离座。
4. `2205 USER_LEVEL_ROOM`：房间状态更新。
5. `6106 <game>EXIT`：辅助连接退出通知。

| 项目 | 普通德州 | 暴击德州 | AOF 必推 |
| --- | --- | --- | --- |
| 配置 ID | 常见 `70/1921` | `1921` | `1927` |
| `playMode` | `0/1/3` 等 | `3` | `9` |
| `smallBlind/bigBlind` | 视房间而定 | 样本 `10/20` | `100/200` |
| `initialBet` | 通常有初始下注 | `20` | `0` |
| `aofBet` | 通常没有 | 没有 | `100` |
| `criticalFlag` | `false` | `true` | `false` |
| `straddle` | 可选 | 样本关闭 | `true` |
| 亮牌 | 按场景 | 强制展示配置 | `SETTLE` 前连续 `3441` 全员亮牌 |
| 动作 | 常规 `DZPK_SEND_ACTION` | 常规动作和保险 | 主要看见服务端固定 `3440` |

## 9. 实现建议

1. 以 `ROOM_TYPE_RESULT`/`ROOM_INFO` 的 `playMode=9`、`gameRoomConfigId=1927`、`aofBet=100` 识别 AOF，不使用入口 `playMode=8` 作为最终依据。
2. 把 `3440` 保存为固定投入、全下或退出的服务端结果事件。
3. 对 `operation=12` 保留原始数值，并结合 `aofBet` 解释为固定投入；`operation=9` 的精确名称需从客户端枚举确认。
4. 把 `3441` 作为系统结算亮牌事件，不要当成普通玩家主动操作。
5. 把 `3434` 作为数组型底池/边池事件处理。
6. 进入房间时先处理 `3260` 快照，因为可能从 `DEAL_RIVER` 等中间阶段恢复。
7. `3263 BRNN_GAME_STATE_PUSH` 是主状态事件，名称中的 BRNN 是历史通用命名，不代表牛牛。
8. `3452` 只表示实时胜率/outs，最终输赢以 `3432` 为准。
9. 生产日志不要输出 token、openId、设备 ID、IP 编码值和完整用户资料。

## 10. 结论

本次日志确认的是 AOF 必推德州房间：

```text
gameName=AOF必推1
gameRoomConfigId=1927
playMode=9
aofBet=100
smallBlind=100
bigBlind=200
straddle=true
initialBet=0
criticalFlag=false
```

核心流程为：

```text
登录/进房
 -> 房间快照或进行中牌局恢复
 -> 固定 AOF 额度投入
 -> DEAL_PERFLOP
 -> DEAL_FLOP
 -> BET_FLOP
 -> DEAL_TURN
 -> BET_TURN
 -> DEAL_RIVER
 -> BET_RIVER
 -> SETTLE
 -> ACTION_SHOWCARD 全员亮牌
 -> INNING_RESULT 结算
```

与普通德州最大的差异是 `aofBet=100`、`initialBet=0`、`playMode=9`，以及结算前统一推送 `3441 DZPK_ACTION_SHOWCARD_PUSH`。本次没有独立的 `AOF_*` 消息，AOF 规则主要通过房间配置和通用 `DZPK_ACTION_BET_PUSH`、`DZPK_INNING_RESULT_PUSH` 表现。
