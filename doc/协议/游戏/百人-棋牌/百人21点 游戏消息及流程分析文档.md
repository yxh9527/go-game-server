## 5. 百人21点消息协议

### 5.1 状态和发牌

| 编号 | 消息 | 关键字段 | 作用 |
|---:|---|---|---|
| 6204 | GAME_STATE | state、roomType、inning、牌靴计数 | 通知阶段变化 |
| 6228 | MB_SNC_ROOM_STATE | state、inning、roomId、牌靴和走势 | 多房间状态同步 |
| 6212 | DEAL_CARDS_AND_ODDS | bankerCards、aCards、bCards、cCards、areaOdds | 发首张牌和本局赔率 |
| 6208 | SHOWDOWN_POKERS | showdownPokers、blackJackAreaInfos、showdownTypes | 公布完整牌面、点数和补牌过程 |
| 6229 | MB_ROOM_BET_SETTLE | roomId、showdownPokers、胜负区域、积分 | 完成一局结算 |

日志中可观察到同一局的 state=0、1、2、3、4、5、6、7。按时间和字段归纳：

- state=0：新局建立或上一局结束后的切换；
- state=1：发首张牌和赔率；
- state=2：开放下注；
- state=3：停止下注并开始发牌；
- state=4：展示最终牌面；
- state=5：结果展示过渡；
- state=6：更新总分、走势图和牌靴统计；
- state=7：本局收尾并准备下一局。

这是基于日志时序的解释，客户端应以服务端状态消息为准。

### 5.2 下注

6101 BET 请求：

~~~json
{
  "roomType": 60,
  "params": [{"areaId": 4, "total": 100}],
  "roomId": 11667073
}
~~~

| 编号 | 消息 | 方向 | 作用 |
|---:|---|---|---|
| 6101 | BET | 客户端 -> 服务端 | 向一个或多个区域下注 |
| 6201 | BET_RESPONSE | 服务端 -> 客户端 | 返回 code、points、myBets、myTotalBets、betAreaIds |
| 6202 | BET_BROADCAST | 服务端 -> 客户端 | 广播六个区域的总下注额 |
| 6210 | PLAYER_BALANCE_UPDATE | 服务端 -> 客户端 | 更新玩家积分 |

本次日志的下注返回：

~~~json
{
  "points": 8607,
  "roomType": 60,
  "code": 0,
  "myBets": [{"areaId": 4, "total": 100}],
  "myTotalBets": [{"areaId": 4, "total": 100}],
  "betAreaIds": [4],
  "roomId": 11667073
}
~~~

code=0 表示请求成功。BET_BROADCAST 的 allPlayerBets 按 areaId=1..6 返回全体下注总额，playerBets=[] 不表示区域没有下注。下注赔率应以本局 6212 或房间快照的 areaOdds 为准。

  "points": -1,

blackJackAreaInfos 的字段含义：

- area：banker、a、b、c 四手牌的标识；
- initialCardType、cardType：服务端牌型编号；
- finalCards：该手最终牌数组，长度由是否补牌决定；
- firstPoint、firstPointAlt：初始点数及 A 的备用点数；
- finalPoint：补牌完成后的最终点数；
- supplySteps：每次补牌后的点数、备用点数和牌型；
- showdownTypes：四手最终牌型编号。

日志显示最终牌数组长度可以不同，例如 a、c 两张停牌，b 三张，banker 四张。不能按固定五张牌模型解析。

winningAreas、tieAreas、lostAreas 是六个下注区域的结果，winType 是全局结果类型编号，points 和 realScore 用于玩家积分结算。

## 6. 一局游戏流程

1. HTTP op=38 查询 roomType=60 的百人21点配置。
2. HTTP op=45 选择 gameType=60、playMode=0。
3. RoomSocket-222 发送 ROOM_LOGIN，建立百人会话。
4. 执行 EXIT -> ENTER，并注册多个百人房间。
5. ENTER_RESPONSE 返回当前房间积分、牌靴进度、赔率和首张牌。
6. state=0/1 阶段建立新局，6212 DEAL_CARDS_AND_ODDS 给庄家、a、b、c 各发一张明牌，另一张暂为 -1。
7. state=2 开放下注，客户端发送 BET，服务端以 BET_RESPONSE 确认，期间持续广播各区域总下注额。
8. state=3 停止下注并按规则补牌。补牌过程不通过玩家操作消息下发，而是在结算消息的 supplySteps 中呈现。
9. state=4 发送 SHOWDOWN_POKERS，公开四手完整牌面、点数、牌型和区域胜负。
10. state=5/6/7 更新积分、走势图、牌靴统计和下一局准备。
11. 新局 state=0/1 到来后，按新的 inning 重复。

## 7. 与普通21点房间的区别

## 8. 实现建议和限制

- 使用 roomType + roomId + inning 作为一局唯一键。
- 牌数组长度不固定，按 finalCards 实际长度解析。
- 初始牌中的 -1 保留为未知牌，不能参与点数计算。
- A 的 firstPointAlt 和 pointAlt 必须保留，不能只保留一个点数。
- 6212 到来时覆盖本局 areaOdds；BET 前检查 state=2、countDown、points 和 roomId。
- 结算时先处理 blackJackAreaInfos 和 showdownPokers，再处理 winningAreas、tieAreas、lostAreas 与积分。
- 牌靴计数只作为服务端进度展示，不要在客户端自行推演剩余牌。
- ROOM_LOGIN 含用户令牌，正式调试日志必须脱敏。
