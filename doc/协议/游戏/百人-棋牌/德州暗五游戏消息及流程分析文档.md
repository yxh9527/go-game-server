### 网页宿主与双连接复核（2026-10-29）

所选列表项为 roomType=50，但原版大厅 op=45 的响应会打开有效的普通德州宿主（roomType=19），并带 openHundredGame=true。客户端保留所选 playMode 供 Bairen 使用。Bairen 是 gameHoldem 上的原生 overlay，没有独立场景，不能强制加载 Bairen/brdz，也不能把类型50配置当作普通德州配置。

RoomSocket-111 执行1105登录、2102以旁观者进入宿主、2201接收普通德州配置（conf.hundredSwitch=true，顶层openHundredGame=true）。RoomSocket-222用宿主roomId独立1105登录，随后直接发送6105选择百人玩法，不需要2102。6205响应后，6123注册类型50并通过6224/6227取得所有启用的五种玩法。

原版 SocketMgr 仅在 domain 与 hundredDomain 不同时建立第二条连接。dev 用 www.localhost:<port> 和 hundred.localhost:<port> 共用既有大厅 WS 代理；生产须配置两个有效公网地址，可由 Nginx 反代到同一常驻 game-server，不依赖本地 client-web 补丁。百人订阅独立保存，不覆盖普通桌身份。多房6228按roomId分发；6204/6208/6212等主百人桌事件仅发送给选中该桌的连接。

原始抓包与当前静态客户端共同确认：快照 hundredParams.betAreaOdds[id] 为 {id,odds}，发牌6212中的areaOdds[id]则为数字。ways 包含1/2/3三个{max,ways}对象，max分别为100/33/5，不是直接对象数组。6208开牌数据须先于6204/state=4，客户端在状态变化时立即读取已初始化的开牌模型。入局快照在开牌及结算阶段还必须包含 winningAreas/tieAreas/lostAreas，不能只返回牌面。

本地调试页面必须等待原版 common/loading/over 通知后加载宿主场景，不能在固定延时后抢先切换；否则 Bairen 尚未完成 prefab 初始化，进房仍会失败。补丁只放 cache/client-web，不修改 static 原始资源。服务端热更新依赖链必须将同一版本传递到百人引擎及 messages.js；静态复用启动时的旧消息表可能使新增消息编号变成 undefined，编码后出现消息号0，即使新进程单测正常也会丢失发牌与结算推送。

浏览器回归脚本为 test/browser/check-hundred-holdem-entry.mjs，支持 --mode=1..5，从原版大厅进入，验证双连接、五玩法注册、下注、结算、下一局和返回大厅。commandSetChipValue 使用显示金额，6101.params[].total、6201.points 和 6229.points/realScore 使用积分；资金核对必须使用实际发送的下注积分，不能将显示金额直接与积分相加。结算后余额应等于下注后余额 + 本局已扣下注总额 + realScore。

### 百人机器人下注（2026-10-29）

百人德州五种模式通过 HundredGame 复用 core/robot.js 的公共调度，经典百家乐使用相同调度。进入房间后，即使真人只旁观而不投注，也会收到机器人经正常 acceptBet/placeBet 生成的 6202 广播；allPlayerBets 为各下注区的全桌累计金额，数值包含机器人与真人已接受的下注。机器人分散时间、区域和筹码金额行动，不直接修改广播数值，不读取尚未公开的牌面或已生成的胜负结果。

默认 6 名初始机器人、10 名目标机器人、24 名上限，可在游戏 config.hundredRobotBehavior 或房间 cfg.robot_behavior 中调整；enabled=false 可关闭新增下注，已有下注仍须完成结算。initialRobots/targetRobots/maxRobots 控制数量，joinProbability/leaveProbability/participationProbability 控制行为概率，betMinMs/betMaxMs/maxBetsPerRound 控制频率，bankrollBets 控制每个新身份的初始最小下注份数。账户、冷却和下注计划随房间保存，热更新不补充资金。

机器人与真人使用相同合法金额校验和输赢计算，模拟资金由公共 hundredWalletContext 隔离，不调用真人余额 RPC。机器人下注只进入全桌累计值，不能加入真人自己的 myBets/ownBets，也不能改变未下注真人的 realScore。对应 6229 仍是每名真人各自的一份结算；热更新不能丢失投注归属、重置模拟余额或重复结算。test/game-server/core/hundred-robot.test.js 覆盖五模式及百家乐，浏览器回归在真人首次下注前验证自动下注广播。

## 4. 百人状态消息

### 4.1 MB_SNC_ROOM_STATE（6228）

6228 是单个百人房间的增量状态消息。日志中观察到的状态上下文：

原版 `BairenMultyBetModel.onMbSncRoomState` 会先校验 `customData == module.customData`，百人棋牌侧为 **2**。因此 6228 必须携带 `customData: 2`；只传 state/countDown 而缺少该上下文字段，客户端会忽略整个状态更新，卡片停在注册时的旧状态，倒计时走到 0 后不再恢复。6226 成功及失败回执也经过相同校验，必须保留该字段。6227 快照与 6229 结算已有相同上下文。

`countDown` 为当前阶段剩余**毫秒**，从房间阶段截止时间计算；重新注册/重连不得重置阶段时钟。原版百人棋牌小卡片初次恢复使用 `floor(countDown / 1000)`，收到增量下注状态则使用 `BRMBDef.DEFAULT_BRQP_COUNT_DOWN = 20` 秒，因此服务端下注阶段同步为 20 秒。热更新后从下一次进入下注阶段采用新时长，保留当前手牌、下注、余额及正在运行的阶段。

| state | 日志上下文 | 说明 |
| ---: | --- | --- |
| 0 | 仅有 inning、roomId、cardColor | 空闲或新局等待 |
| 1 | 带 dealPokers、areaOdds | 发牌和下注准备 |
| 2 | 带 areaOdds、totalBetsByArea | 下注阶段 |
| 3 | 状态转换或等待下一阶段 | 中间过渡 |
| 4 | 带 showdownPokers、showdownTypes | 开牌结果展示 |
| 5 | 结算过渡 | 从开牌到结算 |
| 6 | 带 systemTodayTotalScore、systemInningScore、ways | 结算统计 |
| 7 | 本局结束或结果确认 | 进入下一局前 |

以上是日志上下文推断，完整枚举仍需结合前端常量确认。

### 4.4 原版牌局回顾（6121/6221、6122/6222）

原版 `BairenHistoryModel` 经百人独立连接发送两类请求，不走普通德州的 3167/3446 或大厅 HTTP op=46。

| 方向 | 消息 | 原版字段 |
| --- | --- | --- |
| 请求列表 | 6121 REQUEST_100_RECORD | `{roomType:50, roomId}` |
| 返回列表 | 6221 RETURN_100_RECORD | `{gameRoomId, list:[已结算局号…]}` |
| 请求详情 | 6122 REQUEST_ONE_RECORD | `{gameRoomId, currInning}`，不带 roomType |
| 返回详情 | 6222 RETURN_ONE_RECORD | `{gameRoomId, currInning, showdownPokers, showdownTypes, winAreaIds, lostAreaIds, tieAreaIds, betDetailTableMap}` |

列表按局号升序排列，客户端默认取最后一局；上一局/下一局及首页/末页按此数组索引请求详情。详情牌面为本局已结算的 `{banker:[2张], player:[2张], board:[5张]}`，牌型也是 banker/player/board 三键，不能用发牌阶段的遮罩或下一局房间对象代替。

`betDetailTableMap` 只包含请求玩家本人在本局实际下注的区域，区域键对应 `{areaId, betScore, realScore, score, tax, odds}`。betScore 是本金积分，realScore 为本区域实际净盈亏，score 为本金加净盈亏；当前实现未收税，tax 为 0。无下注旁观者返回空 map，原版显示“未下注”，仍展示其有权查看的本局牌面。所有金额与 6229 本人结算一致，不从当前钱包余额倒推。

本地开发实现位于 `cache/game-server/hundred-holdem-history.js`，每次真实结算后冻结牌面和个人结果，保存于常驻房间，热更新不清空。只保留最近 100 局且八小时过期；只有本局参与下注或当时订阅旁观的用户可查询。查询按可信代理、百人游戏、实际房号和用户隔离，退出后禁止继续请求；不存在或过期的详情仅刷新授权列表，不能返回半截牌面对象导致客户端异常。修复前未保存的旧局无法还原，修复后完成的牌局开始累积。

正式环境不导入该开发内存模块；正式历史仍须接入既有 data-center 的 ES 查询和 Redis 缓存，当前未完成百人回顾的正式数据对接，不能把本地回顾宣称为正式存储功能。

## 8. 百人牌局流程

~~~text
ROOM_LOGIN(1105/1205, openHundredGame=true)
 -> ENTER(6105, roomType=50, playMode=1)
 -> MB_REG_ROOMS_REQ(6123)
 -> MB_REG_ROOMS_RES(6224)
 -> MB_REGED_ROOM_INFOS(6227)
 -> MB_SNC_ROOM_STATE(6228, state=1/2)
 -> DEAL_CARDS_AND_ODDS(6212)
 -> MB_SNC_ROOM_STATE(6228, state=4)
 -> MB_ROOM_BET_SETTLE(6229)
 -> GAME_STATE(6204, state=6/7)
 -> MB_SNC_ROOM_STATE(6228, state=0)
 -> 下一局
~~~

日志同时展示多个 roomId，因此每个 roomId 都可能处于不同 state。客户端应按 roomId 和 inning 维护状态。

## 9. 下注协议边界

本日志中没有看到明确的 RoomSocket-222 百人下注上行消息。RoomSocket-111 中的 DZPK_ACTION_BET_PUSH、DZPK_OPERATION_PLAYER_PUSH 属于常规德州扑克桌，不是暗五公牌的下注确认。

因此可以确认：

1. 6227、6228、6212、6229 是百人房间的下行协议；
2. 下注区为数字 1–7；
3. 下注金额和中奖区会在 6227/6229 中体现；
4. 本日志不足以确认百人下注请求的消息编号和参数格式。

~~~text
MB_UNREG_ROOMS_REQ(6124)
~~~

## 14. 结论

德州暗五公牌百人协议的识别条件和核心链路为：

~~~text
roomType=50
gameRoomConfigId=100
gameName=暗五公牌(底注1)
playMode=1

ENTER(6105)
 -> MB_REG_ROOMS_REQ(6123)
 -> MB_REG_ROOMS_RES(6224)
 -> MB_REGED_ROOM_INFOS(6227)
 -> MB_SNC_ROOM_STATE(6228)
 -> DEAL_CARDS_AND_ODDS(6212)
 -> GAME_STATE(6204)
 -> MB_ROOM_BET_SETTLE(6229)
 -> PLAYER_NUM_CHANGE(6207)
 -> MB_UNREG_ROOMS_REQ/RES(6124/6225)
 -> EXIT(6106)
~~~

实现时应以 roomType=50 和 hundredParams.gameRoomConfigId=100 识别暗五公牌，使用 roomId + inning 管理多桌和局号，以 6227 保存桌面快照，以 6212 保存牌面赔率，以 6229 保存中奖区和最终积分。
