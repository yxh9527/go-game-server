## 4. 百人看二张消息协议

### 4.1 房间快照

6205 ENTER_RESPONSE 和 6227 MB_REGED_ROOM_INFOS 主要字段：

- roomType、playMode、roomId、inning：玩法、档位、房间和局号；
- state、countDown：百人房间阶段和倒计时；
- playerNum、points：在线人数和玩家积分；
- totalBetsByArea：六个下注区域的累计金额；
- dealPokers/showdownPokers：初始公开牌或结算牌；
- areaOdds：本局六个区域赔率；
- ways、aWinCount、bWinCount、cWinCount：走势图和三门历史统计；
- hundredParams：玩法名称、赔率和单人最大下注额。

例如目标房间的快照带有 state=2、countDown=16657、points=10307，并且四手牌各有两个有效牌值。

### 4.2 状态和发牌

| 编号 | 消息 | 关键字段 | 作用 |
|---:|---|---|---|
| 6204 | GAME_STATE | state、roomType、inning、cardColor | 通知百人局阶段变化 |
| 6228 | MB_SNC_ROOM_STATE | state、inning、roomId、areaOdds、dealPokers/showdownPokers | 同步多个房间状态 |
| 6212 | DEAL_CARDS_AND_ODDS | cardColor、banker、a、b、c、areaOdds、inning、playMode | 推送看二张阶段的两张公开牌和赔率 |
| 6208 | SHOWDOWN_POKERS | showdownPokers、showdownTypes、ways、胜负区域 | 推送完整牌面展示 |
| 6229 | MB_ROOM_BET_SETTLE | roomId、showdownPokers、showdownTypes、winningAreas、lostAreas | 完整结算并返回积分变化 |

日志中同一房间可以观察到 state=0、1、2、3、4、5、6、7。按前后字段推断：

1. state=0：上一局结束后的等待或换局；
2. state=1：发出两张明牌和本局赔率；
3. state=2：开放下注；
4. state=3：停止下注或进入开牌过渡；
5. state=4：完整牌面展示和结算；
6. state=5/6/7：结算统计、结果同步和下一局切换。

数值含义应以服务端状态为准，客户端不应以固定秒数代替状态消息。

### 4.3 下注协议

客户端 6101 BET 的日志结构为：

~~~json
{
  "params": [{"areaId": 1, "total": 100}],
  "roomType": 52,
  "roomId": 22697429
}
~~~

| 编号 | 消息 | 方向 | 作用 |
|---:|---|---|---|
| 6101 | BET | 客户端 -> 服务端 | 向一个或多个区域下注 |
| 6201 | BET_RESPONSE | 服务端 -> 客户端 | 返回 code、points、myBets、myTotalBets、betAreaIds |
| 6202 | BET_BROADCAST | 服务端 -> 客户端 | 广播六个区域总下注额 |
| 6210 | PLAYER_BALANCE_UPDATE | 服务端 -> 客户端 | 更新玩家积分 |
| 6207 | PLAYER_NUM_CHANGE | 服务端 -> 客户端 | 更新房间人数 |

BET_RESPONSE.code=0 表示本次成功。myBets 是本局个人下注，myTotalBets 是累计下注；BET_BROADCAST 中 allPlayerBets 按 areaId=1..6 返回全体玩家区域总额。playerBets=[] 只表示当前没有可展示的个人明细，不表示区域无人下注。

## 5. 游戏流程

### 5.1 百人看二张标准流程

1. HTTP op=38 查询 roomType=52 的档位和人数。
2. 客户端选择 playMode=3，进入 RoomSocket-222。
3. 发送 ROOM_LOGIN，建立百人会话。
4. 执行 EXIT -> ENTER -> MB_REG_ROOMS_REQ，注册同类型多房间。
5. 接收 ENTER_RESPONSE 和 MB_REGED_ROOM_INFOS，初始化房间、积分、局号、赔率和两张公开牌。
6. 当前房间进入 state=1 后发送 DEAL_CARDS_AND_ODDS；随后进入 state=2 开放下注。
7. 客户端发送 BET，使用 BET_RESPONSE 确认，并持续接收 BET_BROADCAST。
8. state=3 后停止接受下注；服务端发送 SHOWDOWN_POKERS 或 MB_ROOM_BET_SETTLE，补齐每手第三至第五张牌。
9. 客户端按 winningAreas、tieAreas、lostAreas 更新结果，处理 points/realScore，刷新走势图。
10. 收到 state=0 或下一局 state=1 后，按新的 roomId、inning 重复流程。

### 5.2 与同日志普通抢庄牛牛的区别

RoomSocket-111 的 ROOM_TYPE_RESULT 是 roomType=24、roomType=qznn、gameName=看四张抢庄牛牛(底注0.1)、seeCardNo=4。其状态名为 DEAL_PERFLOP、GRAB_BANKER、CONFIRM_BANKER、BANKER_SELECT、BANKER_SHOW、XIAN_RAISE、RUBBING_CARDS、SETTLE，消息包括 QZNN_Grab_PUSH、QZNN_BankerAnm、QZNN_BetResult_PUSH、QZNN_ShowCard_PUSH 和 QZNN_Settle_PUSH。

这套有座位抢庄协议和百人看二张的 BET、DEAL_CARDS_AND_ODDS、MB_ROOM_BET_SETTLE 不同。分析百人看二张时，应以 RoomSocket-222 的 roomType=52 和 playMode=3 为准。

## 6. 实现和校验建议

- 缓存键使用 roomType + roomId + inning，避免五个百人房间的状态互相覆盖。
- -1 必须保留为未知牌；只有五个位置均为有效值后才进行完整牌型展示。
- areaOdds 可能每局变化，收到 6212 或 6228 时应覆盖旧赔率。
- 下注按钮仅在 state=2 且倒计时有效时开放；提交时校验 points、roomId 和 areaId。
- 收到 BET_RESPONSE 非零 code 时记录服务端错误，不要盲目重复发送。
- 结算先更新完整牌面和牌型，再处理胜负区域、积分和走势图。
- ways 数据量较大，应按房间和局号缓存，显示时按需截取。
- ROOM_LOGIN 中包含用户令牌，生产日志应脱敏。
