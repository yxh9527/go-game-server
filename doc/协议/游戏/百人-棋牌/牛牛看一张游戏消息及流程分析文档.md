# 牛牛看一张游戏消息及流程分析文档

## 2. 玩法识别与配置

大厅先通过 HTTP op=38 查询 gameType=1000、roomType=52 的百人房间列表。列表中同一房间类型按 playMode 分出多档，日志出现的配置编号包括 5205、5204、5203、5202、102。随后 HTTP op=45 请求参数明确带有：

~~~json
{
  "gameType": 52,
  "roomType": 52,
  "playMode": 4,
  "smallBlind": 0,
  "bigBlind": 0,
  "ante": 0,
  "seeCardNo": 0,
  "roomIndex": 0
}
~~~

百人 Socket 的 ENTER_RESPONSE 和 MB_REGED_ROOM_INFOS 将目标房间标识为：

~~~json
{
  "roomType": 52,
  "playMode": 4,
  "hundredParams": {
    "gameName": "百人牛牛看一张(底注1)",
    "gameRoomConfigId": 102,
    "betAreaOdds": {
      "1": {"id": 1, "odds": 1.00},
      "2": {"id": 2, "odds": 1.23},
      "3": {"id": 3, "odds": 1.02},
      "4": {"id": 4, "odds": 0.99},
      "5": {"id": 5, "odds": 0.80},
      "6": {"id": 6, "odds": 0.97}
    },
    "maxBet": 1000000000
  }
}
~~~

“看一张”的直接证据是初始牌面只返回每手牌数组的第一个元素，其余四个位置为 -1，例如：

~~~json
{
  "dealPokers": {
    "a": [7, -1, -1, -1, -1],
    "b": [27, -1, -1, -1, -1],
    "c": [18, -1, -1, -1, -1],
    "banker": [20, -1, -1, -1, -1]
  }
}
~~~

因此 -1 在该阶段表示尚未公开或尚未发出，不应当当作牌值参与牌型计算。结算消息 showdownPokers 才会给出四手完整五张牌。

## 3. 通信建立与多房间注册

### 3.1 登录

RoomSocket-222 先发送 1105 ROOM_LOGIN，字段包含用户标识、登录令牌、客户端版本、俱乐部和 openHundredGame=true。服务端以 1205 ROOM_LOGIN 返回 serverTime、clubId、exchangeRate、openHundredGame 等会话信息。

### 3.2 进入百人通道

| 编号 | 消息 | 方向 | 关键字段 |
|---:|---|---|---|
| 6106 | EXIT | 客户端 -> 服务端 | roomType=52，清理旧订阅 |
| 6105 | ENTER | 客户端 -> 服务端 | roomType=52、playMode=4 |
| 6123 | MB_REG_ROOMS_REQ | 客户端 -> 服务端 | mulRoomTypeList:[{roomType:52}]、customData:2 |
| 6205 | ENTER_RESPONSE | 服务端 -> 客户端 | 当前房间完整快照 |
| 6225 | MB_UNREG_ROOMS_RES | 服务端 -> 客户端 | 取消旧的多房间注册结果 |
| 6224 | MB_REG_ROOMS_RES | 服务端 -> 客户端 | 返回订阅到的五个 roomId |
| 6227 | MB_REGED_ROOM_INFOS | 服务端 -> 客户端 | 五个房间的批量状态快照 |

本次批量注册返回的房间编号为 48719594、41532512、22697429、43852513、33215787。客户端因此可以在一条 WebSocket 上同时显示多个百人房间；后续每条消息仍用 roomId 区分具体房间。

## 4. 百人牛牛看一张消息协议

### 4.1 房间快照

6205 ENTER_RESPONSE 和 6227 MB_REGED_ROOM_INFOS 的一条房间记录包含：

- roomType、playMode、roomId、inning：玩法、档位、房间和局号；
- state、countDown：当前阶段和倒计时；
- playerNum、points：在线人数和当前玩家积分；
- totalBetsByArea：区域 1 到 6 的累计下注额；
- dealPokers/showdownPokers：当前公开牌或已结算牌；
- areaOdds：区域赔率；
- ways：路单统计，ways.1 是最近结果序列，ways.2 是走势组合，aWinCount、bWinCount、cWinCount 是三门统计；
- hundredParams：玩法名称、赔率和单人最大下注额。

roomInfos 中的 state 是快照状态，不能直接等同于 GAME_STATE 的所有阶段。恢复页面时应以同一房间最新消息和 inning 为准。

### 4.2 状态与发牌

| 编号 | 消息 | 关键字段 | 作用 |
|---:|---|---|---|
| 6204 | GAME_STATE | state、roomType、inning、cardColor | 百人局阶段变化 |
| 6228 | MB_SNC_ROOM_STATE | state、inning、roomId、areaOdds、dealPokers/showdownPokers | 多房间状态同步 |
| 6212 | DEAL_CARDS_AND_ODDS | cardColor、banker、a、b、c、areaOdds、inning、playMode | 发出看一张阶段的首张牌及本局赔率 |
| 6208 | SHOWDOWN_POKERS | showdownPokers、showdownTypes、ways、winningAreas、lostAreas | 公开完整牌面和结果 |

日志中可见的百人状态序列包括：

state=0（新局/等待） -> state=1（发牌和赔率准备） -> state=2（下注阶段） -> state=3（停止下注或开牌过渡） -> state=4（结算展示） -> state=5/6/7（结算后统计、切换或下一局准备）。

该数值含义是根据同一 inning 的前后消息推断的，客户端应优先按服务端状态驱动，不要依赖固定延迟。

### 4.3 下注

客户端下注：

~~~json
{
  "params": [{"areaId": 1, "total": 100}],
  "roomType": 52,
  "roomId": 43852513
}
~~~

| 编号 | 消息 | 方向 | 作用 |
|---:|---|---|---|
| 6101 | BET | 客户端 -> 服务端 | 提交一个或多个区域下注 |
| 6201 | BET_RESPONSE | 服务端 -> 客户端 | 返回 code、points、myBets、myTotalBets、betAreaIds |
| 6202 | BET_BROADCAST | 服务端 -> 客户端 | 广播六个区域的累计下注额 |
| 6210 | PLAYER_BALANCE_UPDATE | 服务端 -> 客户端 | 更新玩家余额，例如 points=10307 |

BET_RESPONSE.code=0 表示本次请求成功。myBets 是当前局本次/当前下注明细，myTotalBets 是累计明细；allPlayerBets 在日志中持续返回 areaId=1..6 的总额。日志里的 playerBets=[] 表示当前没有需要展示的其他玩家明细，并不表示区域总下注为零。

### 4.4 结算

6229 MB_ROOM_BET_SETTLE 是一局最完整的结算消息，结构如下：

~~~json
{
  "roomType": 52,
  "roomId": 41532512,
  "showdownPokers": {
    "a": [26, 18, 47, 44, 8],
    "b": [38, 19, 3, 7, 48],
    "c": [40, 45, 51, 31, 41],
    "banker": [29, 17, 12, 10, 32]
  },
  "showdownTypes": {"a": 0, "b": 0, "c": 8, "banker": 0},
  "winningAreas": [2, 3, 4],
  "tieAreas": [],
  "lostAreas": [1, 5, 6],
  "points": -1,
  "realScore": 0,
  "customData": 2
}
~~~

- a、b、c、banker 是四手牌，数组顺序为五张牌；
- showdownTypes 是服务端牌型编号，具体编号到中文牌型的完整映射未在本日志中给出；
- winningAreas、tieAreas、lostAreas 是六个下注区域的开奖结果；
- areaWinningScores（部分消息出现）给出玩家命中的区域收益；
- points 是结算后的玩家积分字段，realScore 是本次实际变动；
- ways 和胜负统计用于走势图，不是下注请求的必要字段。

例如日志中出现 winningAreas=[1,5,6]、lostAreas=[2,4,6] 等结果，说明每个房间独立结算，不能把不同 roomId 的牌面或区域结果拼接到一起。

## 5. 一局游戏流程

### 5.1 百人看一张流程

1. HTTP op=38 获取 roomType=52 的房间列表和档位人数。
2. HTTP op=45 选择 playMode=4，取得百人域名和房间入口。
3. ROOM_LOGIN 建立 RoomSocket-222 会话。
4. EXIT -> ENTER -> MB_REG_ROOMS_REQ 清理并注册五个同类型房间。
5. ENTER_RESPONSE/MB_REGED_ROOM_INFOS 返回当前积分、局号、倒计时、赔率和首张可见牌。
6. 收到 6204/6228 state=2 后进入下注期，客户端发送 BET，并通过 BET_RESPONSE 确认。
7. BET_BROADCAST 持续更新六个区域的总下注额。
8. 状态进入 3/4 后停止下注，服务端发送完整 showdownPokers、showdownTypes 和胜负区域。
9. 客户端更新积分、走势图和历史结果，收到下一局 state=0/1 后重复流程。

### 5.2 与日志中普通抢庄牛牛的区别

同一日志的 RoomSocket-111 连接收到 ROOM_TYPE_RESULT：

- roomType=24；
- roomType=qznn；
- gameName=看四张抢庄牛牛(底注0.1)；
- seeCardNo=4；
- 状态名为 DEAL_PERFLOP、GRAB_BANKER、CONFIRM_BANKER、BANKER_SELECT、BANKER_SHOW、XIAN_RAISE、RUBBING_CARDS、SETTLE。

这条通道是有座位玩家的抢庄牛牛流程，消息包括 QZNN_Grab_PUSH、QZNN_BankerAnm、QZNN_BetResult_PUSH、QZNN_ShowCard_PUSH、QZNN_Settle_PUSH。它和百人看一张的 BET、DEAL_CARDS_AND_ODDS、MB_ROOM_BET_SETTLE 协议属于两套业务，不能以 QZNN_Settle_PUSH 代替百人结算。

## 6. 字段与实现建议

- 以 roomType、roomId、inning 作为一局唯一上下文；不要只用 roomType=52 做缓存键。
- 牌数组中的 -1 保留为“未公开/未知”，不要转换成有效牌。
- 下注按钮只在对应房间处于下注状态时可用；发送 BET 前检查 points、countDown、roomId。
- 收到 BET_RESPONSE.code 非零时保留服务端返回值并停止本次重试，避免重复下注。
- 结算时先处理 showdownPokers/showdownTypes，再处理 winningAreas/lostAreas 和积分，最后更新走势图。
- areaOdds 可能在每局发牌时变化，不能只在登录时读取。
- ways 数据量很大，建议按房间和玩法缓存，展示层按需截取。
- ROOM_LOGIN 日志带有用户令牌，生产环境应脱敏；文档和调试日志不应保存完整 token。
