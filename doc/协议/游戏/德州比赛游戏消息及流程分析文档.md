## 6. 比赛牌局流程

### 6.1 牌局循环


比赛牌局可能因玩家弃牌提前结束，不一定完整经过所有公共牌阶段。

### 6.2 比赛盲注和前注

### 6.3 下注和弃牌

服务端使用 `3440 DZPK_ACTION_BET_PUSH` 广播动作结果。比赛中可以看到：

- `operation=9`：投入剩余积分的全下类动作。
- `operation=1/2`：前注和盲注。
- `operation=4/7`：加注或跟注类动作。

示例：

比赛积分很高，金额字段均以比赛积分为单位，不应按普通现金桌的小盲比例解释。

## 7. 比赛特有流程

### 7.1 换桌/暂停

`20001 COMPETITION_PAUSE_TO_CHANGE_DESK` 表示比赛阶段可能暂停并换桌。比赛详情中的 `MTTRoomInfos` 保存分桌关系：

```json
[
  {"roomIndex":14,"roomId":66045320,"playerNums":4},
  {"roomIndex":18,"roomId":72672705,"playerNums":6}
]
```

实现时不能永久绑定第一次房间号。收到换桌消息后，应重新读取比赛桌上下文，并重新执行比赛房间登录流程。

### 7.2 盲注升级

`20009 COMPETITION_BLIND_UP` 是比赛状态机的核心消息之一。客户端应更新：

- 当前小盲、大盲、前注。
- 下一档盲注。
- 下一次升级倒计时。
- 当前盲注级别。
- `isStopIncrBlind` 是否停止升级。

盲注升级后，后续 `3261` 和 `3431` 会使用新的盲注值。

### 7.3 比赛积分和排名

比赛详情和 `MTTUserRanks` 提供分桌积分和排名数据。比赛结算中：

- `score` 表示本局输赢积分。
- `point` 表示结算后的比赛总积分。
- `currentPlayer/currentLivePlayer` 表示比赛人数和存活人数。
- `MTTRankPrices` 表示排名奖励百分比和金额。

比赛结束/淘汰后，可能需要回到大厅重新查询 `op=36` 或比赛状态接口，以获取最终排名、奖励和用户状态。

## 8. 与普通现金桌的差异

| 项目 | 普通现金桌 | 比赛桌（本日志） |
| --- | --- | --- |
| 入口 `roomType` | `19` | `101` |
| `isMtt` | `false` | `true` |
| `mttId` | `0` | `19619` |
| 房间税费 | 可能启用 | `taxType=0`、`taxPercent=0` |
| 保险 | 可能启用 | `openInsurance=false` |
| 盲注 | 房间固定 | 由 `20009` 动态升级 |
| 前注 | 普通配置 | 随盲注级别动态变化 |
| 携带分 | `carryMin/carryMax` | 比赛积分和分桌排名 |
| 房间切换 | 一般不换桌 | 可能出现 `20001` 换桌 |
| 结算 | 现金桌积分 | 比赛积分、排名和奖池 |

## 9. 实现建议

1. 以比赛详情的 `mttId`、`isMtt` 和 `roomType=101` 识别比赛房间。
2. 通过 `MTTRoomInfos` 维护分桌房间映射，不能把第一次房间号视为永久房间。
3. 把 `20009 COMPETITION_BLIND_UP` 作为比赛盲注状态的唯一服务端来源。
4. 收到 `20001 COMPETITION_PAUSE_TO_CHANGE_DESK` 后，停止当前房间状态处理并准备换桌重连。
5. 比赛房间的 `ROOM_TYPE_RESULT.roomType=19` 是牌局类型，外层 `SEND_JOIN_ROOM.roomType=101` 是比赛通道类型，两者都要保留。
6. 比赛积分使用整数大额数值，不能按普通现金桌的货币金额格式化。
7. `forceShowCard=true`、`openInsurance=false` 是本次比赛桌规则，应据此处理亮牌和保险 UI。
8. `DZPK_PUSH_BLOCKCHAIN_NOTIFY` 只需保存当前局号和证明摘要，完整证明字符串不应进入普通日志。
9. 生产日志需要脱敏 token、用户资料、IP 编码、比赛排行榜和房间域名。

### 11.1 单个玩家离座/淘汰

补充日志首先出现：

```json
{"roomId":66045320,"uid":"<uid>","type":3}
```

随后出现 `GAME_BF_CHANGE(state=false)`、用户离线和 `USER_STANDUP_ROOM`。这组消息表示用户离开比赛桌或被标记为离桌，不等同于整个比赛房间解散。服务端随后发送 `DZPK_PUSH_WATCHGAME`，刷新旁观列表。

建议状态转换：

```text
USER_LEVEL_ROOM(type=3)
  -> USER_ONLINE_CHANGE(state=false)
  -> USER_STANDUP_ROOM(uid)
  -> DZPK_PUSH_WATCHGAME
```

### 11.2 比赛继续和新玩家加入

比赛不会因为单个玩家离桌立即结束。补充日志中随后仍然出现：

- `JOIN_ROOM`：新玩家加入观战或比赛桌。
- `USER_ONLINE_CHANGE(state=true)`：新玩家在线。
- `GAME_TUOGUAN_ACTION`：托管状态同步。
- `COMPETITION_BLIND_UP`：比赛继续推进盲注级别。
- 后续 `BET_FRONT`、`BET_BLIND`、`DEAL_PERFLOP` 和 `SETTLE`：继续产生牌局。

因此 `USER_STANDUP_ROOM` 应理解为玩家级离桌事件，不能直接触发房间销毁。

### 11.3 重新加入和比赛房间失效

补充日志末尾在大厅轮询后，客户端再次发送：

```json
  "roomId": 66045320,
  "clubId": 127700,
  "isOb": true,

  "roomType": 101

```

服务端立即返回错误消息：

```json
{

```

日志随后出现：

```text

```

这组消息是“比赛分桌房间已不存在/已被回收”的明确证据。它可能由比赛桌结束、换桌后的旧房间回收、比赛阶段切换或服务端清理触发，不能单独断言是比赛总冠军结束。

### 11.4 房间解散/失效处理状态机

客户端应区分以下两类状态：

```text
玩家离桌：
USER_LEVEL_ROOM / USER_ONLINE_CHANGE / USER_STANDUP_ROOM
  -> 刷新 ROOM_INFO 或 WATCHGAME
  -> 房间仍可继续游戏

房间失效：
SEND_JOIN_ROOM(roomType=101)
  -> 9999 msgCode=95005
  -> 辅助连接 <game>EXIT
  -> gameBack postMessage
  -> 返回比赛大厅并刷新比赛列表/余额
```

### 11.5 重要边界

- `USER_STANDUP_ROOM` 只表示某个用户离座。
- `GAME_BF_CHANGE(state=false)` 是比赛/前后台状态切换，不是房间删除确认。
- `9999/msgCode=95005` 才是房间不存在或房间已失效的明确错误。
- `<game>EXIT` 是连接退出通知，通常是错误处理或返回大厅的后续动作。
- `postMessage(gameBack)` 是页面层返回大厅的通知，不是比赛结算消息。
- 比赛桌关闭时仍可能先产生最后几局 `DZPK_INNING_RESULT_PUSH` 和 `COMPETITION_BLIND_UP`，再在下一次重连时返回房间不存在。

## 12. 房间解散处理建议

1. 收到 `USER_STANDUP_ROOM` 时只更新用户座位和观战列表，不关闭主 WebSocket。
2. 收到 `2205 type=3` 或用户离线时，保留用户的比赛积分和最后状态，等待后续 `ROOM_INFO`/比赛列表确认。
3. 收到 `9999` 且 `msgCode=95005` 时，将当前分桌标记为 `STALE`，停止发送普通牌局请求。
4. 清理主连接和辅助连接，避免对已失效房间重复重连。
