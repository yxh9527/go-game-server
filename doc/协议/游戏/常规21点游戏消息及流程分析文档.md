## 3. 房间配置协议

### 3.1 ROOM_TYPE_RESULT（2201）

日志中 conf.roomType 为 bj21，核心配置如下：

~~~json
{
  "roomType": "bj21",
  "gameRoomConfigId": 3101,
  "playMode": 0,
  "allowCarryOut": true,
  "roomClassification": 2,
  "bj21Params": {
    "carryIn": 500,
    "ante": 100,
    "maxBet": 10000,
    "operateTime": 10,
    "insuranceTime": 8,
    "carryMin": 500,
    "carryMax": 0,
    "carryDefault": 0,
    "betTime": 10,
    "pairMinBet": 0,
    "pairMaxBet": 0,
    "notPairMinBet": 0,
    "notPairMaxBet": 0,
    "banSameIP": false,
    "observed": true,
    "randomSit": true,
    "banTalk": true,
    "gameStartNum": 1
  }
}
~~~

字段解释：

| 字段 | 含义 |
| --- | --- |
| carryIn / carryMin | 入桌携带分数门槛，样本为 500 |
| ante | 每局底注，样本为 100 |
| maxBet | 主下注上限，样本为 10000 |
| betTime | 下注阶段时长，单位为秒 |
| operateTime | 玩家行动阶段时长，单位为秒 |
| insuranceTime | 保险阶段时长，单位为秒 |
| pairMinBet / pairMaxBet | 对子旁注范围；样本为 0，表示未启用或不可下注 |
| notPairMinBet / notPairMaxBet | 非对子旁注范围 |
| observed | 是否允许旁观 |
| randomSit | 是否随机分配座位 |
| allowCarryOut | 是否允许带分离桌 |
| taxType / taxPercent | 房间税配置；日志样本为 2 / 500 |

## 4. 21点牌局状态消息

### 4.1 4550 <game>undefined

4550 是本日志中最重要的单桌牌局状态广播。它会在下注、玩家行动、庄家结算和下一局重置等阶段重复发送。

通用外层结构：

~~~json
{
  "currentInning": 557,
  "gameState": 6,
  "serverNow": 1792120164008,
  "stateDeadline": 1792120174008,
  "currentActionPlayerId": 15417545,
  "currentActionHandIndex": 0,
  "currentActionAvailableActions": ["HIT", "STAND", "DOUBLE"],
  "actionList": [],
  "players": [],
  "dealerCards": [8, -1],
  "dealerPointValue": 9,
  "dealerPointValues": [9]
}
~~~

字段解释：

| 字段 | 含义 |
| --- | --- |
| currentInning | 当前局号 |
| gameState | 牌局阶段枚举 |
| serverNow | 服务端当前时间 |
| stateDeadline | 当前阶段截止时间 |
| currentActionPlayerId | 当前需要操作的玩家 UID；无人操作时为 0 |
| currentActionHandIndex | 当前玩家正在操作的手牌序号 |
| currentActionAvailableActions | 当前可执行动作 |
| actionList | 已发生的动作记录 |
| players | 玩家牌局状态 |
| dealerCards | 庄家牌；-1 表示暗牌 |
| dealerPointValue / dealerPointValues | 庄家当前点数及多套点数结果 |
| cutDeck / cutCardReached | 切牌和切牌触发状态 |
| shoeDeckColor / shoeDealCount | 牌靴颜色和已发牌数量 |
| insuranceCollect | 当前是否处于保险收集阶段 |

### 4.2 玩家对象

players[] 中每个玩家包含：

~~~json
{
  "uid": 15417545,
  "pos": 2,
  "point": 5900,
  "betAmount": 2000,
  "mainBet": 2000,
  "pairBet": 0,
  "notPairBet": 0,
  "insuranceOperated": false,
  "insuranceAmount": 0,
  "insuranceProfit": 0,
  "stood": true,
  "actionOrder": 2,

~~~

牌局金额字段应按原始整数保存。样本中 ante=100，但主下注可以是 1000、2000 等，不应把所有金额都当作底注。

### 4.3 手牌对象

players[].hands[] 和 actionList[].hands[] 使用相同的核心结构：

~~~json
{
  "handIndex": 0,
  "betAmount": 1000,
  "doubled": false,
  "stood": true,
  "score": 0,
  "cardCount": 2,
  "splitHand": false,
  "cards": [45, 22],
  "pointValue": 17,
  "pointValues": [17],
  "handType": 2
}
~~~

其中：

- cards 是牌面编码数组，不是直接的牌名；
- pointValue 是当前主点数；
- pointValues 保留软牌/多解点数；
- doubled 表示是否加倍；
- splitHand 表示是否由分牌产生；
- stood 表示该手是否已停牌；
- handType 是牌型枚举，具体数字含义应以客户端牌型映射表为准；
- score 是该手结算分，行动阶段可能暂为 0。

## 5. 从日志还原的牌局状态机

### 5.1 gameState=2：新局/等待下注

典型特征：

~~~json
{
  "gameState": 2,
  "currentActionPlayerId": 0,
  "currentActionAvailableActions": [],
  "actionList": [],
  "dealerCards": [],
  "dealerPointValue": 0
}
~~~

玩家对象已经存在，但 betAmount、mainBet 为 0，手牌为空。该阶段用于清理上一局数据并等待新一局下注。

### 5.2 gameState=3：初始发牌/进入行动前

日志中该阶段出现庄家牌 [15, -1]，并且 actionList 已有多条记录，说明主下注和初始发牌已经完成，进入玩家行动队列。-1 表示庄家暗牌。

### 5.3 gameState=6：玩家行动

日志实际观察到：

~~~text
["HIT", "STAND", "DOUBLE", "SPLIT"]
["HIT", "STAND", "DOUBLE"]
["HIT", "STAND"]
~~~

动作集合由服务端按玩家、牌面和下注条件动态下发。可确认的动作含义：

| 动作 | 含义 |
| --- | --- |
| HIT | 要牌 |
| STAND | 停牌 |
| DOUBLE | 加倍下注并通常只再要一张牌 |
| SPLIT | 对相同点值或相同牌面进行分牌；本日志只观察到服务端提供该动作，未观察完整分牌请求 |

服务端通过 currentActionPlayerId 和 currentActionHandIndex 指定轮到谁的哪一手。客户端不应仅按座位顺序猜测轮次，应以这两个字段为准。

### 5.4 保险阶段

房间配置提供 insuranceTime=8，玩家和动作记录中也有：

~~~text
insuranceOperated
insuranceAmount
insuranceProfit
insuranceCollect
~~~

这表明协议支持保险流程。当前粘贴日志没有形成一段完整、可独立确认的保险操作请求，因此只能确认字段和阶段存在，不对具体请求编号或保险赔率做硬编码。

### 5.5 gameState=7：庄家亮牌与结算

日志中庄家牌从 [15, -1] 变为 [15, 17]，之后继续补牌，出现 [15, 17, 3]、[15, 17, 3, 37] 等序列，说明庄家暗牌被翻开并按规则继续要牌。

此阶段通常有：

- currentActionPlayerId=0；
- currentActionAvailableActions=[]；
- dealerCards 完整或逐步完整；
- dealerPointValue、dealerPointValues 更新；
- players[].hands[] 保留最终牌面；
- settleList[] 或 actionList[].handResults[] 出现结算结果。

## 7. 旁观同步和离桌流程

### 7.1 旁观同步

旁观者会收到：

- 2219 DZPK_PUSH_WATCHGAME：旁观用户列表；
- 2206 ROOM_INFO：房间和座位全量信息；
- 4550/4554：牌局实时状态；
- 4551：牌局结算；
- 1249 GAME_RECORD：历史输赢统计；
- 9212 GAME_POINT_UPDATE：桌内分数更新。

### 7.2 结束旁观和退出

日志中的退出链路为：

~~~text
2110 SEND_LEVEL_OUT
 -> 9212 GAME_POINT_UPDATE
 -> 3436 USER_STANDUP_ROOM
 -> 2205 USER_LEVEL_ROOM
 -> 大厅 HTTP op=54 / op=38 刷新钱包和房间列表
~~~

其中：

- SEND_LEVEL_OUT 是客户端发起离桌；
- USER_STANDUP_ROOM 表示用户离开座位或桌面状态更新；
- USER_LEVEL_ROOM 表示用户离开房间；
- op=54 返回钱包余额；
- op=38 重新拉取 21 点大厅房间列表。

## 8. 建议的客户端解析模型

~~~text
roomConfig = ROOM_TYPE_RESULT.conf
roomInfo   = ROOM_INFO

on 4550:
  state[currentInning] = fullSnapshot

on 4554:
  merge current player/actionList into state[currentInning]

on 4551:
  state[currentInning].settleList = settleList
  mark round settled

on 9212:
  update player point

on 2205:
  remove room membership
~~~

建议以 currentInning 为局索引，以 uid + handIndex 为手牌索引，并保留所有未知数值枚举。牌面编码、handType、actionType、handEndType 应从前端常量表进一步确认后再转换为中文。

## 10. 结论

常规21点单桌协议可以按以下主链路实现：

~~~text
大厅 op=45
 -> ROOM_LOGIN(1105/1205)
 -> SEND_JOIN_ROOM(2102, isOb=true)
 -> ROOM_TYPE_RESULT(2201)
 -> ROOM_INFO(2206)
 -> 4550 gameState=2（等待下注）
 -> 4550 gameState=3（初始发牌）
 -> 4550/4554 gameState=6（HIT/STAND/DOUBLE/SPLIT）
 -> 4550 gameState=7（庄家亮牌、补牌）
 -> 4551（settleList 结算）
 -> GAME_RECORD / GAME_POINT_UPDATE
 -> SEND_LEVEL_OUT / USER_LEVEL_ROOM
 -> 大厅 op=54、op=38
~~~

与赌场 21 点大厅 MQTT 文档相比，本文补充了常规 21 点的房间接入、单桌牌局状态、庄家牌面、玩家手牌、动作集合、保险字段、结算列表和离桌刷新流程。
