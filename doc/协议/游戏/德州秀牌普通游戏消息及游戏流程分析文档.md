## 2. 日志格式和传输层

### 2.1 房间 WebSocket 日志

典型格式如下：

```text
<时间> index.4cda5.js:140869 <消息ID> <方向> <消息名> wss://<domain>/ data=<JSON>
```

方向含义：

| 日志方向 | 含义 |
| --- | --- |
| `↑↑` | 客户端发送到服务端 |
| `↓↓` | 服务端推送到客户端 |
| `RoomSocket-111` | 实际德州游戏房间连接 |
| `RoomSocket-222` | 辅助连接，日志中主要出现登录响应和退出消息 |

客户端底层发送的是二进制包，日志位置 `index.4cda5.js:140869` 已经经过 `readBuffer/writeBuffer` 解码，因此本文分析的是业务消息，不是 WebSocket 原始二进制格式。消息主体可能是对象、数组、字符串、数字或 `undefined`，不能一律按对象处理。

### 2.2 大厅 HTTP

| 接口特征 | 作用 | 日志中的观察 |
| --- | --- | --- |
| `/internal/v1/do?op=45` | 进入游戏并获取房间连接信息 | 返回 `roomId`、`roomType`、普通房间域名和百人房间域名 |
| `/internal/v1/do?op=63` | 刷新/查询大厅侧状态 | 多次返回空数组 |
| `/internal/v1/do?op=54` | 查询钱包或资产 | 返回 `walletAmount`、`ticketNums` |
| `/internal/v1/do?op=38` | 获取德州房间列表及配置 | 返回不同盲注、玩法、携带分和房间分类 |
| `/_next/data/.../19/1.json` | 页面/大厅路由数据 | 返回 `initialGameType=19`、`initialSubGameType=1` |

`op=45` 的 `param` 是 Base64 编码的查询串。该日志中解码后可还原出以下关键参数：

```text
gameType=19
smallBlind=10
bigBlind=20
playMode=0
roomType=19
ante=0
initialBet=20
roomClassification=2
carryMin=500
straddle=false
seeCardNo=3
roomIndex=0
forceShowCard=1
op=45
```

其中 `forceShowCard=1`、`seeCardNo=3` 和房间配置里的 `forceShowType=1` 表明这是秀牌/强制展示牌相关房间。`param` 不是 WebSocket 消息体，复现 HTTP 请求时需要先 URL 编码，再进行 Base64 编码。

## 3. 进入房间流程

### 3.1 获取房间域名

客户端先调用大厅 `op=45`，服务端返回类似：

```json
{
  "roomId": 46675129,
  "roomType": 19,
  "domain": "<room-domain-1>,<room-domain-2>",
  "hundredDomain": "<hundred-domain-1>,<hundred-domain-2>"

```

客户端随后建立两个 WebSocket：

- `RoomSocket-111`：普通游戏房间域名，承载德州扑克房间业务。

### 4.4 GTO 建议消息

`3177 GTO_REQ` 的请求体是一个 JSON 字符串，而不是嵌套对象：

```json
{
  "tipsListStr": "[{\"operation\":6,\"data\":0,\"playerAmount\":115},{\"operation\":9,\"data\":0,\"playerAmount\":115}]"
}
```

`3464 GTO_RES` 返回操作编号到概率的映射，例如：

```json
{"7":0.03,"9":0.96}
```

这说明客户端会先从 `DZPK_OPERATION_PUSH` 获得可行动作，再请求 GTO 服务，最后把建议概率映射回操作按钮。GTO 消息属于辅助功能，不是牌局状态推进的必要消息。

## 5. 牌局流程分析

### 5.1 日志开始时的断线恢复/观战同步

日志开始时服务端已经处于 `currentInning=423`，客户端先收到：

```text
DEAL_TURN
DZPK_DEAL_ZHUANG_PUSH
NIUNIU_INNING_BEGIN_INFO
```

`NIUNIU_INNING_BEGIN_INFO` 中已经包含 `flopPokerList`、`turnPoker`、底池、当前操作者和部分玩家手牌摘要。这不是一局新牌的完整发牌顺序，而是进入房间时对当前进行中牌局的恢复快照。

### 5.2 新局开始

完整新局的可观察顺序为：

1. `NIUNIU_CURRENT_INNING_BEGIN_INFO`：发布新局号和参与玩家。
2. `COMMON_SWITCH_REQ/RES`：读取快捷换桌等通用开关。
3. `DZPK_ZHUANG_PUSH`：确定庄位、小盲、大盲、straddle 和枪口位。
4. `QIPAI_RESULT`：洗牌/发牌准备结果。
5. `BRNN_GAME_STATE_PUSH: BET_FRONT`：前置下注阶段。
6. 多条 `DZPK_ACTION_BET_PUSH`：玩家完成初始下注。
7. `BRNN_GAME_STATE_PUSH: BET_BLIND`：小盲和大盲阶段。
8. `BRNN_GAME_STATE_PUSH: DEAL_PERFLOP` 与 `DZPK_DEAL_DI_PUSH`：发底牌。
9. `BRNN_GAME_STATE_PUSH: BET_PERFLOP`：翻牌前轮的行动阶段。

日志中的一局新局示例：

```text
BET_FRONT -> BET_BLIND -> DEAL_PERFLOP -> BET_PERFLOP
```

`DZPK_DEAL_DI_PUSH` 的 `cardList` 对其他玩家可能为空或为 `[-1,-1]`，这是服务端按权限隐藏底牌的表现，不代表没有发牌。

### 5.3 翻牌、转牌、河牌

标准牌局的后续状态和消息关系如下：

| 状态 | 发牌消息 | 说明 |
| --- | --- | --- |
| `DEAL_FLOP` | `DZPK_DEAL_FAN_PUSH` | 一次发 3 张公共牌 |
| `BET_FLOP` | `DZPK_OPERATION_PLAYER_PUSH`、`DZPK_OPERATION_PUSH`、`DZPK_ACTION_BET_PUSH` | 翻牌圈行动 |
| `DEAL_TURN` | `DZPK_DEAL_ZHUANG_PUSH` | 一次发 1 张转牌 |
| `BET_TURN` | 保险提示、胜率推送和下注动作 | 转牌圈可能进入保险 |
| `DEAL_RIVER` | `DZPK_DEAL_HE_PUSH` | 一次发 1 张河牌 |
| `BET_RIVER` | `DZPK_ACTION_BET_PUSH` | 河牌圈行动 |
| `SETTLE` | `DZPK_INNING_RESULT_PUSH` | 牌型和积分结算 |

日志中的公共牌样本为：

```text
翻牌：[39, 28, 12]
转牌：[16]
河牌：[45]
```

牌值的具体数值映射需要结合客户端牌面枚举；日志同时提供 `pokerEnumList`，因此解析牌型时应优先使用枚举名，而不是只根据数字猜测。

### 5.4 玩家动作

客户端提交动作的统一入口是 `3162 DZPK_SEND_ACTION`：

```json
{
  "uid": "<uid>",
  "operation": 7,
  "operationData": 2.3
}
```

服务端通常先返回 `3440 DZPK_ACTION_BET_PUSH`，再返回下一位的 `3433 DZPK_OPERATION_PLAYER_PUSH` 和新的 `3426 DZPK_OPERATION_PUSH`。因此客户端判断动作是否生效，应以服务端 `ACTION_BET_PUSH` 为准，不能只看本地发送成功。

本次日志可观察到的操作编号关系如下，属于基于样本的推断：

| operation | 样本表现 | 推断 |
| ---: | --- | --- |
| 1 | 多名玩家 `currentBetScore=20` | 前置下注/初始下注 |
| 2 | 小盲增加 10、大盲增加 20 | 盲注动作 |
| 3 | 下注额补到当前轮最高额 | 跟注类动作 |
| 6 | `currentBetScore=0`，玩家积分保留 | 弃牌或不继续本轮，需结合客户端枚举确认 |
| 7 | `operationData` 为 `0.2`、`1.15`、`2.3` 等，下注额增加 | 加注/下注金额类动作 |
| 9 | `point=0` 或下注额达到剩余积分 | 全下类动作 |
| 13 | 下注额一次性增加到新的轮次额度 | 特殊加注/跟注动作，需结合枚举确认 |

操作编号是协议枚举值，以上表格不能替代客户端 `SEND_ACTION` 枚举。实现模拟器时应把未知编号保留为原始数字，避免把 `6`、`7`、`9` 等硬编码成不可验证的中文动作名。

### 5.5 保险流程

日志中一局牌的保险时序为：

1. `DEAL_TURN` 和转牌到达。
2. 服务端发送 `DZPK_PUSH_INSURANCE_HIT_POOL_MSG(state=0)`。
3. 服务端发送 `DZPK_CARDTYPE_PUSH` 和 `DZPK_PUSH_INSURANCE_TIPS_MSG`。
4. 客户端发送 `DZPK_SEND_BUY_INSURANCE_REQ`，样本购买金额为 `99`。
5. 服务端发送 `DZPK_PUSH_BUY_INSURANCE_MSG` 确认购买。
6. 河牌到达后发送 `DZPK_PUSH_BUY_INSURANCE_SETTLE_MSG` 和 `DZPK_PUSH_INSURANCE_HIT_POOL_MSG(state=1)`。
7. 进入 `BET_RIVER`、`SETTLE`，最终保险金额写入结算结果。

### 5.6 结算

`3432 DZPK_INNING_RESULT_PUSH` 是一局牌的最终结算消息，消息体是数组，每个元素代表一名玩家：

```json
{
  "xiaZhuData": 500,
  "cardTypeInfo": {
    "pokerEnumList": ["SPADE_3", "HEART_3", "DIAMOND_K", "HEART_A", "SPADE_A"],
    "handCardList": [41,28,12,26,39],
    "cardTypeId": 3
  },
  "cardTypeId": 0,
  "insuranceBet": 99,
  "insuranceProfit": -99,
  "isWin": true,
  "uid": "<uid>",
  "score": 956,
  "point": 1456,
  "handPais": [41,28,12,26,39],
  "pos": 6
}
```

结算字段要点：

- `score` 是本局输赢分，`point` 是结算后的携带分/积分。
- `xiaZhuData` 是本局累计下注。
- `handPais` 是最终 5 张牌；`showCards` 用于明确展示的两张底牌。
- `cardTypeInfo.cardTypeId` 和顶层 `cardTypeId` 可能同时存在，分别对应完整牌型信息和展示/玩家状态字段，不能简单认为二者始终相同。
- `insuranceBet`、`insuranceProfit`、`winInsurance` 用于保险结算。

### 5.7 回放和离开

牌局结束后客户端可以发送 `3167 DZPK_SEND_GameBackReq`：

```json
{
  "excellentGame": false,
  "beginNum": 421,
  "endNum": 421,
  "roomId": 46675129
}
```

服务端通过 `3446 DZPK_PUSH_GameBackMsg` 返回 `playBackList`。回放中的每个玩家包含 `operateList`，每个操作通常带有：

```json
{
  "cards": [38,29],
  "operate": 9,
  "bet": 150,
  "gameState": 3,
  "critAnte": 0
}
```

离开时主房间会出现 `USER_STANDUP_ROOM`、`USER_LEVEL_ROOM` 等状态消息；辅助连接日志中出现 `<game>EXIT`，其 `roomType=50` 更像辅助房间的退出通知，不能直接当作主德州房间的结算消息。

## 6. 一局牌的可实现状态机

结合本次日志，可以抽象为：

```text
ROOM_LOGIN
  -> SEND_JOIN_ROOM / ROOM_TYPE_RESULT / ROOM_INFO
  -> CURRENT_INNING_BEGIN
  -> ZHUANG / QIPAI
  -> BET_FRONT
  -> BET_BLIND
  -> DEAL_PERFLOP
  -> BET_PERFLOP
  -> DEAL_FLOP
  -> BET_FLOP
  -> DEAL_TURN
  -> [INSURANCE]
  -> BET_TURN
  -> DEAL_RIVER
  -> BET_RIVER
  -> SETTLE
  -> INNING_RESULT
  -> GAME_RECORD / POINT_UPDATE
  -> NEXT_INNING 或 EXIT
```

需要注意三点：

1. `3263 BRNN_GAME_STATE_PUSH` 是状态机的主时钟，消息名虽然带 `BRNN`，但在本日志中承载的是德州状态。
2. `3426 DZPK_OPERATION_PUSH` 和 `3433 DZPK_OPERATION_PLAYER_PUSH` 共同决定当前客户端是否可以操作、可以做什么以及剩余时间。
3. `3440 DZPK_ACTION_BET_PUSH`、`3432 DZPK_INNING_RESULT_PUSH` 是服务端确认结果，客户端不能用本地按钮事件替代它们。

## 7. 协议实现建议

- 按 `messageId` 分发，不要只按消息名分发；同名 `ROOM_LOGIN` 同时用于请求和响应。
- 对 payload 做类型联合处理：`object | array | string | number | undefined`。
- 将 `3263` 的状态字符串和 `3427` 至 `3430` 的发牌消息组合起来，形成牌局状态机。
- 将 `DZPK_ACTION_BET_PUSH` 保存为不可变事件，再由事件计算底池、玩家累计下注和当前操作人。
- 对底牌 `-1`、空数组和缺少 `cardList` 保持原值，不要当作服务端漏字段。
- `tipsListStr` 是 JSON 字符串，需要二次 `JSON.parse`；`blind` 等回放字段也可能是 JSON 字符串，需要按字段类型二次解析。
- 保险、GTO、宝箱、积分、战绩属于可选旁路模块，主牌局解析器应与这些模块解耦。
- 生产日志不要输出 `userToken`、`openId`、设备 ID、完整用户列表或 IP 编码值。

## 8. 本次日志结论

本次日志不是单纯的“进入房间”记录，而是包含了一个进行中牌局的恢复、至少一局完整德州牌局、保险购买、结算、历史回放请求、下一局开始以及离开房间的连续样本。最可靠的流程判断依据是：

```text
ROOM_INFO
  -> BRNN_GAME_STATE_PUSH
  -> DZPK_DEAL_*
  -> DZPK_OPERATION_PLAYER_PUSH / DZPK_OPERATION_PUSH
  -> DZPK_ACTION_BET_PUSH
  -> DZPK_PUSH_INSURANCE_*
  -> DZPK_INNING_RESULT_PUSH
```

其中 `ROOM_INFO` 提供房间和玩家快照，`BRNN_GAME_STATE_PUSH` 提供阶段，`DZPK_DEAL_*` 提供公共牌/底牌事件，`DZPK_ACTION_BET_PUSH` 提供动作确认，`DZPK_INNING_RESULT_PUSH` 提供最终输赢。这四类消息组合后即可重建主要游戏流程。
