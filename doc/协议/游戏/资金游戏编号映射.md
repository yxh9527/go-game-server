# 客户端玩法与资金游戏编号映射

日期：2026-11-10。当前已完成 Node 路由校验、Lottery/DataCenter 适配代码和隔离后端编译验证；后台表结构和现有线上资金链路尚未切换。

客户端 gameType + roomType 唯一确定本项目玩法，由可信 data-center 映射到 gp_game.number。Lottery 请求中的 gameId 使用 number；gp_game.id 继续作为数据库主键，symbol 用作既有游戏和奖池配置标识。

## 现有字段兼容

实际后端 gp_game.gameType 指向 gp_game_type 分类，初始化分类包含 slots、fruits、ug5。web-api 的 GameList 和 SyncAllPool 使用此字段。它不是客户端大厅 gameType，直接改写旧值会影响旧游戏分类和按分类同步奖池。

建议 gp_game 保留原 gameType，新增可空 clientGameType 和 roomType。旧游戏两者均为 NULL；本项目游戏两者均为正整数。对新映射建立 UNIQUE(clientGameType, roomType)，保证一个客户端玩法只对应一个 number。number 仍须全局唯一，创建新游戏时检查冲突，不能重新编号旧游戏或以客户端数字拼接生成资金编号。

如果最终采用只增加 roomType、复用 gameType 的方案，必须先明确修改后的分类语义，并同步调整 gp_game_type、后台分类接口、奖池批量同步和旧游戏兼容；这不是单独添加一个字段即可完成的变更。

data-center 面向 Node 投影为 gameType、roomType、number、symbol、state、isFrozen。其中投影 gameType 来自 clientGameType，不能直接投影旧分类字段。

## 路由使用

- 按服务端已确认的房间配置取得 gameType 与 roomType，不信任客户端自报的 number。
- 例如德州 (19,19)、百人德州 (1000,50)、麻将胡了 (1004,61)、赏金女王 (1004,63) 是独立映射；不在代码中预填尚未核对的资金编号。
- playMode、gameRoomConfigId、底分等继续是玩法和房间配置，默认不进入游戏身份联合键；需要独立资金游戏编号时再扩展身份约定。
- 房间等级 level 仍需对应实际奖池配置，不能把 number 或 roomType 当成 level。
- 同一个客户端玩法可以有多个代理和等级奖池，agent/level 不改变其 number。
- 一局创建时绑定 number 与 symbol；热更新映射只影响新局，不能让正在下注或结算的旧局改换资金游戏身份。
- 缺失映射、重复映射、重复 number、维护或冻结时拒绝新资金操作，不回退猜测编号。
