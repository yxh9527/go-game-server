已观察到的 type：

| type | 观察到的上下文 | 协议解释 |
| ---: | --- | --- |
| 1 | isFlower、flowerNum、opTime | 摸牌/进入回合 |
| 2 | 带 card | 出牌 |
| 8 | 牌局结束前出现 | 胡牌事件 |
| 9 | 带 card，随后继续出牌 | 听牌或特殊操作确认状态，需结合客户端枚举 |

### 6.2 补花

极速麻将额外在 3803 中提供：

~~~json
{
  "uid": 77363345,
  "pos": 2,
  "type": 1,
  "isFlower": true,
  "flowerNum": 1,
  "opTime": 1,
  "leftCardLen": 70,
  "tingIndex": 0,
  "isLastCard": false
}
~~~

随后同一玩家会收到正常摸牌状态：

~~~json
{
  "uid": 77363345,
  "pos": 2,
  "type": 1,
  "isFlower": false,
  "flowerNum": 1,
  "opTime": 10,
  "leftCardLen": 69
}
~~~

处理顺序应为：

~~~text
检测 isFlower=true
 -> 增加 flowerNum
 -> 使用短补花倒计时
 -> 等待服务端继续发牌
 -> isFlower=false 后进入正常操作
~~~

不能把补花事件当成普通摸牌，否则牌墙数量和计分会错位。

~~~text

 -> ROOM_INFO(2206)
~~~

日志中 leftCardLen 从 107 持续下降到 66、50 等值，补花事件会插入额外流程，但仍由服务端统一维护牌墙数量。

## 10. 旁观和权限边界

旁观端通常可以看到：

- 3801 中自己的 handCards；
- 其他玩家的 cardLen；
- 3803 中公开的 card、isFlower、flowerNum、tingIndex；
- 3804 的完整结算手牌和分数。

应保留 -1 遮罩或缺失字段，不能把旁观状态下的空手牌当成真实空牌。

## 14. 结论

极速麻将四人场的识别条件和协议链路为：

~~~text
roomType=26 / jsmj
gameRoomConfigId=2601
playMode=0
maxPeople=4
gameStartNum=4

ROOM_LOGIN(1105/1205)
 -> SEND_JOIN_ROOM(2102)
 -> ROOM_TYPE_RESULT(2201)
 -> ROOM_INFO(2206)
 -> 3801 起手快照
 -> 3802 JSMJ_PUSH_TURN
 -> 3803 摸牌、出牌、补花和胡牌
 -> 3600 客户端动作
 -> 3602 / 3808 听牌查询
 -> 3804 补花、胡分、加番牌和最终结算
 -> 9211 / 9212 / 1249 分数与记录
 -> SEND_LEVEL_OUT / USER_LEVEL_ROOM
~~~

实现时应以 roomType=26、roomType=jsmj 和 gameRoomConfigId=2601 识别极速麻将，以 3801 保存全量快照，以 3803 驱动增量状态，以 isFlower/flowerNum 处理补花，以 3804 保存补花和胡分明细。
