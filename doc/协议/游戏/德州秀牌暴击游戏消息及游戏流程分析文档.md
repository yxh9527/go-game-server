房间日志格式：

```text

```

| 标记 | 含义 |
| --- | --- |
| `↑↑` | 客户端发送到服务端 |
| `↓↓` | 服务端推送到客户端 |

## 4. 进入房间流程

### 4.1 获取房间信息

客户端先通过大厅 `op=45` 获取房间号和连接域名。随后连接 `RoomSocket-111`，同时创建辅助连接 `RoomSocket-222`。

### 4.2 登录和加入房间

客户端发送 `1105 ROOM_LOGIN`：

```json
{
  "isAutoLogin": true,
  "userId": "<uid>",
  "openId": "<openId>",
  "userToken": "<token>",
  "version": "<client-version>",
  "cVersion": 20240607,
  "deviceId": "<deviceId>",
  "deviceName": "<device-name>",
  "language": 1,
  "openHundredGame": false,
  "clubId": "<clubId>",
  "packetId": 5,
  "isApiLogin": true,
  "currency": "CNY",
  "plat": 4,
  "abFlag": 2,
  "roomId": "<roomId>",
  "isInRoom": false
}
```

服务端返回 `1205 ROOM_LOGIN`，包含服务端时间、俱乐部、汇率和快捷换桌状态。

主连接随后执行：

1. `2102 SEND_JOIN_ROOM`：`{roomId,clubId,isOb,openHundredGame,roomType}`。
2. `2219 DZPK_PUSH_WATCHGAME`：当前观战玩家列表。
3. `2201 ROOM_TYPE_RESULT`：完整暴击德州配置，并确认最终房间号。
4. `2117 SEND_GAME_SETTING` 和 `2220 DZPK_PUSH_GAME_SETTING`：请求/返回游戏设置。
5. `3178/3465 DZPK_FORCE_INSURANCE_CONF_REQ/RES`：读取强制保险设置。
6. `2200/2221 COMMON_SWITCH_REQ/RES`：读取通用开关。
7. `2111 LOGIN_ROOM`：正式进入房间。
8. `2206 ROOM_INFO`：同步当前座位、玩家、旁观者、局号和规则。

`ROOM_INFO` 中的 `dzpk` 对象是客户端建立规则上下文的主要来源，优先级高于大厅入口参数。

## 6. 暴击相关字段和可见行为

### 6.1 已确认的暴击配置

暴击玩法的唯一明确配置来源是 `ROOM_TYPE_RESULT`/`ROOM_INFO`：

```json
{
  "criticalFlag": true,
  "criticalAnte": 100,
  "criticalInterval": "5-8",
  "playMode": 3,
  "gameRoomConfigId": 1921
}
```

`criticalAnte` 与普通 `initialBet=20` 是两个不同概念：普通初始下注仍为 20，而暴击配置另有 100 的专属数值。日志没有足够证据判断 100 是每局固定前注、触发时附加前注，还是暴击池的计算基数，不能直接用它推导结算公式。

### 6.2 结算中可观察字段

`3432 DZPK_INNING_RESULT_PUSH` 每个玩家元素包含：

```json
{
  "xiaZhuData": 500,
  "cardTypeId": 0,
  "insuranceBet": 0,
  "insuranceProfit": 0,
  "winInsurance": 0,
  "calamariScore": 0,
  "isWin": false,
  "control": false,
  "uid": "<uid>",
  "score": -500,
  "point": 0,
  "handPais": [1,2,3,4,5],
  "pos": 0
}
```

其中 `calamariScore`、`control` 可能是通用或特殊玩法字段。本次日志中 `calamariScore` 未观察到非零值，也没有出现明确的 `criticalScore`、`criticalMultiple` 或 `criticalResult` 字段。因此不能把 `calamariScore` 直接等同于暴击分。

### 6.3 暴击流程的合理模型

根据字段命名可以建立以下待验证模型：

```text
房间配置 criticalFlag=true
  -> 牌局按普通德州阶段运行
  -> 服务端根据 criticalInterval/criticalAnte 判定是否触发暴击规则
  -> 下注事件仍通过 DZPK_ACTION_BET_PUSH 广播
  -> 最终金额应体现在 DZPK_INNING_RESULT_PUSH 的 score/point 或专属字段
```

这只是协议层的工作假设。当前日志只能确认暴击开关和参数，未捕获到一次能把 `criticalAnte=100` 与最终分数一一对应的明确样本。实现解析器时应保留未知字段，不能自行把暴击金额写死到普通下注计算中。

## 7. 游戏流程

### 7.1 进入时的进行中牌局恢复

本次进入房间时 `ROOM_INFO.currentInning=224`，随后收到：

```text
NIUNIU_INNING_BEGIN_INFO(gameState=BET_FLOP)
DZPK_PLAYER_DIPAI_PUSH
GAME_TUOGUAN_ACTION
MULTI_ROOM_STATUS_SYNC
DZPK_PUSH_WATCHGAME
GAME_RECORD
```

这说明客户端不是从牌局起点开始，而是先恢复一局正在进行的牌局。`NIUNIU_INNING_BEGIN_INFO` 的 `flopPokerList`、`pot`、`currentOperatorId`、`roundBetMap` 和 `memberDeskInfos` 是恢复 UI 的核心数据。

### 7.2 新局流程

日志中可以完整观察到新局 `currentInning=225` 的流程：

1. `NIUNIU_CURRENT_INNING_BEGIN_INFO`：发布局号和玩家列表。
2. `DZPK_ZHUANG_PUSH`：确定庄位、小盲、大盲和枪口位。
3. `QIPAI_RESULT`：洗牌/发牌准备结果。
4. `BET_FRONT`：前置下注。
5. `BET_BLIND`：小盲和大盲下注。
6. `DEAL_PERFLOP` + `DZPK_DEAL_DI_PUSH`：发底牌。
7. `BET_PERFLOP`：翻牌前行动。
8. `DEAL_FLOP` + `DZPK_DEAL_FAN_PUSH`：发 3 张翻牌。
9. `BET_FLOP`：翻牌圈行动。
10. `DEAL_TURN` + `DZPK_DEAL_ZHUANG_PUSH`：发转牌。
11. `BET_TURN`：转牌圈行动，并可能触发保险。
12. `DEAL_RIVER` + `DZPK_DEAL_HE_PUSH`：发河牌。
13. `BET_RIVER`：河牌圈行动。
14. `SETTLE` + `DZPK_INNING_RESULT_PUSH`：结算并更新积分。

状态序列可以抽象为：

```text
BET_FRONT
 -> BET_BLIND
 -> DEAL_PERFLOP
 -> BET_PERFLOP
 -> DEAL_FLOP
 -> BET_FLOP
 -> DEAL_TURN
 -> BET_TURN
 -> DEAL_RIVER
 -> BET_RIVER
 -> SETTLE
```

### 7.3 玩家动作确认

客户端提交动作的统一消息为 `3162 DZPK_SEND_ACTION`：

```json
{
  "uid": "<uid>",
  "operation": 7,
  "operationData": 1.15
}
```

服务端广播 `3440 DZPK_ACTION_BET_PUSH`：

```json
{
  "uid": "<uid>",
  "currentBetScore": 115,
  "totalBetScore": 155,
  "operation": 7,
  "point": 345,
  "pot": 575
}
```

然后通过 `3433 DZPK_OPERATION_PLAYER_PUSH` 指定下一位操作玩家。客户端应以服务端的 3440 作为动作生效依据，不应把本地按钮点击当成最终结果。

本日志中观察到的动作编号：

| operation | 观测表现 | 说明 |
| ---: | --- | --- |
| 1 | 多人各增加 20 | 前置下注 |
| 2 | 小盲增加 10、大盲增加 20 | 盲注 |
| 4 | 下注增加到 106，底池增加 | 加注/下注类动作，精确枚举需结合客户端常量 |
| 6 | `currentBetScore=0` | 弃牌或退出当前轮，需结合枚举确认 |
| 7 | `operationData` 为 0.2、1.15 等 | 下注/加注金额类动作 |
| 9 | `point=0` 或达到剩余积分 | 全下类动作的候选值 |
| 10 | 玩家不再继续下注 | 特殊跟注/弃牌动作，需结合枚举确认 |

以上是日志推断，不应替代源码中的操作枚举。

### 7.4 保险和暴击的交叉点

暴击配置和保险配置同时开启，但两者是不同模块：

- 暴击由房间配置中的 `criticalFlag/criticalAnte/criticalInterval` 表达。
- 保险由 `DZPK_PUSH_INSURANCE_TIPS_MSG`、`DZPK_PUSH_BUY_INSURANCE_MSG` 等消息表达。
- 保险金额在结算中明确出现在 `insuranceBet`、`insuranceProfit`、`winInsurance`。
- 本次日志没有暴击专属结果字段，所以不能用保险字段推断暴击结算。

## 8. 结算和离开

`3432 DZPK_INNING_RESULT_PUSH` 是一局牌最终结果，payload 为玩家数组。关键字段：

| 字段 | 含义 |
| --- | --- |
| `xiaZhuData` | 本局累计下注 |
| `handPais` | 最终组合牌 |
| `showCards` | 展示的底牌 |
| `cardTypeInfo` | 牌型名称、牌值和牌型 ID |
| `score` | 本局输赢分 |
| `point` | 结算后的携带分 |
| `insuranceBet` | 保险下注额 |
| `insuranceProfit` | 保险盈亏 |
| `calamariScore` | 特殊玩法通用字段，本次未观察到非零值 |
| `control` | 控制/特殊结果标记，本次样本均为 `false` |
| `isWin` | 玩家是否赢得主牌局结果 |

本次日志观察到多局结算：有的牌局在翻牌圈因其他玩家弃牌直接进入 `SETTLE`，有的牌局完整经过转牌、保险、河牌。也就是说，不能要求每局都出现完整的 `DEAL_TURN` 和 `DEAL_RIVER`。

用户离座时会出现：

- `3436 USER_STANDUP_ROOM`：payload 为用户 ID。
- `2205 USER_LEVEL_ROOM`：更新用户房间状态。
- `2219 DZPK_PUSH_WATCHGAME`：刷新观战列表。
- 辅助连接可能出现 `6106 <game>EXIT`。

## 9. 协议实现建议

1. 以消息 ID 分发，而不是只按消息名分发；`ROOM_LOGIN` 同时用于请求和响应。
2. 把 `3263` 的状态字符串作为状态机主事件，把 `3427` 至 `3430` 作为发牌事件，把 `3440` 作为动作确认事件。
3. 为 payload 保留联合类型：对象、数组、字符串、数字、`undefined`。
4. 在房间初始化时保存完整 `dzpk` 配置，尤其是 `criticalFlag`、`criticalAnte`、`criticalInterval`、`playMode` 和 `gameRoomConfigId`。
5. 不要把 `criticalAnte=100` 直接当作固定每局扣款；应等待带有明确暴击结果字段的样本。
6. 对 `-1`、缺少 `cardList` 和空数组保持原样，它们可能表示底牌权限隐藏。
7. `GAME_RECORD`、`DZPK_PUSH_BLOCKCHAIN_NOTIFY`、宝箱和积分消息属于旁路模块，和主牌局状态机解耦。
8. `DZPK_PUSH_BLOCKCHAIN_NOTIFY.notarizationCode` 是长字符串证明数据，只保存 `currentInning` 和摘要即可，避免把完整证明写入普通业务日志。
9. 生产环境禁止输出 `userToken`、`openId`、设备 ID、登录 IP 和完整用户列表。

## 10. 结论

本日志确认的是“暴击德州”房间，而不是普通德州房间。确认依据为：

```text
roomType=19
roomTypeName=dzpk
gameRoomConfigId=1921
playMode=3
criticalFlag=true
criticalAnte=100
criticalInterval=5-8
```

牌局主流程仍然遵循标准德州状态序列：

```text
房间登录
 -> 房间快照/进行中牌局恢复
 -> 庄位和洗牌
 -> 前置下注/盲注
 -> 底牌
 -> 翻牌前
 -> 翻牌/翻牌圈
 -> 转牌/转牌圈
 -> 保险（可选）
 -> 河牌/河牌圈
 -> 结算
 -> 积分、战绩和下一局
```

暴击目前能从房间配置层可靠识别，但本次日志没有独立暴击消息或明确暴击结算字段。后续若要还原暴击算法，需要继续采集包含不同 `criticalInterval`、不同 `criticalAnte` 和完整结算事件的多局日志，并对比 `DZPK_ACTION_BET_PUSH`、`DZPK_INNING_RESULT_PUSH` 中的分数变化。
