## 3. 传输层和日志方向

```text
<时间> index.4cda5.js:140869 <消息ID> <方向> <消息名> wss://<domain>/ data=<payload>
```

| 标记 | 含义 |
| --- | --- |
| `↑↑` | 客户端发送到服务端 |
| `↓↓` | 服务端推送到客户端 |
| `RoomSocket-111` | 主房间连接 |
| `RoomSocket-222` | 辅助连接 |

## 4. 进房和房间同步流程

客户端发送 `1105 ROOM_LOGIN`：

```json
{
  "isAutoLogin": true,
  "userId": "<uid>",
  "openId": "<openId>",
  "userToken": "<token>",
  "version": "<client-version>",
  "cVersion": 20240607,
  "deviceId": "<deviceId>",
  "language": 1,
  "openHundredGame": false,
  "clubId": "<clubId>",
  "packetId": 5,
  "isApiLogin": true,
  "currency": "CNY",
  "plat": 4,
  "roomId": "<roomId>",
  "isInRoom": false
}
```

服务端通过 `1205 ROOM_LOGIN` 返回服务端时间、俱乐部、汇率和快捷换桌状态。主连接随后执行：

1. `2102 SEND_JOIN_ROOM`：申请加入房间。
2. `2219 DZPK_PUSH_WATCHGAME`：旁观玩家列表。
3. `2201 ROOM_TYPE_RESULT`：普通不秀牌配置。
4. `2117/2220 SEND_GAME_SETTING/DZPK_PUSH_GAME_SETTING`：游戏设置。
5. `3178/3465 DZPK_FORCE_INSURANCE_CONF_REQ/RES`：强制保险设置，日志返回 `{switch:false,ratio:0}`。
6. `2200/2221 COMMON_SWITCH_REQ/RES`：通用开关。
7. `2111 LOGIN_ROOM`：正式进入房间。
8. `2206 ROOM_INFO`：玩家、座位、旁观者、局号和配置快照。

进入时 `3260 NIUNIU_INNING_BEGIN_INFO` 可能是 `BET_PERFLOP` 等中间状态，表示恢复正在进行的牌局；重新连接不能假定从 `BET_FRONT` 开始。

## 6. 普通不秀牌牌局流程

### 6.1 状态机

日志观察到的完整状态集合：

```text
BET_FRONT
 -> BET_BLIND
 -> DEAL_PERFLOP
 -> BET_PERFLOP
 -> DEAL_FLOP
 -> BET_FLOP
 -> DEAL_TURN
 -> BET_TURN
 -> DEAL_RIVER
 -> BET_RIVER
 -> SETTLE
```

短牌局可能在翻牌前或翻牌圈因其他玩家弃牌直接进入 `SETTLE`，不一定包含转牌和河牌。

### 6.2 前置下注和盲注

普通房间配置 `initialBet=20`。线上每名入局玩家先在 `BET_FRONT` 阶段投入该金额，使用 `operation=1`；这笔投入扣减玩家积分并计入 `totalBetScore` 和底池，但不计入盲注后的本轮跟注额。典型 `3440`：

```json
{
  "uid": "<uid>",
  "currentBetScore": 20,
  "totalBetScore": 20,
  "operation": 1,
  "point": 980,
  "pot": 20
}
```

全部玩家完成 `initialBet` 后进入 `BET_BLIND`，小盲再投入 10、大盲再投入 20，`operation=2`。所以小盲的累计投入为 30、大盲为 40；客户端按 `currentBetScore` 累加后减去 `initialBet`，牌桌上显示的盲注仍分别是 10 和 20：

```json
{"uid":"<uid>","currentBetScore":10,"totalBetScore":30,"operation":2,"point":1329,"pot":130}
```

### 6.3 常规下注动作

`3426 DZPK_OPERATION_PUSH` 是操作选项数组。线上样本中，`data` 和 `playerAmount` 使用最小分单位，而客户端把这两个字段除以 100 显示；例如跟注选项 `{"operation":7,"data":115,"playerAmount":460}` 对应客户端发送 `3162` 的 `{"operation":7,"operationData":1.15}`。`playerAmount` 表示当前玩家可用分数，应在每个选项中保持为同一个玩家余额，不能用跟注额或 0 代替。

常规不秀牌客户端的操作枚举与字段用途：

| operation | 客户端用途 | `3426.data` |
| ---: | --- | --- |
| 3 | 底池快捷选项 | 分单位金额 |
| 6 | 弃牌 | 0 |
| 7 | 跟注 | 分单位跟注额 |
| 8 | 加注滑条 | 分单位的最小加注目标 |
| 9 | 全下 | 0 |
| 10 | 过牌 | 0 |
| 12 | 无人下注时的下注滑条 | 分单位的最小下注额 |
| 15 | 开启自定义加注/底池快捷按钮 | 必须带 `userData.bigBlind`，客户端据此生成 BB 倍数快捷项 |

客户端 `3162.operationData` 使用显示货币单位（即 `3426.data / 100`）。加注/下注和底池快捷动作（operation 3/4/5/13/14/15）应将其乘以 100 转回分单位；不能把该值解释为底池倍数。发送 operation 15 且附带 `userData.bigBlind`，客户端才会按桌面设置展示底池/BB 快捷按钮。服务端实际扣款和广播仍以服务端状态计算为准。

客户端动作消息：

```json
{
  "uid": "<uid>",
  "operation": 7,
  "operationData": 0.1
}
```

`3440.currentBetScore` 是本次动作实际投入分数，`totalBetScore` 是本局累计投入分数（包含 `operation=1` 的 `initialBet`）。例如玩家本局已投入 40 分，本次跟注 10 分，则两个字段分别为 10 和 50。

服务端确认：

```json
{
  "uid": "<uid>",
  "currentBetScore": 10,
  "totalBetScore": 40,
  "operation": 7,
  "point": 460,
  "pot": 160
}
```

日志中观察到 `operation` 包括：

| 值 | 日志表现 | 推断 |
| ---: | --- | --- |
| 1 | 多名玩家各投入 20 | 前置下注 |
| 2 | 小盲/大盲分别投入 10/20 | 盲注 |
| 3 | `3426` 中出现的底池快捷选项 | 客户端快捷下注选项 |
| 4/5/13/14 | 快捷下注/加注选项金额 | 客户端底池快捷选项 |
| 6 | `currentBetScore=0` | 弃牌候选动作 |
| 7 | `operationData` 为显示货币单位的小数，`3440.currentBetScore` 为其乘 100 后的分值 | 跟注 |
| 8 | 客户端加注滑条选项 | 加注 |
| 9 | `point=0` 或投入剩余分 | 全下候选动作 |
| 10 | 客户端过牌按钮 | 过牌 |
| 12 | 客户端下注滑条选项 | 无人下注时下注 |
| 15 | 自定义加注/GTO 建议动作 | 按客户端当前动作选项保留原始枚举值 |

最终应以 `3440 DZPK_ACTION_BET_PUSH` 为准，不能以按钮点击或客户端发送成功代替服务端确认。

### 6.4 发牌和不秀牌行为

| 状态 | 消息 | 说明 |
| --- | --- | --- |
| `DEAL_PERFLOP` | `DZPK_DEAL_DI_PUSH` | 发底牌通知；无权限牌可能隐藏 |
| `DEAL_FLOP` | `DZPK_DEAL_FAN_PUSH` | 3 张公共牌 |

由于 `forceShowCard=false`，结算时不是所有玩家都必须通过 `3441` 亮牌。`3432` 结算数组中常见部分玩家只有 `showCards` 或没有完整 `cardTypeInfo`，这表示客户端只展示服务端授权的牌。

### 6.5 结算

`3432 DZPK_INNING_RESULT_PUSH` 是玩家数组：

```json
{
  "cardTypeInfo": {
    "pokerEnumList": ["DIAMOND_5", "DIAMOND_8", "SPADE_9", "CLUB_10", "SPADE_10"],
    "handCardList": [4,7,47,22,48],
    "cardTypeId": 2
  },
  "xiaZhuData": 500,
  "insuranceBet": 0,
  "insuranceProfit": 0,
  "isWin": false,
  "uid": "<uid>",
  "score": -500,
  "point": 230,
  "handPais": [4,7,47,22,48],
  "pos": 2
}
```

字段含义：`xiaZhuData` 为累计下注，`score` 为本局输赢分，`point` 为结算后携带分，`cardTypeInfo` 为牌型，`handPais` 为最终五张牌，`insuranceBet/insuranceProfit` 为保险字段，`isWin` 表示是否赢得主牌局。

本日志中部分玩家在牌局提前结束时没有完整牌型信息，这属于不秀牌和弃牌后的正常权限表现，不能当作协议缺失。

## 7. 保险、补分、回放和退出

### 7.1 保险

房间能力配置 `openInsurance=true`，但 `3465 DZPK_FORCE_INSURANCE_CONF_RES` 返回：

```json
{"switch":false,"ratio":0}
```

日志仍出现部分 `3448 DZPK_PUSH_INSURANCE_TIPS_MSG`、`3449 DZPK_PUSH_BUY_INSURANCE_MSG` 和 `3454 DZPK_PUSH_INSURANCE_HIT_POOL_MSG`，说明保险协议作为旁路能力存在；是否可购买以当前牌局消息中的 `switchOn`、`ratio` 和提示字段为准。

### 7.2 补分

普通房间 `carryMin=500`。客户端面板把分值按 `100` 缩放为显示单位，因此提交的 `carryIn` 是显示单位；游戏服须乘以 `100` 还原成分值，再校验最低带入、钱包余额并记入座位积分。成功响应中的 `carryIn` 和 `carryBalance` 仍使用分值。客户端可能发送：

```json
{"carryIn":5}
```

服务端通过 `3229 CARRYIN_RESULT` 返回入座补分面板数据。客户端会读取 `carryMin`、`carryMax`、`configCarryMax` 和 `accountBalance` 初始化金额滑杆；`configCarryMax` 必须为有效数值。无限上限房间用玩家可用余额作为面板上限。服务端通过 `3230 CARRY_SCORE_RESULT` 返回实际补分结果；`3445 PUSH_CARRYIN_TIPS_USER_LIST` 提供可补分玩家和 12 秒倒计时。

### 7.3 回放和退出

客户端可发送 `3167 DZPK_SEND_GameBackReq`，服务端用 `3446 DZPK_PUSH_GameBackMsg` 返回回放列表。点击单局详情后，客户端另外请求大厅 `op=46`，服务端通过 `GAME_RECORD_DETAIL_API` 返回 `{exploitsInfoMsgs:[detail]}`。详情至少需要 `gameInningId`、`gameRoomUnion.roomConfig`，以及 JSON 字符串字段 `inningResults`、`roundList`、`inningInfo` 和数组字段 `memberResults`。客户端 `HoldemHistoryModel.onPushRecordDetail` 会无条件解析前三个 JSON 字符串，并遍历 `memberResults`。下注行需提供 `roundBetScore`、`currentBetScore`、`totalBetScore` 和 `pot`；公共牌街道需有 `gameState=DEAL_FLOP/DEAL_TURN/DEAL_RIVER` 的记录，供客户端读取该街底池和公共牌。`roundList` 必须保留跨玩家的真实时间顺序，不能按 `pot` 排序；客户端按顺序逐条扣减 `memberResults[].openingPoint` 来显示玩家剩余筹码。`memberResults[].posName` 是客户端位置名称表的数值索引（BTN=1、SB=2、BB=3 等），不是座位字符串。`roundList[].operationType=11` 是客户端 `GameOptNames.SHOW` 摊牌标记（`gameState=11`）；旁观者查看机器人牌局时也必须由已摊牌玩家的 `SHOW` 事件触发结果面板初始化。未授权展示的玩家不能在 `inningResults` 或 `memberResults[].pais` 中提供底牌；`inningInfo.forceShowCard` 应反映该局配置。离开流程通常包括 `2110 SEND_LEVEL_OUT`、`3436 USER_STANDUP_ROOM`、`2205 USER_LEVEL_ROOM`、积分更新和辅助连接 `6106 <game>EXIT`。

开发环境的德州现金桌将当前房间生命周期内的全部已结束牌局保存在房间对象的内存 `history` 中，收到 `3167` 后按 `roomId`、`beginNum/endNum` 和 `excellentGame` 查询并返回 `3446`。按当前线上客户端，普通回放请求的 `beginNum/endNum` 是从 0 开始的局号索引，包含首尾；例如客户端要局号 80 时发送 `79/79`。两个负数表示请求最新一页，回放按局号升序返回，客户端取列表最后一局作为最新局；`totalNum` 必须是可导航的最大已完成局号，不能只返回当前分页条数。精彩牌局用 `excellentGame=true, beginNum=0, endNum=0` 请求全部匹配局。回放操作项包含客户端回放组件分别读取的 `operate`（优秀牌局筛选）、`operationType`、`bet`、`currentBetScore`、`totalBetScore`、`pot` 和数字 `gameState` 字段；局记录含 `currentInningNum`、`firstGameList`、`secondGameList`，玩家项含 `uid`、`score`、`cardTypeId`、`cards`、`handPais`、`commonPoker`、`operateList`。服务端内存另外保存不下发给 `3446` 的逐局 `roundEvents` 时间线和详情适配元数据（`openingPoint`、数值 `posName`、`showCards`、完整 `cardTypeInfo`）；详情构造时据此生成 `roundBetScore` 和 `DEAL_*` 行，并按真实顺序输出。内存记录随房间回收或服务进程重启清空。

线上不能使用上述进程内存历史。现有 game-server -> data-center RPC 的 `GetRecords/GetRecordDetail` 只返回通用牌局摘要和 `RecordLog`，没有德州回放所需的逐手牌面、下注操作和局号范围查询字段，因此不能把摘要伪装成 `3446` 回放。线上回放还未完成：需要先扩展 data-center 回放查询契约，再由 game-server 通过 Redis 缓存优先查询、未命中时调用 data-center（由 data-center 访问 ES），并映射为客户端 `3446` 结构。当前生产环境不读取房间内存历史。

### 回放列表玩家字段

线上 `3446` 回放列表中的 `firstGameList` 玩家项由 `DzpkHistoryItem` 渲染。客户端读取顶层 `userName`、`userIcon`、数字 `posName`、`score`、`isWin`、`showCards`、`cardTypePokers`、`commonPoker` 和 `operateList`；其中 `showCards` 是两张底牌数组，未授权时用 `[-1,-1]`，`handPais` 是最终五张组合牌。`operateList` 需要包含 `gameState=3/5/7/9` 的底牌、翻牌、转牌和河牌阶段，客户端据此显示回顾牌面。下注操作项不得携带未授权底牌；`cards`、`handPais`、`showCards` 与阶段操作中的底牌都必须遵守摊牌权限。回放盈亏按 `isWin` 显示，仅赢家显示总盈亏。

### 回顾详情摊牌牌面展示

当前 `historyContent` 界面实际使用 `assets/main/index.88f4e.js` 中的 `HoldemHistoryModel`、`HoldemHistoryRoundTitleItem` 和 `HoldemHistoryOpenCardItem`。必须保持原版客户端逻辑，由服务端按各消息的字段语义返回数据；不得为了掩盖字段错误修改客户端渲染、清空公共牌或隐藏列表。

`op=46` 的 `inningResults[].handPais` 是已授权公开的两张底牌，未授权时为空数组；`commonPokerList` 是已经发出的公共牌（河牌结束时为五张）。`cardTypeInfo.handCardList` 和回顾列表的 `cardTypePokers` 才是最终最佳五张组合，用于牌型及高亮。不能将结算或回顾列表的最佳五张 `handPais` 直接复用于详情字段。原版解析器将详情 `handPais` 映射为 `holdCards`，将 `commonPokerList` 映射为 `commonCards`；原版玩家行分别渲染两组牌，并按 `cardTypePokers` 高亮最佳五张，其余牌置灰。因此完整摊牌是两张底牌加五张公共牌共七张，五张最佳组合亮显；错误传入五张底牌字段才会形成十张。阶段标题仍使用完整公共牌。

`assets/Holdem/index.55219.js` 中的旧组件 `DzpkHistoryDetail` 同样分别读取详情底牌与公共牌。两套客户端保持原版；回归检查需将服务端实际列表/详情送入原版 `HoldemHistoryModel.onPushRecordDetail`、`HoldemHistoryOpenCardItem.updateObject`，验证底牌为两张、公共牌完整、七张不重复、最佳五张高亮，以及未授权底牌不泄露。历史内存记录仍保留原始牌面，查询详情时做字段适配，不能破坏原始记录或改写真实输赢分数。

## 9. 实现建议

1. 以 `ROOM_TYPE_RESULT`/`ROOM_INFO` 的 `playMode=1`、`gameRoomConfigId=1924`、`forceShowCard=false` 识别普通不秀牌房间。
2. 以 `3263` 驱动牌局状态机，以 `3427` 至 `3430` 驱动发牌事件。
3. 将 `3440` 作为所有下注、弃牌、加注和全下动作的服务端确认事件。
4. 对 `operation` 和 `operationData` 保留原始值，中文动作名称应来自客户端枚举，不能只凭单条日志硬编码。
5. `3441` 是条件性亮牌事件；不秀牌房间不得按全员展示处理。
6. `3432` 的玩家数组允许字段缺失，尤其是弃牌玩家和未授权底牌。
7. `3260` 快照恢复优先级高于按状态字符串重放，避免重连时重复处理已经完成的街道。
8. 保险、GTO、宝箱、积分、公证和回放属于旁路模块，与主牌局状态机解耦。
9. 生产环境不要记录 token、openId、设备 ID、IP 编码值和完整用户资料。

## 10. 结论

本次日志确认的是普通不秀牌德州扑克：

```text
gameRoomConfigId=1924
playMode=1
gameName=常规德州(不秀牌)0.1/0.2(0.2)
smallBlind=10
bigBlind=20
initialBet=20
forceShowCard=false
criticalFlag=false
```

核心流程为：

```text
登录/进房
 -> 房间快照或牌局恢复
 -> BET_FRONT
 -> BET_BLIND
 -> DEAL_PERFLOP
 -> BET_PERFLOP
 -> DEAL_FLOP
 -> BET_FLOP
 -> DEAL_TURN
 -> BET_TURN
 -> DEAL_RIVER
 -> BET_RIVER
 -> SETTLE
 -> 条件性亮牌和结果结算
```

与暴击德州和 AOF 必推的主要区别是：该房间 `playMode=1`、`gameRoomConfigId=1924`、`forceShowCard=false`、`aofBet=0`，采用标准的逐街下注和弃牌/加注流程；结算只展示服务端授权的牌，不会像秀牌或 AOF 房间一样统一亮出所有底牌。
