## 4. 进房和房间同步流程

客户端发送 `1105 ROOM_LOGIN`：

```json
{
  "isAutoLogin": true,
  "userId": "<uid>",
  "openId": "<openId>",
  "userToken": "<token>",
  "version": "<client-version>",
  "cVersion": 20240607,
  "deviceId": "<deviceId>",
  "language": 1,
  "openHundredGame": false,
  "clubId": "<clubId>",
  "packetId": 5,
  "isApiLogin": true,
  "currency": "CNY",
  "plat": 4,
  "roomId": "<roomId>",
  "isInRoom": false
}
```

服务端通过 `1205 ROOM_LOGIN` 返回服务端时间、俱乐部、汇率和快捷换桌状态。主连接随后执行：

1. `2102 SEND_JOIN_ROOM`：申请加入房间。
2. `2219 DZPK_PUSH_WATCHGAME`：旁观玩家列表。
3. `2201 ROOM_TYPE_RESULT`：普通不秀牌配置。
4. `2117/2220 SEND_GAME_SETTING/DZPK_PUSH_GAME_SETTING`：游戏设置。
5. `3178/3465 DZPK_FORCE_INSURANCE_CONF_REQ/RES`：强制保险设置，日志返回 `{switch:false,ratio:0}`。
6. `2200/2221 COMMON_SWITCH_REQ/RES`：通用开关。
7. `2111 LOGIN_ROOM`：正式进入房间。
8. `2206 ROOM_INFO`：玩家、座位、旁观者、局号和配置快照。

进入时 `3260 NIUNIU_INNING_BEGIN_INFO` 可能是 `BET_PERFLOP` 等中间状态，表示恢复正在进行的牌局；重新连接不能假定从 `BET_FRONT` 开始。

## 6. 普通不秀牌牌局流程

### 6.1 状态机

日志观察到的完整状态集合：

```text
BET_FRONT
 -> BET_BLIND
 -> DEAL_PERFLOP
 -> BET_PERFLOP
 -> DEAL_FLOP
 -> BET_FLOP
 -> DEAL_TURN
 -> BET_TURN
 -> DEAL_RIVER
 -> BET_RIVER
 -> SETTLE
```

短牌局可能在翻牌前或翻牌圈因其他玩家弃牌直接进入 `SETTLE`，不一定包含转牌和河牌。

### 6.2 前置下注和盲注

普通房间配置 `initialBet=20`。典型 `3440`：

```json
{
  "uid": "<uid>",
  "currentBetScore": 20,
  "totalBetScore": 20,
  "operation": 1,
  "point": 980,
  "pot": 20
}
```

进入 `BET_BLIND` 后，小盲增加 10，大盲增加 20：

```json
{"uid":"<uid>","currentBetScore":10,"totalBetScore":30,"operation":2,"point":1329,"pot":130}
```

### 6.3 常规下注动作

客户端动作消息：

```json
{
  "uid": "<uid>",
  "operation": 7,
  "operationData": 0.1
}
```

服务端确认：

```json
{
  "uid": "<uid>",
  "currentBetScore": 10,
  "totalBetScore": 40,
  "operation": 7,
  "point": 460,
  "pot": 160
}
```

日志中观察到 `operation` 包括：

| 值 | 日志表现 | 推断 |
| ---: | --- | --- |
| 1 | 多名玩家各投入 20 | 前置下注 |
| 2 | 小盲/大盲分别投入 10/20 | 盲注 |
| 3 | 增加到跟注额度 | 跟注/补齐类动作 |
| 4 | 大额增加，底池明显扩大 | 加注类动作 |
| 5 | 特殊金额增加 | 需要结合客户端枚举确认 |
| 6 | `currentBetScore=0` | 弃牌候选动作 |
| 7 | `operationData` 为小数盲注倍数 | 下注/加注 |
| 9 | `point=0` 或投入剩余分 | 全下候选动作 |
| 10 | 玩家停止继续下注 | 弃牌/结束行动候选动作 |
| 12/15 | 特殊加注或 GTO/策略动作 | 必须保留原始枚举值 |

最终应以 `3440 DZPK_ACTION_BET_PUSH` 为准，不能以按钮点击或客户端发送成功代替服务端确认。

### 6.4 发牌和不秀牌行为

| 状态 | 消息 | 说明 |
| --- | --- | --- |
| `DEAL_PERFLOP` | `DZPK_DEAL_DI_PUSH` | 发底牌通知；无权限牌可能隐藏 |
| `DEAL_FLOP` | `DZPK_DEAL_FAN_PUSH` | 3 张公共牌 |
| `DEAL_TURN` | `DZPK_DEAL_ZHUANG_PUSH` | 1 张转牌 |
| `DEAL_RIVER` | `DZPK_DEAL_HE_PUSH` | 1 张河牌 |

由于 `forceShowCard=false`，结算时不是所有玩家都必须通过 `3441` 亮牌。`3432` 结算数组中常见部分玩家只有 `showCards` 或没有完整 `cardTypeInfo`，这表示客户端只展示服务端授权的牌。

### 6.5 结算

`3432 DZPK_INNING_RESULT_PUSH` 是玩家数组：

```json
{
  "cardTypeInfo": {
    "pokerEnumList": ["DIAMOND_5", "DIAMOND_8", "SPADE_9", "CLUB_10", "SPADE_10"],
    "handCardList": [4,7,47,22,48],
    "cardTypeId": 2
  },
  "xiaZhuData": 500,
  "insuranceBet": 0,
  "insuranceProfit": 0,
  "isWin": false,
  "uid": "<uid>",
  "score": -500,
  "point": 230,
  "handPais": [4,7,47,22,48],
  "pos": 2

```

字段含义：`xiaZhuData` 为累计下注，`score` 为本局输赢分，`point` 为结算后携带分，`cardTypeInfo` 为牌型，`handPais` 为最终五张牌，`insuranceBet/insuranceProfit` 为保险字段，`isWin` 表示是否赢得主牌局。

本日志中部分玩家在牌局提前结束时没有完整牌型信息，这属于不秀牌和弃牌后的正常权限表现，不能当作协议缺失。

## 7. 保险、补分、回放和退出

### 7.1 保险

房间能力配置 `openInsurance=true`，但 `3465 DZPK_FORCE_INSURANCE_CONF_RES` 返回：

```json
{"switch":false,"ratio":0}
```

日志仍出现部分 `3448 DZPK_PUSH_INSURANCE_TIPS_MSG`、`3449 DZPK_PUSH_BUY_INSURANCE_MSG` 和 `3454 DZPK_PUSH_INSURANCE_HIT_POOL_MSG`，说明保险协议作为旁路能力存在；是否可购买以当前牌局消息中的 `switchOn`、`ratio` 和提示字段为准。

### 7.2 补分

普通房间 `carryMin=500`。客户端可能发送：

```json
{"carryIn":5}
```

服务端通过 `3229 CARRYIN_RESULT` 返回可补分范围和剩余时间，并通过 `3230 CARRY_SCORE_RESULT` 返回实际补分结果。`3445 PUSH_CARRYIN_TIPS_USER_LIST` 提供可补分玩家和 12 秒倒计时。

### 7.3 回放和退出

客户端可发送 `3167 DZPK_SEND_GameBackReq`，服务端用 `3446 DZPK_PUSH_GameBackMsg` 返回回放列表。离开流程通常包括 `2110 SEND_LEVEL_OUT`、`3436 USER_STANDUP_ROOM`、`2205 USER_LEVEL_ROOM`、积分更新和辅助连接 `6106 <game>EXIT`。

## 8. 与其他德州玩法的差异

| 项目 | 普通不秀牌（本日志） | 暴击德州 | AOF 必推 |
| --- | --- | --- | --- |
| 配置 ID | `1924` | `1921` | `1927` |
| `playMode` | `1` | `3` | `9` |
| 盲注 | `10/20` | 样本 `10/20` | `100/200` |
| `initialBet` | `20` | `20` | `0` |
| `forceShowCard` | `false` | `true` | `true` |
| `criticalFlag` | `false` | `true` | `false` |
| `aofBet` | `0` | 无 | `100` |
| 动作模式 | 常规下注、弃牌、加注、全下 | 普通动作 + 暴击配置 | 固定投入 + 全下/退出 |
| 结算亮牌 | 只展示授权牌 | 强制展示配置 | 全员亮牌 |

## 9. 实现建议

1. 以 `ROOM_TYPE_RESULT`/`ROOM_INFO` 的 `playMode=1`、`gameRoomConfigId=1924`、`forceShowCard=false` 识别普通不秀牌房间。
2. 以 `3263` 驱动牌局状态机，以 `3427` 至 `3430` 驱动发牌事件。
3. 将 `3440` 作为所有下注、弃牌、加注和全下动作的服务端确认事件。
4. 对 `operation` 和 `operationData` 保留原始值，中文动作名称应来自客户端枚举，不能只凭单条日志硬编码。
5. `3441` 是条件性亮牌事件；不秀牌房间不得按全员展示处理。
6. `3432` 的玩家数组允许字段缺失，尤其是弃牌玩家和未授权底牌。
7. `3260` 快照恢复优先级高于按状态字符串重放，避免重连时重复处理已经完成的街道。
8. 保险、GTO、宝箱、积分、公证和回放属于旁路模块，与主牌局状态机解耦。
9. 生产环境不要记录 token、openId、设备 ID、IP 编码值和完整用户资料。

## 10. 结论

本次日志确认的是普通不秀牌德州扑克：

```text
gameRoomConfigId=1924
playMode=1
gameName=常规德州(不秀牌)0.1/0.2(0.2)
smallBlind=10
bigBlind=20
initialBet=20
forceShowCard=false
criticalFlag=false
```

核心流程为：

```text
登录/进房
 -> 房间快照或牌局恢复
 -> BET_FRONT
 -> BET_BLIND
 -> DEAL_PERFLOP
 -> BET_PERFLOP
 -> DEAL_FLOP
 -> BET_FLOP
 -> DEAL_TURN
 -> BET_TURN
 -> DEAL_RIVER
 -> BET_RIVER
 -> SETTLE
 -> 条件性亮牌和结果结算
```

与暴击德州和 AOF 必推的主要区别是：该房间 `playMode=1`、`gameRoomConfigId=1924`、`forceShowCard=false`、`aofBet=0`，采用标准的逐街下注和弃牌/加注流程；结算只展示服务端授权的牌，不会像秀牌或 AOF 房间一样统一亮出所有底牌。
