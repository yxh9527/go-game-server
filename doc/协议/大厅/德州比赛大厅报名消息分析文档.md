## 原版详情页签补充（2026-10-30）

原版大厅 chunks/434 通过同一个 op=36/type=1 返回值渲染奖励、玩家与盲注页签；不是分别请求 op=44/62/63。这三个数组缺失时原版直接显示空列表：

- MTTRankPrices：奖励配置映射为 rank（例如 1/1）、from、to、price、ticketNums；price 保留最小货币单位，原版除以 100 显示，ticketNums 为门票张数。保留 currency 与原 items，不把不同币种相加；原版此面板只显示本场配置币种的金额。优先使用比赛已经锁定的 award_json，未锁定且只配置 award_id 时才引用已加载模板。
- MTTUserRanks：真实参赛记录映射为 userId、userName、icon、point、roomId、rank；存活玩家按积分降序，淘汰/结束玩家按已有最终名次。头像复用公共会员头像映射。未报名或没有有效参赛记录时保持空数组，不补假玩家。
- blindConfig：字符串数组，每项格式为级别/小盲/大盲，例如 1/50/100。报名后已锁定的真实盲注计划优先于后改模板；未使用模板的固定盲注比赛只显示实际固定的一档，不编造后续级别。原版 increaseBindTime 使用分钟，计划 interval 使用秒，展示时换算。

生产大厅启动/业务热更新通过统一 RPC 加载奖励和盲注模板到常驻内存；管理端修改通过现有 match 频道广播 match_metadata，data 仍为 JSON 字符串，内容为 {kind:award或blinds,row:完整模板行}。玩家读取比赛详情只查大厅缓存，不直接查询 MySQL。dev 进程间内存总线不共享，由内部比赛快照附带 metadata 同步模板；该字段不透传客户端。业务热更新原位扩展缓存，不清除原有比赛快照序号或成员。

## 2. 接口时序

```text
op=42  指定比赛状态/资格查询
  -> op=36  指定比赛详情
  -> op=44  大厅通用状态刷新
  -> op=35  比赛列表
  -> op=62  用户/大厅状态刷新
  -> 后续应由用户操作触发报名提交（本日志未捕获）
```

所有请求使用：

```text
GET https://alobby.bucoa.top/internal/v1/do
```

公共参数包括 `token`、`userId`、`clubId`、`op` 和 Base64 编码的 `param`。`msgCode=200` 只代表接口请求处理成功，不代表报名成功。

## 7. 从大厅到比赛牌局的预期流程

```text
op=35 查询比赛列表
  -> op=36 查询比赛详情
  -> op=42 查询用户/俱乐部资格或报名状态
  -> op=44/op=62 刷新大厅状态
  -> 用户点击报名
  -> 报名提交接口（本日志未捕获）
  -> 返回报名成功或状态变化
  -> 比赛开始后分配比赛房间
  -> 使用 roomType=101 和 domain 建立比赛连接
  -> ROOM_LOGIN / LOGIN_ROOM
  -> 比赛牌局消息
```

比赛详情的 `domain` 是比赛专用候选域名，`roomType=101` 表示比赛房间和普通现金桌 `roomType=19` 使用不同房间类型。进入比赛房间后，才会出现 `ROOM_LOGIN`、`ROOM_INFO`、`BRNN_GAME_STATE_PUSH`、`DZPK_ACTION_BET_PUSH` 等消息。

## 8. 实现建议

1. 对 `param` 先 Base64 解码，再按键值对解析。
2. 对 `championshipName`、`consults` 等 JSON 字符串进行二次解析。
3. 比赛列表和详情按 `id` 关联，列表用于展示，详情用于规则和状态。
4. 报名按钮状态应综合 `registerStatus`、`playerStatus`、`championshipStatus`、`register`、费用和当前时间。
5. 不要仅凭 `msgCode=200` 判断报名成功。
6. 报名成功应等待明确的状态变化、用户报名标志、比赛房间号或成功事件。
7. 免费比赛需校验 `registerType=4`、`registerGold=0`、`serviceGold=0`、`registerTicket=0`。
8. 比赛房间使用 `roomType=101`，不能直接套用普通现金桌 `roomType=19` 的连接假设。
9. 生产日志必须脱敏 token、用户身份、排行榜和房间域名。
