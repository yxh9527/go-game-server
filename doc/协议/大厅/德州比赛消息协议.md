# 德州比赛消息协议

## 1. 协议概览

本日志记录的是德州扑克比赛大厅的比赛列表查询，不是普通现金桌房间配置。客户端切换到德州比赛页面后，通过 HTTP 接口获取比赛列表。

| 项目 | 内容 |
| --- | --- |
| 游戏名称 | Holdem，德州扑克比赛 |
| `gameType` | `19` |
| `subGameType` | `101` |
| 房间类型 | `roomType: 101` |
| 请求操作 | `op=35` |
| 查询页码 | `pageNum=1` |
| 每页数量 | `pageSize=1000` |
| 比赛分类 | `category=0` |
| 返回状态 | `msgCode=200` |
| 日志中比赛数量 | 4 场比赛记录 |

本次日志只包含比赛列表 HTTP 请求和响应，没有 MQTT 业务消息，也没有进入具体比赛房间后的 RoomSocket 游戏消息。

## 2. 大厅切换消息

```json
{
  "type": "changeType",
  "value": {
    "gameType": 19,
    "subGameType": 101
  }
}
```

客户端随后执行：

```text
preloadByChangeType
preloadGameSceneRes
requestGameType: 101
gameCfg: 19
gameName: Holdem
```

## 3. 比赛列表请求

请求接口：

```text
GET /internal/v1/do
```

`param` Base64 解码后为：

```text
pageNum=1&pageSize=1000&category=0&op=35
```

请求 URL 还携带：

```text
userId=2223152
clubId=125566
```

同一请求在日志中出现了两次，服务端均返回成功结果。

## 4. 响应封装

```json
{
  "msgCode": 200,
  "errMsg": null,
  "data": [
    {
      "id": 19566,
      "gameType": 19,
      "roomType": 101
    }
  ]
}
```

`data` 数组中的每一项代表一场比赛。

## 8. 状态字段初步判断

根据本次日志观察：

| 字段 | 观察到的值 | 说明 |
| --- | --- | --- |
| `championshipStatus` | `1`、`2` | `1` 出现在尚未开始的比赛，`2` 出现在当前进行或开放中的比赛 |
| `status` | `1`、`2` | 与比赛阶段相关，具体枚举仍需结合比赛房间消息确认 |
| `registerStatus` | `1` | 当前比赛列表中的报名状态 |
| `playerStatus` | `0` | 当前用户未处于比赛中的特殊状态 |
| `register` | `false` | 当前用户未报名 |
| `rest` | `false` | 当前用户不在休息状态 |

以上是基于单份大厅日志的观察，不等同于最终枚举定义。

## 9. 通信流程

1. 前端发送 `changeType`，切换到 `gameType=19`、`subGameType=101`。
2. 客户端预加载德州扑克比赛页面资源。
3. 大厅通过 HTTP `op=35` 请求比赛列表。
4. 请求参数指定第 1 页、每页 1000 条、比赛分类 `0`。
5. 服务端返回比赛对象数组。
6. 前端根据 `data` 刷新比赛列表，并展示报名费、奖池、人数和盲注信息。
7. 用户点击具体比赛后，才可能进入比赛 RoomSocket；本次日志没有记录该阶段。
