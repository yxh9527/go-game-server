# 房间列表公共人数

## 入口与范围

hall 的 op=38 统一为 roomInfoData[].totalPeople 生成展示人数，字段仍为非负整数。
普通棋牌、百人游戏、slots 及后续新增游戏均经过同一公共入口，不使用游戏类型白名单。

实现：hall/src/room-population.js；公共配置：hall/src/room-population-config.js。
这是正式大厅展示功能，dev 和 prod 共用，保留在生产包内，不放入 cache/。
测试在 test/hall/room-population.test.js。

展示人数不会写回房间配置、房间成员、旁观列表或排行榜，也不会创建机器人、创建/唤醒房间。
分房、80% 满座扩容、八小时生命周期以及比赛 op=35 的报名/存活人数仍使用真实数据。

## 时段与准入

默认按 Asia/Shanghai（北京时间）计算，与服务器操作系统时区无关。

| 北京时间 | 基础活跃倍率变化 | 趋势 |
| --- | --- | --- |
| 00:00–03:00 | 1.00 → 0.20 | 逐渐减少 |
| 03:00–06:00 | 0.20 | 最低平台 |
| 06:00–12:00 | 0.20 → 0.65 | 逐渐增加 |
| 12:00–14:00 | 0.65 → 0.45 | 逐渐减少 |
| 14:00–24:00 | 0.45 → 1.00 | 逐渐增加 |

时段内线性插值，跨午夜连续；在趋势上叠加小幅随机变化，不保证每一次刷新都沿同一方向。
准入优先使用实际返回的 carryMin（与客户端金额单位一致）；没有有效正数准入时，按顺序使用
hundredMinBet、ante、initialBet、bigBlind、smallBlind，最后回退为 0。
同一游戏在同一时刻共用随机波动，准入越高人数越少；整数取整或上下限处允许相同人数。
不会按当前请求返回了多少档房间重新分配权重，筛选、分页或请求顺序不改变同一配置的数值。

计算方式：

~~~text
准入衰减 = (1 + 准入 / entryReference) ^ (-entryDecay)
准入系数 = minimumActivityShare + (1 - minimumActivityShare) × 准入衰减
人数 = round(minPeople + (maxPeople - minPeople) × 准入系数 × 时段倍率 × 随机系数)
随机系数范围 = [1 - randomAmplitude, 1 + randomAmplitude]
最终人数限制在 minPeople～maxPeople
~~~

## 可调整参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| enabled | true | 关闭时恢复已有列表人数逻辑：已接入现金桌取真实房间池人数，其余取配置字段 |
| timeZone | Asia/Shanghai | 业务时区 |
| refreshSeconds | 5 | 人数按此时间桶更新；同桶重复请求结果一致 |
| minPeople / maxPeople | 8 / 100 | 所有房间展示人数的下限/上限；单个房间最多 100 人 |
| entryReference | 500 | 准入基准，单位同 carryMin；增大后高准入房间人数提高 |
| entryDecay | 0.45 | 准入衰减强度，越大则高准入房间人数越少 |
| minimumActivityShare | 0.15 | 高准入房间至少保留人数区间的 15% 参与时段变化，避免全天取整成最低人数；0 恢复完全衰减 |
| randomAmplitude | 0.18 | 随机上下浮动幅度，默认 ±18%；0 为关闭随机，仅保留时段趋势 |
| randomPeriodSeconds | 10 | 随机目标间隔，目标之间平滑过渡；大厅按约 5 秒拉取，短时间内可见变化，个别相邻刷新仍可能相同 |
| activity.midnight | 1.00 | 午夜峰值 |
| activity.low | 0.20 | 03:00–06:00 低谷 |
| activity.noon | 0.65 | 12:00 午间峰值 |
| activity.afternoon | 0.45 | 14:00 午后低点 |
| seed | gogame-room-population-v1 | 随机序列种子；保持相同可保证多个 hall 实例一致 |

调整各相邻时段端点倍率即可调整涨跌幅度；例如午间下降幅度由 noon - afternoon 决定。
倍率维持 0 ≤ low ≤ afternoon ≤ noon ≤ midnight ≤ 1；不合法输入会被限幅。
单个房间展示人数的硬上限为 100 人，minPeople/maxPeople 配置覆盖值也不能突破此上限；随机波动后的最终值同样限幅。刷新间隔限制在 1～3600 秒，随机幅度限制在 0～50%，避免错误配置产生 NaN 或无限值。

配置文件纳入 hall 的版本化热更新链，修改公共配置后会自动热替换业务，无需重启服务。
hall 启动配置也支持 room_population 对象覆盖同名参数（activity 支持部分覆盖）；
启动 YAML 只在进程启动时读取，在线调参应修改公共 JS 配置，不依赖重启。
若 YAML 已覆盖某参数，该参数仍以覆盖值为准。

人数由游戏身份、绝对时间和种子确定，不创建定时器或逐用户缓存。
相同配置在业务热更新、请求突增和多实例之间保持一致；重复刷新不能加速人数涨跌。
原始大厅和游戏客户端静态文件保持不变。
高准入房间通过 minimumActivityShare 保留时段变化区间，不能只增大随机幅度而让全天基础人数仍被取整成固定值。
若整数取整造成个别房间连续刷新数值相同，可缩短 randomPeriodSeconds 或增大 randomAmplitude；
设置 randomPeriodSeconds 明显大于客户端 op=38 刷新频率，或幅度过小，可能导致连续多次拉取显示相同整数。

## 页面更新链路

当前 static/hall 的 434 房间列表组件原先只为百人、slots 和捕鱼页面启动 5 秒轮询，普通棋牌只在进入/切换时拉取。
因此仅改变接口中的 totalPeople，不会使停留在普通棋牌大厅的页面自动更新。
hall/src/room-list-refresh.js 在资源响应层将该组件已有轮询条件统一为请求 op=38，并使用静默请求；
保留原来的页面隐藏暂停、恢复可见刷新、请求防重、切换页面丢弃旧响应及组件卸载清理，不另加一套计时器。
比赛 op=35 不进入此轮询，仍走原比赛更新逻辑。此适配在 dev/prod 共用，纳入热更新及生产包。
hall/src/web.js 只适配当前 434 房间列表资源的响应，磁盘上的 static 文件不改；升级大厅资源时必须核对匹配位置，不能静默替换不相干代码。
后端调整可直接热更新；已经打开的页面需要刷新一次以加载这条页面刷新链路。
