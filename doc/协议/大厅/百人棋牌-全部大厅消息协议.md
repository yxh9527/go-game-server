# 百人棋牌-全部大厅消息协议

## 1. 协议概览

本文整理百人棋牌“全部大厅”日志中的大厅切换、房间配置查询、状态轮询和 MQTT 心跳消息。该日志没有进入具体牌桌，因此没有采集到牌桌内的下注、发牌、结算等游戏业务消息。

| 项目 | 内容 |
| --- | --- |
| 大厅名称 | 百人棋牌全部大厅 |
| `gameType` | `1000` |
| 全部大厅 `subGameType` | `99` |
| 房间配置接口 | `GET /internal/v1/do`，`op=38` |
| 状态轮询接口 | `GET /internal/v1/do`，`op=63` |
| 房间类型 | `50`、`51`、`52`、`62` |
| 全量房间数量 | 16 个（5 + 5 + 5 + 1） |
| 响应状态 | HTTP `200`，业务 `msgCode=200` |
| MQTT 地址 | `wss://mq.wahaowu.top/mqtt` |

## 2. 大厅切换与子大厅映射

进入全部大厅时，客户端收到：

```json
{
  "type": "changeType",
  "value": {
    "gameType": 1000,
    "subGameType": 99
  }
}
```

客户端日志还显示预加载了以下通用资源：

```text
Holdem -> gameHoldem
Dznn   -> gameDzNiuNiu
Dzjh   -> gameDzjh
```

注意：这些是全部大厅的预加载资源，不足以证明每个 `roomType` 与具体游戏名称的一一对应关系。根据本次日志可以确认的映射只有：

| `subGameType` | 请求条件 | 返回的 `roomType` | 日志确认内容 |
| ---: | --- | ---: | --- |
| `99` | 不带 `roomType` | `50`、`51`、`52`、`62` | 全部大厅房间集合 |
| `1` | `roomType=50` | `50` | 切换并查询 50 类房间 |
| `2` | `roomType=51` | `51` | 切换并查询 51 类房间 |
| `3` | `roomType=52` | `52` | 切换并查询 52 类房间 |
| `5` | `roomType=62` | `62` | 切换并查询 62 类房间 |

## 3. 房间配置请求

### 3.1 全部房间查询

请求：

```text
GET https://alobby.bucoa.top/internal/v1/do
```

`op=38` 请求中的 `param` Base64 解码后为：

```text
gameType=1000&roomClassifications=&op=38
```

该请求返回四种房间类型共 16 个配置：`roomType=50`、`51`、`52` 各 5 个，`roomType=62` 1 个。

### 3.2 指定房间类型查询

客户端按大厅 tab 查询单类房间时，参数分别为：

```text
gameType=1000&roomClassifications=&roomType=50&op=38
gameType=1000&roomClassifications=&roomType=51&op=38
gameType=1000&roomClassifications=&roomType=52&op=38
gameType=1000&roomClassifications=&roomType=62&op=38
```

每个请求响应的 `data[0].gameType` 仍为 `1000`，但 `roomInfoData` 只返回指定 `roomType` 的配置。

请求 URL 还携带 `userId`、`clubId` 和 token 等公共参数。本文不保存完整 token。

## 6. 状态轮询消息

客户端定时请求：

```text
op=63
param=op=63（Base64 编码：b3A9NjM=）
```

响应：

```json
{
  "msgCode": 200,
  "errMsg": null,
  "data": []
}
```

日志中该请求出现多次，属于大厅状态/附加信息轮询，不是百人牌桌下注消息。

## 7. MQTT/WebSocket 消息

日志只捕获到 MQTT 保活心跳，没有捕获业务 `PUBLISH` 消息。

连接地址：

```text
wss://mq.wahaowu.top/mqtt
```

客户端发送：

```json
{
  "protocol": "MQTT",
  "packet": "PINGREQ",
  "flags": 0,
  "remainingLength": 0
}
```

服务端响应：

```json
{
  "protocol": "MQTT",
  "packet": "PINGRESP",
  "flags": 0,
  "remainingLength": 0
}
```

该 `PINGREQ/PINGRESP` 是 MQTT 协议层心跳，不能代表百人游戏业务消息。当前日志没有 `CONNECT`、`SUBSCRIBE` 或 `PUBLISH` 的可读对象日志，因此无法从这份日志确认 MQTT topic 和业务 payload。

## 8. 字段说明

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `gameType` | number | 大厅配置类型；本次为 `1000` |
| `subGameType` | number | 大厅 tab/子类型；`99` 表示全部，`1/2/3/5` 对应四类房间 |
| `roomType` | number | 具体房间类别；本次为 `50/51/52/62` |
| `gameRoomConfigId` | number | 房间配置唯一 ID |
| `totalPeople` | number | 当前大厅人数统计 |
| `playMode` | number | 房间玩法模式代码；本次为 `0` 至 `5`，名称待客户端配置确认 |
| `key` | string | 房间配置组合键；百人房间格式为 `roomType/0/0/false/playMode/0/0/0/0` |
| `hundredGame` | number | 百人类房间标识；本次为 `1` |
| `hundredMaxBet` | number | 单项最大下注值；本次为 `1000000000` |
| `hundredMinBet` | number | 单项最小下注值；本次为 `100` |
| `maintenanceInfoMsg` | string | 维护信息 JSON 字符串；本次无维护项目 |
| `privateRoomOpen` | boolean | 是否开放私人房；本次为 `false` |

## 9. 通信流程总结

1. 大厅先进行 `op=63` 状态查询，返回空数组。
2. 全部大厅触发 `changeType(gameType=1000, subGameType=99)`。
3. 发送 `op=38` 全量房间查询，返回 `roomType=50/51/52/62` 的房间集合。
4. 用户切换 tab 时触发 `subGameType=1/2/3/5`，并通过 `roomType` 参数请求对应房间列表。
5. 大厅继续通过 `op=38` 刷新人数，并通过 `op=63` 轮询附加状态。
6. MQTT 连接只观察到 `PINGREQ/PINGRESP` 心跳；本日志没有牌桌业务 `PUBLISH` 消息。

## 10. 采集限制

- 本文只整理大厅层 HTTP、Cocos `changeType` 和 MQTT 协议层心跳。
- `playMode` 的具体名称、四种 `roomType` 对应的产品名称，以及进入房间后的业务消息，需要结合对应客户端资源或牌桌日志确认。
- 认证 token、用户标识等运行时参数未写入文档，避免将会话凭证作为协议内容保存。
