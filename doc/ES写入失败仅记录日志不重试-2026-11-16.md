## 行为

注单、账变、战绩和回放的 ES 写入，每批只尝试一次。失败日志包含错误及可用的原局号、批次数量或记录 ID，失败批次结束，不自动重投，也不再写 MySQL 原文副本。现金最终注单仍是 go_gp_settlement，详情仍在 log，账变仍在 go_gp_flowing_water。

lottery 新统一资金投递在现有快照中区分“已尝试”和“实际写入成功”：ReportsAttempted／BillAttempted 表示该输出已经处理过；ReportsIndexed／BillStored 仅在实际成功时为真，另保留原批次失败标识。原进度经过失败批次后继续，不能因为失败标志为假再次投递同一输出。后续批次仍可继续保存。

普通下注、撤注退款的输出在现有原快照上保存尝试结果；失败不会再次执行原资金操作。当前原局已删除时不会重建。尝试标记保存失败只记日志，当前进程仍保留已尝试状态，不因此重新发出 ES 请求；不新增额外 Redis 键或恢复任务。

旧游戏原注单／账变通道使用 RunOnce：批量写入失败或写入函数异常时记录日志，结束该批并继续后面的批次。原缓存转交成功后移除，不因未结算标志或定时器再次发送同一缓存对象。批量通道本身仍有界，未处理的新输出仍按原批次形成工作。

报告 ES Bulk 调用显式使用 StopRetrier，关闭客户端库内的自动重试，不能只删除业务重试却让 SDK 再发请求。通用 Run 重试函数保留供其他原业务使用，注单和账变消费者均改用 RunOnce。

## Node 与比赛推进

game-server 原战绩输出每批只调用一次 gateway。无论成功、回执不完整或抛错，处理后移除该批；失败由日志说明，不再设置 retryAt 或指数退避。相同实例业务热更新不会重新加入已移除的失败批次。

gateway 对本批现金报告、回放和既有玩家统计各执行一次投递，不因第一项失败而跳过本批后面的输出；遇到失败仍向调用方报告错误，由调用方记日志并结束本批。金融操作本身的确认、防重和既有业务数据职责保持原规则。

比赛当前手牌的回放投递尝试结束后，即使 ES 写入失败也释放报告等待，不因为报告错误阻止检查点、正常结束或清理。缺少真实参与者报告等原数据采集错误仍单独校验，不能把不完整牌局伪装成正常记录。

## 保留规则

不新增 MySQL 中转、Redis 永久历史、重试队列或人工补写任务。终态快照原完成时间起一小时清理、历史查询结果 180 秒不续期规则保持不变。失败批次可能没有对应 ES 历史，按用户要求只保留日志，不自动补写。

本要求仅针对 ES 报告写入。实际扣款、退款、派奖、带入、比赛报名费／门票等资金责任，继续使用原确认及防重保护，不把资金失败当作成功，也不移除其原有处理机制。
